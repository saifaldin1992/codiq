# تقرير المرحلة 8B — واجهات الأوامر واختبارات القبول

**الحالة:** مكتملة فنياً ومختبرة.  
**النطاق المنفذ:** واجهات أوامر التاجر ومالك المنصة فقط، مرتبطة بمسارات API الخاصة بالمرحلة 8A وبجلسات HTTP الحالية.  
**النطاق غير المنفذ:** Customer UI أو Storefront أو Checkout أو إنشاء طلب أو دفع أو شحن أو تعديل مخزون أو اشتراكات أو خطط. لا يوجد endpoint أو زر جديد خارج ما اعتمد للمرحلة الثامنة.

## 1. ملخص التنفيذ

استبدلت المرحلة 8B صفحات الطلبات التجريبية في لوحتي التاجر ومالك المنصة بواجهات عربية RTL بطابع One UI. الواجهة الجديدة لا تعيد تنفيذ منطق الأعمال؛ بل تستدعي خدمات 8A المقيدة بالجلسة وتعرض النتائج وحالات الخطأ بشكل صريح. تبقى قاعدة PostgreSQL وPrisma وExpress كما هي من 8A، ولم تنشأ هجرة أو تغيير في State Machine أو أي مسار Customer تشغيلي.

| السطح | ما نُفذ |
|---|---|
| التاجر | قوائم أوامر مقيدة بـ`storeSlug`، مرشحات وبحث وتاريخ وcursor pagination، تفاصيل الطلب، سجل الحالة، وإجراءات انتقال الحالة المتاحة فقط. |
| مالك المنصة | قائمة عالمية للقراءة فقط، مرشحات المتجر والتاجر والحالة والبحث والتاريخ، تفاصيل الطلب وسجله، من دون أي إجراء لتغيير الحالة. |
| التجربة | حالات تحميل وفراغ وخطأ وإعادة محاولة، وواجهة هاتف RTL وقائمة جانبية متجاوبة وتركيز لوحة مفاتيح. |
| التزامن | رسالة واضحة بعد `409 ORDER_VERSION_CONFLICT` ثم إعادة تحميل أحدث حالة من الخادم، من دون ادعاء نجاح محلي. |

## 2. الواجهات والمسارات المنفذة

يتشارك السطحان مكوّن `OrderWorkspace`، مع اختلاف واضح في الصلاحيات والعمليات المسموح بها. لا يرسل التاجر `storeId` من الواجهة؛ يتحدد النطاق من `storeSlug` في المسار وجلسة الخادم. أما المالك فيقرأ البيانات عالمياً فقط عبر مسارات المنصة المعتمدة.

| اللوحة | المسارات العملية | السلوك |
|---|---|---|
| التاجر | `/merchant/stores/{storeSlug}/dashboard/orders` ومسارات الحالات | قائمة مقيدة بالمتجر، مع البحث والتاريخ والحالة وتحميل المزيد. |
| التاجر | `/merchant/stores/{storeSlug}/dashboard/orders/{orderId}` | تفاصيل وسجل انتقالات، وزر واحد لكل انتقال مسموح في الحالة الحالية. |
| المالك | `/platform/dashboard/orders` ومسارات الحالات | إشراف عالمي للقراءة فقط، مع مرشحات `storeSlug` و`merchantId`. |
| المالك | `/platform/dashboard/orders/{orderId}` و`/history` | تفاصيل وسجل زمني بلا أزرار أو نموذج لتغيير الحالة. |

يتعامل مسار المالك **قيد التنفيذ** (`/platform/dashboard/orders/fulfillment`) مع `preparation` فقط، كما أُقر صراحة؛ لم تُضف حالة خلفية جديدة.

## 3. سلوك الحالة والعزل في الواجهة

تقرأ الواجهة حالة الطلب وإصداره من الخادم، وتعرض فقط الإجراءات المنصوص عليها في State Machine. لذلك لا يظهر «إلغاء» عند `out_for_delivery`، ولا يظهر «جديدة» عند `processing`، ولا يظهر أي إجراء للحالات النهائية. عند تعارض الإصدار تعيد الواجهة جلب التفاصيل والسجل وتبقي رسالة توضيحية للمستخدم.

| السلوك | النتيجة المنفذة |
|---|---|
| `new → processing` | زر مرئي للتاجر وينجح مع تحديث الحالة والإصدار والسجل. |
| `completed → returned` | زر مرئي للتاجر وينجح، ثم تصبح الحالة نهائية. |
| `processing → new` | لا زر في الواجهة؛ محاولة API مصطنعة تعود `422` وتعيد الواجهة قراءة المصدر. |
| `out_for_delivery → cancelled` | لا زر إلغاء في الواجهة؛ محاولة API مصطنعة تعود `422`. |
| تعارض النسخة | طلب ناجح واحد، وطلب ثانٍ قديم يعود `409` مع رسالة ثم إعادة تحميل. |
| تاجر B إلى طلب A | لا تسريب واجهي؛ يعود طلب A تحت سياق Store-B بـ`404`. |
| Customer إلى أوامر التاجر | يعود `403 IDENTITY_BOUNDARY_DENIED`، ولم تنشأ صفحة Customer للأوامر. |

## 4. نتائج سيناريوهات قبول التاجر — M-01 إلى M-22

شغّل الاختبار الآلي `phase8b.browser-acceptance.mjs` خادماً إنتاجياً محلياً مبنياً، وجلسات متصفح منفصلة، وتاجرين ومتجرين ومالكاً وزبوناً وطلبات حالة متعددة. أنشئت البيانات داخل قاعدة اختبار PostgreSQL ثم عولجت الواجهة عبر HTTP الحقيقي.

| المجموعة | السيناريوهات | النتيجة |
|---|---|---|
| القائمة والترشيح | M-01 إلى M-06 | **نجحت.** ظهرت أوامر Store-A فقط، وعمل البحث والتاريخ والفراغ والـcursor، كما رفضت الواجهة سياق المتجر الناقص. |
| التفاصيل والسجل | M-07 إلى M-10 | **نجحت.** ظهرت تفاصيل البند ولقطة SKU والاسم والسعر التاريخية والسجل؛ وحالة معرف غير موجود آمنة. |
| الحالات والتزامن | M-11 إلى M-18 | **نجحت.** ظهرت الانتقالات الصحيحة فقط، وتحُقق `completed → returned`، ورفضت الانتقالات المخالفة، وأثبت الاختبار `409` وإعادة التحميل وعدم تغيير المخزون. |
| عزل الهوية والمتجر | M-19 إلى M-22 | **نجحت.** منع تبديل المتجر وعبور `orderId` ومسار المنصة وCustomer endpoint بحسب `403` و`404`. |

## 5. نتائج سيناريوهات قبول المالك — O-01 إلى O-07

| السيناريوهات | النتيجة |
|---|---|
| O-01 | **نجح.** أظهرت القائمة العالمية طلباً من Store-A وآخر من Store-B مع المتجر والتاجر والحالة والوقت. |
| O-02 | **نجح.** عملت مسارات الحالة، بما فيها `fulfillment` كمرشح `preparation` فقط. |
| O-03 | **نجح.** عملت مرشحات المتجر والتاجر والحالة والبحث والتاريخ، ثم مسحها. |
| O-04 وO-06 | **نجحا.** عرضت التفاصيل وسجل الحالة نفسه من المسار المباشر ومن صفحة التفاصيل. |
| O-05 | **نجح.** لم يظهر في لوحة المالك أي زر أو حقل أو طلب UI لتغيير حالة الطلب. |
| O-07 | **نجح.** عرضت الواجهة حالة «الطلب غير موجود» لمعرف غير موجود. |

## 6. نتائج التجربة وإتاحة الاستخدام — U-01 إلى U-04

| السيناريوهات | النتيجة |
|---|---|
| U-01 | **نجح.** تحققت اللقطات المرئية على عرض `390px` من درج جانبي RTL متجاوب، مع واجهات بطاقات One UI واضحة. |
| U-02 | **نجح.** أمكن وضع التركيز بلوحة المفاتيح على زر تطبيق المرشحات، مع تسمية أزرار وحقول عربية. |
| U-03 | **نجح.** ظهرت حالات الخطأ والفراغ وإعادة المحاولة بدلاً من شاشة فارغة أو بيانات قديمة مضللة. |
| U-04 | **نجح.** بقي عنصر «قيد المعالجة» محدداً عبر `aria-current="page"` عند مسار الحالة، وظل قسم الطلبات مفتوحاً في القائمة. |

سُجلت نتائج التحقق المرئي التفصيلية في `PHASE8B_VISUAL_VERIFICATION.md`. وتظهر لقطتا قبول المتصفح درج التاجر المتجاوب وبطاقات الإشراف العالمية للمالك من دون أدوات تغيير حالة في سطح المالك.

## 8. حدود ما بقي مؤجلاً

لم تنفذ المرحلة 8B أي إنشاء طلبات أو ربط Customer بواجهة تشغيلية، ولا Customer Account أو Address، ولا عربة أو Checkout أو دفع أو شركة توصيل أو خصم/حجز مخزون، ولا خطط أو اشتراكات أو Feature Gating. صفحات التاجر **التسليم** و**التسويات** و**التقارير** بقيت placeholders، كما بقيت صفحات المالك المالية والتنفيذية الأخرى خارج النطاق.

## 9. قرار التسليم

أُنجزت الواجهات وفق سيناريوهات القبول المعتمدة، واجتاز تشغيل المتصفح واختبارات الانحدار. التقرير الحالي يقدم النتائج قبل طلب الموافقة النهائية على المرحلة الثامنة بالكامل، كما طُلب. لا يُبدأ أي نطاق لاحق — Storefront/Customer أو الصفحة التسويقية والاشتراكات — قبل توجيه مستقل وموافقة صريحة جديدة.
