# معاينة المرحلة 14 — الموظفون والصلاحيات الدقيقة والتنقل المركزي

> **الحالة:** تخطيط فقط. لا يوجد تنفيذ، ولا migration، ولا فرع، ولا تغيير وظيفي للمرحلة 14.

## الهدف وقيمة الأعمال

تهدف المرحلة 14 إلى تمكين التاجر من تشغيل متجره بفريق عمل دون منح كل موظف صلاحيات التاجر الكاملة. تقدم هوية مستقلة للموظف، عضوية مقيدة بمتجر، وصلاحيات قابلة للمراجعة على مستوى endpoint والواجهة. كما توحد التنقل في لوحات المالك والتاجر والموظف عبر مصدر تكوين مركزي بدلاً من قوائم hardcoded. [1]

## الوظائف القائمة ذات الصلة

| المجال | ما هو موجود اليوم | أثره على المرحلة 14 |
|---|---|---|
| جلسات التاجر | جلسة واحدة مقيدة بمتجر واحد | نموذج مرجعي لفصل جلسة الموظف عن التاجر |
| عزل المتجر | `requireMerchantStore` والتحقق الخادمي | يجب أن يبقى مصدر عزل المتجر، لا يستبدل بدور واجهة |
| لوحة التاجر | Store Switcher وسياق متجر نشط | الموظف لا يملك Switcher عاماً؛ سياقه يأتي من العضوية المصرح بها |
| API الحالية | endpoints حساسة للتاجر عبر مراحل 5–13 | تحتاج retrofit permission موثق قبل إعلان المرحلة مكتملة |

## النطاق المقترح

يشمل التنفيذ المستقبلي هوية `staff` مستقلة وجلساتها، جدول عضويات يربط الموظف بالمتجر والدور، قائمة permissions أولية وأدواراً حزمية مثل Store Manager وStore Staff، ثم resolver خادمي موحد يفحص الصلاحية لكل endpoint حساس. ستضيف الواجهة إدارة فريق التاجر ودخول موظف مستقل وNavigation Configuration مركزية تقود القوائم والمسارات الظاهرة. [1]

## متطلبات الأمن والبيانات

ستحتاج المرحلة migrations **additive-first** لجداول هوية الموظف وجلساته وعضوياته وربما جداول الأدوار والصلاحيات. يجب أن تكون كل عضوية مقيدة بـ`store_id`، وأن تفرض القاعدة التفرد وقيود المرجعية. لا تكفي إخفاء عناصر التنقل؛ يجب أن يعيد endpoint غير المصرح به `403` من الخادم. يجب كذلك اختبار IDOR بين موظفين لمتجرين مختلفين، وبين موظف وتاجر، وإبطال وصول الموظف فور تعطيل عضويته أو جلسته.

## API وواجهة المستخدم المتوقعة

| الطبقة | نطاق مقترح |
|---|---|
| API | إنشاء/دعوة موظف، قائمة الأعضاء، تعيين دور، تعديل permissions ضمن عضوية، تعطيل عضوية، دخول/خروج موظف |
| الواجهة | صفحة الفريق، نموذج إضافة موظف، اختيار الدور، عرض/تعديل الصلاحيات، حالة معطل، دخول موظف مستقل |
| Navigation | تعريف مركزي للعناصر: المسار، icon، permission، الحالة implemented/placeholder؛ يولد sidebars من مصدر واحد |

## الاختبارات ومعايير القبول

يلزم اختبار إيجابي وسلبي لكل permission على API، ومصفوفة عزل لمتجرين، واختبار أن عنصر بلا permission لا يظهر وأن مساره يعيد `403` إن طلب مباشرة. يجب أن يثبت القبول الحي: تاجر ينشئ موظفاً، الموظف يدخل، يرى عناصره المصرحة، وينجح فقط في العمليات المسموحة. يمر الانحدار الكامل لمراحل 1–13 قبل طلب الدمج.

## خارج النطاق

لا تشمل المرحلة خطط الاشتراك أو billing أو حد الموظفين بحسب الخطة (المرحلة 16)، ولا 2FA أو OTP/SMS أو دعوات بريد مزود خارجي، ولا نطاقات أو تخصيص storefront أو دفع أو شحن. لا يبدأ أي Retrofit شامل غير موثق لنقاط API خارج قائمة الصلاحيات المعتمدة.

## قرارات مطلوبة من المالك قبل البدء

1. اعتماد ADR لنموذج هوية `staff` مستقلة عن `merchant` و`customer`.
2. اعتماد قائمة الصلاحيات الأولية.
3. اعتماد تعريف الدورين الحزميين Store Manager وStore Staff وما يسمح به كل منهما.
4. اعتماد طريقة الإنشاء الأولية: إنشاء مباشر بكلمة مرور مؤقتة أم دعوة مؤجلة عبر مزود بريد في المرحلة 15.
