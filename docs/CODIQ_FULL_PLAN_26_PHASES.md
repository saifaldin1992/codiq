# القسم الأول — المراحل المنجزة (1 → 9) ✅

مثبتة بتقارير وبوابات اختبار معتمدة. تُذكر هنا لأن كل مرحلة قادمة تُختبر ضدها انحدارًا.

### المرحلة 1 — أساس الهوية والعزل ✅
جداول هوية وجلسات منفصلة لكل نوع (platform_owners / merchants / customers)، بريد المالك محجوز ضد التجار بـTriggers مع advisory locks، عميل محلي لكل متجر UNIQUE(store_id, email/phone)، جلسات بـtoken_hash + revoked_at + expires_at، أسعار توصيل 18 محافظة، COD مقفل بقيد CHECK.
**المثبت:** العزل في القاعدة نفسها لا في الـAPI فقط.

### المرحلة 2 — هيكل لوحة المالك ✅
لوحة مالك المنصة (One UI هادئ، RTL، **Rubik** للعربية و**Inter** للاتينية) بأقسامها.
*(الخط قرار مسجَّل في `DECISIONS_LEDGER.md` — ق-25؛ يُثبَّت رسمياً في المرحلة 21. النص التاريخي كان يذكر IBM Plex Sans Arabic.)*

### المرحلة 3 — هيكل لوحة التاجر ✅
لوحة التاجر بسياق متجر واحد، نفس لغة التصميم بمعلومات وصلاحيات مختلفة.

### المرحلة 4 — بوابة الفصل الكامل ✅ (مع إعادة اختبار)
اكتُشف تعارض مسار توجيه التاجر → أُصلح بنطاق ضيق → أعيدت البوابة كاملة ونجحت.
**المثبت:** الانضباط المنهجي: توقف، وثّق، انتظر القرار، أصلح، أعد الاختبار كله.

### المرحلة 5 — عزل التجار ببيانات حية ✅
منتجات وطلبات فعلية لتاجرين متنافسين، 403 لتبديل slug، 404 لحقن معرفات، Triggers ضد SQL المباشر.

### المرحلة 6 — الإضافة اليدوية (تاجر/زبون) ✅
provisioning يدوي من لوحة المالك بمعاملات ذرية، اعتماد عشوائي غير مكشوف للزبون، الانتقال إلى كوكي HttpOnly، فحص قوة كلمة المرور على الخادم (12+).

### المرحلة 7 — إدارة المنتجات الحقيقية ✅
منتجات/تصنيفات/مخزون/صور عبر S3-compatible (R2 الآن)، فحص magic bytes، Triggers ضد ربط عابر للمتاجر، is_low_stock مولد.

### المرحلة 8 (8A + 8B) — دورة حياة الطلبات ✅
آلة حالات محكمة (لا رجوع لـnew، completed→returned مسموح)، expectedVersion مع 409، سجل order_status_events append-only محمي بـTrigger حتى ضد SQL المباشر، واجهات إدارة الطلبات للتاجر والمالك مع تحقق بصري (جوال + سطح مكتب) وإتاحة استخدام.

### المرحلة 9 (9A) — خلفية Storefront ✅
سلات (ضيف بtoken مُبصم + زبون)، حجوزات مخزون عند checkout، معاملة Serializable، idempotency key، rate limits، CSRF Origin، دخول زبون بالهاتف، تسوية الحجوزات ضمن انتقالات الحالة (تحرير عند إلغاء/رفض، استهلاك عند completed، pending_inspection عند الإرجاع). قاعدة الإنتاج على Neon بسبع هجرات ناجحة.
**فجوات موثقة تُغلق في المرحلة 10:** اختبارات Skipped (انظر أدناه).

# القسم الثاني — إكمال البناء (المراحل 10 → 17) ✅ مكتمل

**كل مراحل هذا القسم مدموجة في `main`** وبوابة نهايته محققة كودياً واختبارياً. النطاقات أدناه تُبقى كما هي لأنها المرجع الانحداري لكل مرحلة تالية.

### المرحلة 10 — تصلب 9A وتنظيف الإرث ✅
**الهدف:** إغلاق كل الفجوات الموثقة قبل بناء أي واجهة جديدة، وتنظيف بقايا الجيل القديم.
**النطاق:**
1. الاختبارات المتخطاة في 9A: (أ) سباق overselling بين سلتين متنافستين على آخر قطعة — واحدة تنجح والثانية تُرفض بوضوح؛ (ب) guest checkout مباشر بلا حساب؛ (ج) idempotency key مكرر بـpayload مختلف → 409/422 لا إعادة الطلب نفسه؛ (د) IDOR على عناوين الزبائن؛ (هـ) قائمة/تفاصيل طلبات الزبون مع عزلها.
2. حارس TRUNCATE: كل سكربت اختبار يرفض التشغيل ما لم يحتوِ اسم القاعدة على test أو phase أو development.
3. تنظيف package.json: إزالة drizzle-orm وdrizzle-kit وmysql2 وvite-plugin-manus-runtime وأي تبعية للقالب القديم، وإصلاح تحذير حقل pnpm المهمل.
4. حسم ملف الخادم: التأكد أن مسار الإنتاج لا يمر بقالب Manus (tRPC/oauth/storageProxy)، الخادم يفشل بوضوح إذا انشغل PORT (لا findAvailablePort صامت)، حد JSON ≤ 1mb.
5. إزالة سكربتات publish_phaseX.js من الاستخدام (تبقى في التاريخ فقط).
6. توثيق قرار نافذة completed→returned كقرار مؤجل صريح في docs/adr/.
**خارج النطاق:** أي ميزة جديدة، أي migration جديدة (باستثناء ما قد يتطلبه إصلاح فجوة اختبار إن وُجد — بموافقة مسبقة).
**بوابة القبول:** كل اختبارات 1→9A + الاختبارات الخمسة الجديدة خضراء؛ pnpm install نظيف بلا تحذيرات؛ تشغيل الخادم محليًا يخدم الـAPI بلا ملفات القالب.
**قرارك:** إجازة قائمة الحذف من package.json قبل التنفيذ.
**تقدير:** 3–5 أيام عمل.

### المرحلة 11 — CI/CD وStaging ✅
**الهدف:** كل تغيير بعد هذه المرحلة يمر عبر أنبوب آلي — تنفيذ شرطك الأصلي أخيرًا.
**النطاق:**
1. GitHub Actions workflow على كل PR: lint → typecheck → build → كل اختبارات المراحل (قاعدة PostgreSQL مؤقتة داخل الـCI).
2. فرع Neon باسم staging (من الفروع التسعة المتاحة) + نشر تلقائي للتطبيق إلى بيئة staging عند الدمج في main.
3. الإنتاج: ترقية يدوية بموافقتك فقط (workflow يدوي التفعيل).
4. حماية main في GitHub: منع الدفع المباشر، إلزام PR + نجاح الفحوصات.
5. الأسرار كـGitHub Secrets (رابط staging فقط في CI؛ أسرار الإنتاج في بيئة النشر اليدوي).
6. توثيق: docs/DEPLOYMENT.md — من commit إلى إنتاج خطوة خطوة.
**بوابة القبول:** PR تجريبي يمر بالأنبوب كاملًا ويُنشر على staging آليًا؛ محاولة دفع مباشر إلى main تُرفض.
**قرارك:** اختيار مزود استضافة التطبيق لبيئتي staging/الإنتاج (سأقدم لك مقارنة قصيرة عندها — المعيار: قابلية النقل والتكلفة).
**تقدير:** 3–4 أيام.

### المرحلة 12 — واجهة Storefront وحساب الزبون (9B) ✅
**الهدف:** المتجر العام الذي يراه الزبون — أول واجهة تدرّ قيمة تجارية مباشرة.
**النطاق:**
1. كتالوج عام تحت /store/{slug}: شبكة منتجات، صفحة منتج، تصنيفات، بحث، حالات نفاد المخزون.
2. سلة (ضيف + زبون) متزامنة مع خلفية 9A، مؤشرات الحجز والتوفر.
3. تدفق checkout بـCOD: عنوان + محافظة (أسعار التوصيل من جداول المرحلة 1) + تأكيد + صفحة نجاح برقم الطلب.
4. حساب الزبون: دخول بالهاتف، طلباتي، تتبع حالة الطلب، عناويني.
5. تصميم بمتغيرات CSS قابلة للحقن (تمهيد theme لكل متجر لاحقًا)، RTL، جوال أولًا 390px، حالات Loading/Empty/Error لكل شاشة.
6. سيناريوهات قبول متصفح على نمط 8B: تدفق شراء كامل ضيفًا وزبونًا، عزل بين متجرين، جوال وسطح مكتب.
**خارج النطاق:** الدفع الإلكتروني، تخصيص مظهر المتجر من لوحة التاجر، SEO المتقدم (مرحلة 22).
**بوابة القبول:** كل سيناريوهات القبول المعتمدة منك تمر متصفحًا حيًا + الانحدار الكامل.
**قرارك:** إجازة قائمة سيناريوهات القبول قبل التنفيذ (سيقدمها Claude Code كوثيقة أولًا).
**تقدير:** 7–10 أيام.

### المرحلة 13 — Store Switcher وإنشاء المتاجر ✅
**الهدف:** تعدد المتاجر الفعلي للتاجر الواحد دون كسر قيد "جلسة = متجر واحد".
**النطاق:**
1. endpoint اختيار سياق: يستقبل جلسة تاجر صالحة + slug متجر يملكه → يصدر جلسة جديدة مقيدة بالمتجر المختار (الجلسة القديمة تبقى صالحة لسياقها).
2. واجهة Switcher في لوحة التاجر: قائمة متاجره، تبديل بنقرة، مؤشر واضح للمتجر النشط.
3. إنشاء متجر جديد من لوحة التاجر: نموذج (اسم، slug بـregex صارم `^[a-z0-9](?:[a-z0-9-]{1,48}[a-z0-9])?$`، فحص التفرد) → createStoreFoundation.
4. حد أقصى مؤقت للمتاجر لكل تاجر (ثابت في الإعدادات) — يُستبدل بحدود الخطط في المرحلة 16.
**بوابة القبول:** اختبار API: جلسة متجر A مرفوضة على متجر B حتى لنفس التاجر (403)؛ التبديل يصدر جلسة جديدة؛ slug غير صالح يُرفض على الخادم؛ متصفح حي للتدفق.
**قرارك:** الحد المؤقت لعدد المتاجر (اقتراحي: 3).
**تقدير:** 4–5 أيام.

### المرحلة 14 — Staff والصلاحيات الدقيقة + Navigation المركزية ✅
**الهدف:** فريق التاجر بصلاحيات granular، وهي أكبر إضافة معمارية متبقية.
**النطاق:**
1. جدول هوية staff مستقل بجلساته (اتساقًا مع فلسفة الفصل — ADR جديد)، عضويات: staff_memberships(staff_id, store_id, role).
2. نظام صلاحيات: permissions (مثل products.view/create/update/delete، orders.view/update، customers.view، settings.manage) + أدوار حزمية (Store Manager، Store Staff) + إمكانية تخصيص per-membership.
3. resolver على الخادم: كل endpoint حساس يمر بفحص permission — يشمل endpoints المراحل السابقة (retrofit موثق).
4. واجهة إدارة الفريق في لوحة التاجر: دعوة/إنشاء موظف، تعيين دور، تعطيل.
5. Navigation Configuration مركزية: ملف تكوين واحد يربط عناصر القوائم بالمسارات والصلاحيات — Sidebar المالك والتاجر (والموظف) تُبنى منه، لا hardcoded.
6. دخول الموظف: مسار مستقل، جلسة مقيدة بمتجر العضوية.
**بوابة القبول:** مصفوفة اختبار: كل permission يُختبر إيجابًا (الدور المخول ينجح) وسلبًا (غير المخول 403) على مستوى API؛ عنصر قائمة بلا صلاحية لا يظهر ولا يعمل مساره؛ الانحدار الكامل.
**قراراتك:** إجازة ADR نموذج staff المستقل + قائمة الصلاحيات الأولية + تعريف الدورين الحزميين.
**تقدير:** 8–12 يومًا (أثقل مراحل هذا القسم).

### المرحلة 15 — الإشعارات عبر Outbox ✅
**الهدف:** إشعار التاجر والزبون بالأحداث دون أي طابور مملوك لمزود.
**النطاق:**
1. جدول notification_outbox: يُكتب الحدث (order.created، order.status_changed، low_stock) في نفس معاملة العملية الأصلية.
2. عامل معالجة (worker) منفصل: يقرأ غير المعالج، يرسل، يعلّم بالنتيجة، إعادة محاولة بتراجع أسّي، dead-letter بعد N محاولات.
3. طبقة Provider abstraction: واجهة واحدة sendSms/sendEmail — أول مزود فعلي واحد فقط (SMS عراقي أو بريد) والباقي stubs.
4. تفعيل notification_settings المقفلة منذ المرحلة 1: التاجر يختار ما يصله.
5. سجل إشعارات في لوحة التاجر (آخر ما أُرسل وحالته).
**بوابة القبول:** حدث طلب جديد يولد صف outbox في نفس المعاملة (اختبار rollback: فشل الطلب = لا صف)؛ worker يعالج ويعيد المحاولة على فشل مصطنع؛ الانحدار الكامل.
**قرارك:** اختيار مزود SMS/بريد الأول (سأجهز مقارنة بمزودات تدعم العراق عندها).
**تقدير:** 5–7 أيام.

### المرحلة 16 — الخطط والاشتراكات وFeature Gating ✅
**الهدف:** أساس نموذج الربح: حدود لكل خطة تُفرض على الخادم.
**النطاق:**
1. الجداول: plans → plan_features (حدود: متاجر، منتجات، طلبات شهرية، موظفون، مساحة صور) → merchant_subscriptions (خطة، بداية، نهاية، حالة).
2. entitlement resolver: خدمة واحدة تُسأل عند كل أمر كتابة محدود — تجاوز الحد = 403 برمز PLAN_LIMIT_EXCEEDED ورسالة عربية واضحة.
3. لوحة المالك: إدارة الخطط، إسناد/ترقية اشتراك تاجر يدويًا (الدفع الفعلي مرحلة 25).
4. لوحة التاجر: عرض خطته واستهلاكه من كل حد.
5. استبدال الحد المؤقت للمتاجر (مرحلة 13) بحدود الخطة.
6. خطة افتراضية Free بحدود دنيا تُسند تلقائيًا لكل تاجر موجود وجديد (migration backfill).
**بوابة القبول:** اختبارات لكل حد: عند الحد الأقصى الأمر يُرفض من الخادم حتى بطلب API مباشر متجاوزًا الواجهة؛ الترقية ترفع الحد فورًا؛ الانحدار الكامل.
**قراراتك:** تعريف الخطط الأولية (أسماء، حدود، أسعار استرشادية).
**تقدير:** 6–8 أيام.

### المرحلة 17 — التسويات والعمولات + النطاقات ✅
**الهدف:** الحساب المالي بين المنصة والتاجر، ووصول المتاجر بنطاقاتها.
**النطاق:**
1. سجل مالي append-only بنمط order_status_events: قيد لكل طلب completed (مبلغ، توصيل، عمولة منصة بنسبة الخطة)، وقيد عكسي عند returned — محمي بـTrigger ضد التعديل.
2. **حسم قرار نافذة الإرجاع هنا:** completed→returned يقيد ماليًا داخل نافذة X يومًا؛ بعدها يتطلب مسار تسوية يدوية من المالك.
3. تقارير: للتاجر (مستحقاته بالفترة)، للمالك (عمولات، إجمالي المنصة) — استعلامات مفهرسة لا حسابات في الواجهة.
4. دورة تسوية: المالك يعلّم فترة "مسوّاة" (دفع يدوي خارج المنصة حاليًا) — سجل التسويات append-only أيضًا.
5. النطاقات: تفعيل default_subdomain (حل Host→store على مستوى الخادم) + custom_domain للتاجر (توثيق DNS + TLS عبر مزود الاستضافة/Cloudflare).
6. الموقع التعريفي العام للمنصة + تسجيل التاجر الذاتي (بموافقة المالك قبل التفعيل) — يستخدم regex الـslug من مرحلة 13 وحدود Free من مرحلة 16.
**بوابة القبول:** قيود مالية صحيحة رياضيًا في اختبارات سيناريو (إكمال، إرجاع داخل/خارج النافذة)؛ محاولة UPDATE على السجل المالي تُرفض من القاعدة؛ نطاق فرعي يحل للمتجر الصحيح؛ تسجيل ذاتي كامل حتى أول منتج؛ الانحدار الكامل.
**قراراتك:** نافذة الإرجاع (اقتراحي 15 يومًا) + نسب العمولة لكل خطة + سياسة الموافقة على التسجيل الذاتي.
**تقدير:** 8–10 أيام.

**🏁 بوابة نهاية القسم الثاني:** تدفق كامل end-to-end على staging: تسجيل تاجر ذاتيًا → إنشاء متجر → إضافة منتج بصورة → زبون يشتري من Storefront → إشعار للتاجر → دورة حالة حتى completed → قيد مالي → ظهور في تقرير التسوية. **هذه لحظة "المنصة تعمل تجاريًا".**

### المرحلة 18 — التدقيق الشامل وسجل الدين التقني ✅
**الهدف:** خريطة صادقة كاملة قبل أي تحسين — بوابة إلزامية لكل ما بعدها.
**النطاق:** فحص كل الطبقات (Frontend/Backend/DB/API/Auth/RBAC/Tenancy/Storage/Jobs/Config/Infra) وإخراج تقريرين: ARCHITECTURE AUDIT REPORT (قوة/ضعف/coupling/تكرار/مخاطر توسع وأمان وأداء) + TECHNICAL DEBT REGISTER (لكل بند: وصف، شدة، أثر، حل مقترح، أولوية، تعقيد). كتابة MASTER ARCHITECTURE الرجعية وADRs المتراكمة إن لم تكتمل قبلها.
**قاعدة صارمة:** لا refactoring كبير في هذه المرحلة — فحص وتوثيق فقط.
**بوابة القبول:** اعتمادك للتقريرين وترتيب أولويات السجل.
**تقدير:** 4–6 أيام.

### المرحلة 19 — الأمان ودورة حياة الحسابات (موسَّعة بقرارات المالك)

**الحالة:** 📅 المرحلة التالية للتنفيذ. اتسع نطاقها بأربعة قرارات بعد كتابة الخطة الأصلية؛ هذا هو نطاقها الكامل المحدَّث.

**19-أ — دورة حياة الحساب (يحسم D-12 وD-35 وD-62/63/65):**
1. إعادة تعيين كلمة المرور برمز موقوت أحادي الاستعمال + تغيير كلمة السر من داخل الحساب.
2. توثيق البريد والهاتف؛ **OTP لدخول الزبون** عبر البريد/واتساب (توسيع D-12 المعلن).
3. `POST /auth/*/logout` لكل الهويات + إدارة أجهزة الجلسات + إبطال الجلسة السابقة عند `login`/`switch`.
4. **تغيير بريد آمن لحساب المالك (ق-48):** تأكيد مزدوج من العنوان القديم والجديد + إبطال كل الجلسات + إشعار أمني للعنوانين. **التحديث المباشر للبريد ممنوع صراحة — تلك ثغرة استيلاء على الحساب.**
5. **2FA مفعّل فعلياً لحساب المالك (ق-48)** بالهاتف عاملاً ثانياً — لا «بنية جاهزة للتفعيل لاحقاً».
6. حقل **هاتف تواصل** منفصل في ملف المالك (بيانات صرفة).
7. كوكي لكل هوية أو إبطال القديمة + `__Host-` (D-63)؛ حد أدنى 32 بايت لسر الجلسة ودعم مفتاحين أثناء التدوير (D-62)؛ مقارنة hash وهمية دائماً لمنع الـenumeration الزمني (D-65).

**19-ب — طاقم المنصة (ق-45):** مرآة آلية المرحلة 14 على مستوى المنصة: رموز صلاحية منصة (`registrations.approve`, `finance.view`, `finance.settle`, `plans.manage`, `orders.oversee`…) + أدوار حزمية (مشرف تسجيلات / محاسب / مشرف عام) + تجاوزات لكل عضو + فحص عضوية حي وإبطال فوري + **سجل تدقيق لأفعال طاقم المنصة**. **حد صارم غير قابل للتفويض:** نسب العمولة، حذف/أرشفة الخطط، وإدارة طاقم المنصة نفسه — للمالك وحدها.
*يُنفَّذ مع 19 لأن retrofit دورة حياة الحساب يمسّ الأسطح نفسها.*

**19-ج — بنية التحقق zod (ق-49، يحسم D-14):** schema لكل endpoint + mapper موحد إلى `422` بأكواد قابلة للترجمة. **شرط مسبق لمرحلتين:** payloads الدفع في 25أ، وi18n في 22 (الرسائل الخليطة عربي/إنجليزي لا تُترجم).

**19-د — الهجوم والدفاع:** إعادة اختبار العزل على النظام المكتمل (يشمل الجديد: التحليلات، تصدير CSV، jobs، ملفات R2 — روابط موقعة لا عامة، وملفات الوصفات الخاصة)؛ OWASP Top 10 + ASVS كسيناريوهات هجوم فعلية (XSS في مدخلات المنتجات، path traversal في الصور، brute force، session fixation)؛ **helmet وCSP كاملة (D-34 — المنفَّذ اليوم ثلاثة رؤوس يدوية فقط: nosniff وframe-deny وreferrer-policy، بلا CSP ولا HSTS)** مع السماح بالنطاقات الثلاثة للبكسلات **لصفحات المتجر فقط**؛ فحص أسرار بالتاريخ الكامل (gitleaks)؛ مراجعة CORS وrate limits على النظام كله؛ تشفير `NotificationSettings.apiKey` at-rest (D-40).

**بوابة القبول:**
1. تقرير هجوم/دفاع لكل بند: السيناريو، النتيجة قبل، الإصلاح، النتيجة بعد. **لا Critical مفتوح.**
2. مصفوفة صلاحيات طاقم المنصة مختبرة إيجاباً وسلباً على مستوى الـAPI، والبنود الثلاثة غير القابلة للتفويض تُرفض حتى لأعلى دور.
3. تغيير بريد المالك يفشل بلا تأكيد العنوانين، وينجح بإبطال كل الجلسات فعلياً.
4. الدخول بحساب المالك بلا العامل الثاني يُرفض.
5. الانحدار الكامل 1→20B.

**اعتماديته الحاجبة:** لا شيء — **جاهزة للبدء الآن**. (D-13 تفكيك طبقة HTTP كان شرطها المسبق وقد أُنجز في PR #17.)
**يفتح بدوره:** شطر البريد من مركز النطاقات والبريد (ق-46) يبدأ **بعدها مباشرة** لأنه يعتمد تشفير 19-د at-rest.
**قرارات مطلوبة منك قبل البدء:** (أ) قائمة رموز صلاحيات المنصة والأدوار الحزمية الثلاثة (كما فعلتِ في المرحلة 14)؛ (ب) هل OTP الزبون عبر البريد أم واتساب أولاً (واتساب يعتمد 25ب)؛ (ج) هل 2FA إلزامي لطاقم المنصة أيضاً أم لحساب المالك وحده.
**تقدير:** 12–16 يوماً (رُفع من 7–10 بعد إضافة طاقم المنصة وzod ودورة الحساب الموسعة).

### المرحلة 21 — البنية الأمامية وDesign System الكامل

**الحالة:** 📅 لم تبدأ. تحمل **خمسة قرارات للمالك** كانت مكتوبة ككتل مُلحقة متتابعة، وأُعيد تنظيمها هنا في نطاق واحد قابل للتنفيذ. هي أثقل مرحلة واجهات في الخطة كلها لأن كل قرار بصري في المشروع ينتهي إليها.

**21-أ — الأساس البنيوي:** ترحيل تدريجي إلى `features/` modules مع فصل Use Cases عن الصفحات (ملفاً ملفاً بلا big-bang، حسب أولويات سجل الدين)؛ **Design Tokens مركزية كاملة** (ألوان/خط/مسافات/زوايا/ظلال/حركة/breakpoints) — صفر hex داخل المكونات (D-21: ~1,095 لوناً صلباً اليوم + نظاما ثيم لا يتخاطبان، يُوحَّد مصدر الثيم)؛ مكتبة المكونات الكاملة (Button, Input, Select, Table, Modal, Drawer, Tabs, Badge, Toast, Tooltip, Pagination, Skeleton, Empty/Error/Loading)؛ توحيد طبقة جلب البيانات في `lib/api-client.ts` واحد (D-52: ست نسخ من `api<T>` و12 موضع fetch خام اليوم).

**21-ب — الطباعة والهوية (ق-25، ق-23، ق-24):** تثبيت **Rubik للعربية وInter للاتينية** كخط المنصة في كل الواجهات الأربع، معلَنتين مرة واحدة في `--font-sans` — **لا يسمّي أي مكوّن عائلة خط مجدداً**. وتعميم **اللغة البصرية «الصافية»** (ق-23): بلا رسومات توضيحية أو زخارف مصوّرة إطلاقاً · Vector/SVG حصراً لكل رسوميات الواجهة والشعارات والأيقونات، ممنوع أي أصل نقطي قابل للبكسلة · النقطي لمحتوى المستخدم فقط (صور المنتجات) بأحجام متعددة محسّنة · والشعار النصي **CODIQ** بأحرف كبيرة (ق-24، منفَّذ).

**21-ج — المود النهاري والليلي (ق-27):** لوحة ألوان ليلية كاملة للوحات الثلاث والـStorefront، معرّفة **حصراً عبر Design Tokens** (تستحيل قبل إزالة الـhex في 21-أ)، بمفتاح تبديل محفوظ للمستخدم واحترام `prefers-color-scheme`.

**21-د — `store_theme` وتخصيص التاجر ضمن حدود (ق-30):** جدول `store_theme` (لون أساسي، شعار، غلاف) + واجهة «مظهر متجري» للتاجر، **داخل إطار Tokens لا يستطيع التاجر كسره**؛ و**عمق التخصيص استحقاق خطة** عبر نظام الاستحقاقات القائم من المرحلة 16: مجانية = لون أساسي + شعار · نمو = + غلاف وألوان كاملة · احتراف = + قوالب وخيارات متقدمة. المالك يتحكم بهذه الحدود من لوحته كإعداد لا ككود (ق-08).

**21-هـ — الوصولية والتجاوب (ق-28):** إزالة `maximum-scale=1` المانع للتكبير وإدارة تركيز في الـdrawers واستبدال `window.confirm` وتفعيل الـToast المركّب بلا استدعاء (D-53)؛ ومعيار قبول متجاوب صريح: **كل شاشة تُختبر بصرياً على 390px و768px و1440px بلا تجاوز أفقي** (D-54: معظم شاشات الإدارة غير متحقق منها على 390px اليوم).

**بوابة القبول:**
1. **المعيار الحرفي الحاكم:** بناء **theme بديل كامل** للـStorefront بتغيير tokens فقط دون لمس أي Business Logic — يُثبت عملياً. *(هذا المعيار هو أيضاً شرط انطلاق 21B.)*
2. صفر قيمة لون خام في أي مكوّن (فحص آلي في الـCI).
3. المود الليلي يعمل على كل شاشة في اللوحات الثلاث والـStorefront.
4. تاجر بخطة مجانية لا يستطيع تجاوز حدود التخصيص **حتى بطلب API مباشر**.
5. تمرير بصري 390/768/1440 لكل شاشة.

**اعتماديته الحاجبة:** لا شيء تقنياً — لكن تنفيذها قبل المرحلة 22 مقصود، لأن i18n فوق مكونات غير موحّدة يضاعف العمل.
**تفتح بدورها:** 21B معرض القوالب · باني الصفحات (ق-44/ق-51، المرحلة 28-A) · P27-4 محرر صفحة الهبوط (ق-80) — الثلاثة تنتظر Tokens ومكتبة المكونات.
**قرارات مطلوبة منك عند البدء:** (أ) تثبيت Rubik خط المنصة رسمياً في كل الواجهات (انظر «يحتاج توضيح» رقم 7 في سجل القرارات)؛ (ب) لوحة الألوان الليلية — هل تُشتق آلياً من النهارية أم تُصمَّم يدوياً.
**تقدير:** 10–15 يوماً (يشمل المود الليلي والتحقق المتجاوب).

### المرحلة 21B — معرض قوالب المتاجر (ق-31، نطاق معتمد 2026-08-26، يحسم D-29)
**النطاق:** فوق نظام Tokens للمرحلة 21 — كل قالب = حزمة tokens + تخطيطات جاهزة؛ معرض قوالب يختار منه التاجر **ضمن حدود خطته** (نفس محرك الاستحقاقات في 21-د)؛ يشمل **قوالب القطاعات** (منها قالب القطاع الصيدلي — ق-50) لا الأذواق فقط؛ وإمكانية قوالب مدفوعة كمصدر دخل رابع.
**معيار القبول:** تبديل التاجر بين قالبين يغيّر مظهر متجره كلياً بلا أي تغيير في بياناته أو منطقه؛ وقالب مقفل بخطة أعلى يُرفض من الخادم لا من الواجهة.
**اعتماديته الحاجبة:** **لا يبدأ قبل اكتمال 21 وإثبات معيار «theme بديل بتغيير tokens فقط»** — وإلا كل قالب يصبح شيفرة منفصلة تُصان يدوياً.
**قرار مطلوب منك عند البدء:** عدد القوالب في الإطلاق الأول، وأيها مجاني وأيها بخطة أو بشراء.

### نطاق معتمد (2026-08-26) — منتجات المنصة لمرة واحدة + باني الصفحات (ق-44) — ⏳ بعد 21

**النطاق:**
1. جدول `platform_products` (اسم، مواصفات، سعر، حالة) يُدار من لوحة المالك **بنفس فلسفة الخطط: إعدادات لا كود** (ق-08) — إضافة منتج جديد لا تتطلب نشراً.
2. الشراء = قيد في الدفتر المالي append-only + **استحقاق** يمنح الصفحة، فوق محرك الاستحقاقات القائم من المرحلة 16.
3. التحصيل **يدوي باعتماد المالك قبل 25أ**، وذاتي إلكتروني بعدها — وتُذكر هذه الحقيقة في الواجهة صراحة (ق-10).
4. **باني الصفحات** (أقسام/ألوان/نصوص/شعار) فوق Tokens ومكتبة مكونات المرحلة 21.

**قاعدة نموذج الربح:** الشراء لمرة واحدة **غير قابل للتبديل بطبيعته** — بخلاف الاشتراكات القابلة للترقية والتخفيض. لا يُبنى له مسار «تغيير المنتج».
**معيار القبول:** المالك ينشئ منتجاً ويسعّره من لوحته بلا نشر؛ شراء واحد ينتج قيداً مالياً واحداً واستحقاقاً واحداً؛ محاولة «ترقية» منتج لمرة واحدة مرفوضة من الخادم؛ والصفحة الناتجة قابلة للتحرير الكامل من لوحة المالك.
**اعتماديته الحاجبة:** **Tokens ومكتبة مكونات المرحلة 21** — باني صفحات بلا نظام تصميم يعني إعادة بنائه بعدها.
**منزله النهائي:** يلتقي هذا الباني مع P27-4 (محرر صفحة الهبوط، ق-80) وصفحات الأطباء في **محرك واحد** — المرحلة **28-A** (ق-51/ق-54). **لا يُبنى محركان.**
**قرارات مطلوبة منك عند البدء:** تسعير المنتج الأول ومواصفاته، وهل يُباع لغير مشتركي CODIQ أيضاً.

### نطاق معتمد (2026-08-26) — حزمة «تدليل الزبون» (8 ميزات بأمر المالك، تنفذ متداخلة مع 20B)
اعتمدت المالك 8 ميزات لتجربة زبون بمواصفات عالمية (وأجّلت: دليل المقاسات، كوبونات المناسبات، مستويات VIP):
1. **صفحة «أين طلبي؟» عامة** — تتبع برقم الطلب + الهاتف دون تسجيل، بخط زمني بصري؛ rate-limited. (مستقلة — CD-1)
2. **رسالة «مندوبك في الطريق»** — حدث outbox عند `out_for_delivery` (بريد الآن، واتساب مع 25ب). (CD-1)
3. **تقييمات ومراجعات بالصور** ⭐ بشارة «مشترٍ موثّق» (زبون له طلب مكتمل للمنتج) وإشراف التاجر. (CD-2)
4. **بوابة إرجاع ذاتية** — طلب إرجاع من حساب الزبون بتتبع حالته، مربوط بآلة الحالات ونافذة الإرجاع القائمة. (CD-3)
5. **قائمة الرغبات ♥ + «نبّهني عند التوفر»** للمتغير النافد — التنبيه عبر outbox بdedupe. (CD-2)
6. **«اطلبه مجدداً»** بنقرة من تاريخ الطلبات (يملأ السلة بالمتغيرات المتوفرة ويصارح بالنافد). (CD-1)
7. **«يُشترى معه عادة»** — توصيات من اقتران order_items التاريخي، store-scoped. (CD-4)
8. (رقمها الأصلي 9) **نقاط الولاء** — كسب عند الإكمال، صرف كخصم **فوق محرك كوبونات 20B-1** (بعده حكماً). (CD-5)
**التسلسل والحالة (2026-08-30):** **الحزمة مكتملة بالكامل ✅** — CD-1 ✅ (تتبع عام + رسالة المندوب + اطلبه مجدداً، PR #35)، CD-2 ✅ (مراجعات بشارة «مشترٍ موثّق» عمودُها رقم الطلب لا علم، والتاجر يخفي النص لا الدرجة + قائمة رغبات + تنبيه توفر، PR #68)، CD-3 ✅ (بوابة إرجاع ذاتية: الطلب ليس إرجاعاً، والموافقة تمر بمسار المال الوحيد، PR #69)، CD-4 ✅ (توصيات باقتران ≥3 طلبات منفصلة، PR #70)، CD-5 ✅ (نقاط الولاء: الرصيد مجموع لا عمود، والإرجاع يعكس الجهتين، PR #70). كل بند اجتُبر بطفرة مقصودة في الكود.

### نطاق معتمد (2026-08-26) — حزمة «تدليل التاجر» (12 ميزة بأمر المالك — اعتماد كامل)
اعتمدت المالك الحزمة كاملة، مقسمة دفعات بمحور الجهد والاعتمادية:
**MD-1 «راحة اليوم» (مكاسب سريعة، تُنفذ مبكراً):** البحث الشامل الواحد في اللوحة (منتج/طلب/زبون/هاتف — فوق مكوّن cmdk الموجود)؛ نسخ منتج بنقرة؛ ملاحظات داخلية ووسوم على الطلب (للتاجر وطاقمه)؛ إجراءات جماعية على الطلبات (انتقال حالة دفعة واحدة بحراسة expectedVersion لكل طلب)؛ وضع «إجازة» للمتجر (إغلاق مؤقت برسالة مخصصة في الـStorefront بدل التعطيل الكامل).
**MD-2 «الطباعة بنقرة» (يحسم D-33):** بوليصة شحن + فاتورة عربية أنيقة + قائمة تجهيز — قوالب HTML للطباعة (بلا مكتبة PDF في v1)، RTL بخط المنصة، لكل طلب ودفعات طلبات.
**MD-3 «الرسائل الذكية» (فوق Outbox والماسح الدوري):** الملخص اليومي التلقائي للتاجر (مبيعات اليوم، طلبات تنتظر — بريد الآن وواتساب مع 25ب، opt-in)؛ توقع نفاد المخزون (بمعدل البيع الأخير: «سينفد خلال ~N أيام» — ترقية لتنبيه المخزون القائم).
**MD-4 «البائع الاجتماعي»:** مشاركة المنتج بنقرة — توليد صورة أنيقة جاهزة (المنتج + السعر + رابط الطلب) للستوري/واتساب، توليداً على العميل (Canvas/SVG) بلا تبعيات خادمية.
**MD-5 «محفظتي»:** شاشة مستحقات التاجر الصافية حتى اللحظة وتسويته القادمة — قراءة فوق الدفتر المالي القائم.
**MD-6 «متجر موثّق»:** شارة توثيق يمنحها المالك (علم على المتجر + شارة في الـStorefront + معاييرها في لوحة المالك) — تفعيل حقيقي لقائمة «التحقق».
**MD-7 «شهرك في CODIQ»:** تقرير شهري أنيق (صفحة HTML للطباعة/المشاركة v1) بأرقام التاجر وإنجازاته — job شهري فوق التحليلات.
**الترتيب والحالة (2026-08-30):** **الحزمة مكتملة بالكامل ✅** — MD-1 ✅ (بحث/نسخ/ملاحظات ووسوم/إجراءات جماعية/إجازة)، MD-2 ✅ (بوليصة + فاتورة + قائمة تجهيز، تحسم D-33، وملاحظة الزبون تصل إلى الورقة)، MD-3 ✅ (ملخص يومي بتوقيت بغداد بمفتاح فريد يمنع التكرار بنيوياً + توقع نفاد المخزون يرفض التخمين)، MD-4 ✅ (صورة مشاركة 1080×1350 تُولَّد في المتصفح، مُثبَتة بقراءة الكانفس)، MD-5 ✅ (محفظتي — قراءة فوق الدفتر، والتسوية تدفع بالضبط ما أظهرته)، MD-6 ✅ (شارة توثيق يمنحها المالك، والقاعدة ترفض شارة بلا مانح)، MD-7 ✅ (تقرير شهري قابل للطباعة، بلا نسبة نمو مخترعة من صفر). كل بند اجتُبر بطفرة مقصودة في الكود للتأكد أن الاختبار يمسكها.

### نطاق معتمد (2026-08-27) — حزمة «فجوات المنصة» (9 بنود بأمر المالك — اعتماد كامل)
مراجعة تصميمية شاملة بعد اكتمال 20B كشفت فجوات لم يرصدها سجل الدين ولا المقارنات التنافسية. اعتمدت المالك التسعة كاملة، مرتبة بمحور الإلحاح:

**PG-A — الحماية والامتثال (أولوية قصوى، قبل أي إطلاق حقيقي):**

1. **إلغاء الطلب من الزبون** (PG-1، ق-68).
   **النطاق:** زر إلغاء ذاتي ما دام الطلب في حالة `new` — **عبر آلة الحالات نفسها** بحارس ملكية وسبب اختياري. يوفر مكالمات ويمنع رفض الاستلام لاحقاً.
   **معيار القبول:** الإلغاء يمر بـ`transitionOrderStatus` القائم لا بمسار موازٍ (فيُحرِّر الحجوزات ويكتب حدث الحالة تلقائياً)؛ محاولة إلغاء طلب غادر `new` تُرفض بـ409؛ محاولة إلغاء طلب زبون آخر تعيد 404 لا 403 (لا تسريب وجود)؛ لا انحدار في تسوية المخزون.
   **اعتماديته الحاجبة:** لا شيء — **أخفّ بنود الحزمة وأعلاها أثراً**، يُنفَّذ مع حزم التدليل مباشرة.

2. **الحذف الناعم وسلة المحذوفات** (PG-2، ق-70).
   **النطاق:** حذف ناعم موحد (منتجات/تصنيفات/كوبونات/موظفين) + استعادة خلال 30 يوماً + سجل تدقيق «من فعل ماذا» للتاجر. شبكة أمان **تُباع كميزة ثقة لا كتحسين تقني**.
   **معيار القبول:** المحذوف يختفي فوراً من الـStorefront ومن كل القوائم لكن **لا يُفقد أي أثر تدقيق مخزوني** (المشكلة الحقيقية في D-48: الحذف الصلب يبيد سجل الحركات بـCascade)؛ الاستعادة تعيد العنصر بحالته الكاملة؛ بعد 30 يوماً يُنقّى بـjob؛ محاولة حذف عنصر مرتبط بطلب تعيد 409 واضحة لا 500 عامة.
   **⚠️ مرجع يحتاج تصحيحاً:** النص الأصلي قال «يوسّع D-20»، لكن D-20 في سجل الدين هو *غياب code splitting* لا الحذف الناعم؛ الأرجح أن المقصود **D-48** و/أو بند soft-delete في المرحلة 20. مسجَّل في «يحتاج توضيح المالك» بسجل القرارات.
   **اعتماديته:** يتقاطع مع استراتيجية الـsoft-delete الموحدة في المرحلة 20 — **يُنفَّذ قبل المرحلة 19** كما اعتُمد، والمرحلة 20 تعمّمه على بقية الجداول.

3. **صحة المراسلة** (PG-3، ق-69).
   **النطاق:** رابط إلغاء اشتراك **إلزامي في كل رسالة تسويقية** (لا التشغيلية) + سقف يومي لكل متجر + تتبع الشكاوى.
   **لماذا هو شرط امتثال لا تحسيناً:** بدونه يُدرج نطاق المنصة كمُرسل مزعج فتضيع **كل** الرسائل — التشغيلية منها قبل التسويقية.
   **معيار القبول:** تصنيف كل نوع حدث outbox «تسويقي» أو «تشغيلي» **في القاعدة** لا في الكود؛ رسالة تسويقية بلا رابط إلغاء اشتراك **تفشل الإرسال** لا تُرسل ناقصة؛ إلغاء الاشتراك يوقف التسويقي ويبقي التشغيلي؛ تجاوز السقف اليومي يؤجل لا يُسقط.
   **اعتماديته الحاجبة:** لا شيء — بنية Outbox قائمة. يُنفَّذ مع حزم التدليل مباشرة، **وقبل أي حملة رسائل حقيقية**.

4. **السياسات القانونية** (PG-9، ق-71).
   **النطاق:** شروط استخدام · سياسة خصوصية · سياسة إرجاع · سياسة محتوى — صفحات منصة + صفحات لكل متجر (فوق CMS-lite)، وقبول صريح عند التسجيل.
   **معيار القبول:** القبول مسجَّل بتاريخه ونسخة النص التي قُبلت (لا علم boolean مجرد — لا قيمة قانونية له)؛ صفحات المنصة منشورة وقابلة للوصول بلا تسجيل؛ سياسات المتجر اختيارية **فوق** سياسات المنصة الإلزامية (تتقاطع مع P27-2 §3).
   **اعتماديته الحاجبة:** لا شيء تقنياً — لكنه **بوابة قانونية إلزامية قبل 25أ وأي بوابة دفع** (لا مجمّع دفع يقبل منصة بلا سياسات منشورة)، ويُنفَّذ **قبل المرحلة 19**.
   **قرار مطلوب منك:** من يكتب النصوص القانونية — هذا عمل قانوني بشري لا يُولَّد آلياً.

**PG-B — ثراء التجربة (مع 21/22 أو قبلهما):**

5. **صفحة منتج غنية** (PG-4، ق-72).
   **النطاق:** وصف منسق عبر **markdown آمن أو محرر مقيد** (لا HTML حر — سطح حقن)، + مواصفات كقيم مفتاح/قيمة قابلة للترتيب، + أسئلة شائعة لكل منتج.
   **معيار القبول:** محاولة حقن `<script>` أو `onerror=` في أي من الحقول الثلاثة تُعقَّم على **الخادم** لا على العميل؛ المواصفات تظهر في الـStorefront وفي تصدير CSV؛ منتج بلا حقول جديدة يعرض تماماً كما اليوم.
   **اعتماديته:** مكونات المرحلة 21 (المحرر المقيد مكوّن مكتبة، لا مكوّن شاشة واحدة — ق-06).
   **قرار مطلوب:** markdown مقيد أم محرر WYSIWYG بقائمة سماح؟

6. **ملاحظة الزبون على الطلب** (PG-5، ق-73).
   **النطاق:** حقل «ملاحظات» اختياري في checkout (≤500 حرف، تحقق خادمي) يظهر للتاجر في تفاصيل الطلب وفي الطباعة (MD-2). طلب يومي في السوق العراقي («اتصل قبل الوصول»، «هدية»).
   **معيار القبول:** الملاحظة تُحفظ داخل معاملة checkout نفسها بلا مساس ببصمة idempotency ولا بترتيب الأقفال؛ تظهر في تفاصيل الطلب وفي بوليصة MD-2؛ 501 حرفاً تُرفض من الخادم؛ لا انحدار في اختبارات 9A/20A/20B الحرفية.
   **اعتماديته الحاجبة:** لا شيء — **جاهز الآن**، وأخفّ بنود الحزمة جهداً. يظهر في الطباعة عند وصول MD-2.

7. **بحث عربي ذكي** (PG-6، ق-74) — ↗️ **أُلحق بالمرحلة 20 ولم يعد بنداً منفصلاً.** نطاقه ومعيار قبوله في وصف المرحلة 20 أعلاه.

**PG-C — النمو والتشغيل (بعد استقرار حزم التدليل):**

8. **نبض المنصة للمالك** (PG-7، ق-75).
   **النطاق:** لوحة صحة أعمال في لوحة المالك: تجار نشطون اليوم/الأسبوع · **تجار متوقفون** (لا مبيعات منذ 7 أيام — أهم رقم لأنه إنذار مغادرة مبكر) · أسرع المتاجر نمواً · معدل التحول من تسجيل إلى أول طلب.
   **معيار القبول:** كل رقم قابل للتفسير بنقرة (من هم هؤلاء التجار تحديداً)؛ الاستعلامات مجمَّعة في القاعدة فوق فهارس 20 لا في الذاكرة (درس D-16)؛ لا تُحمَّل مسارات الكتابة (درس D-17)؛ تعريف «نشط» و«متوقف» مكتوب حرفياً في الواجهة (ق-10).
   **اعتماديته:** تحليلات 20B-2 ✔️ مكتملة — **جاهز تقنياً**، مؤجل بالترتيب لا بالاعتمادية.
   **قرار مطلوب:** تعريف «التاجر النشط» — أي بيع؟ أي دخول للوحة؟ أم كلاهما؟

9. **تجربة التاجر الأولى** (PG-8، ق-76).
   **النطاق:** مسار onboarding من خمس خطوات في لوحة التاجر الجديدة (منتج أول ← صورة ← تفعيل توصيل ← طلب تجريبي ← نشر المتجر) بمؤشر تقدم مستمر.
   **معيار القبول:** حالة كل خطوة **مشتقة من البيانات الفعلية** لا من علم يدوي (خطوة «منتج أول» تكتمل لأن منتجاً وُجد فعلاً)؛ المسار قابل للتخطي ولا يحجب اللوحة؛ يظهر للتاجر الجديد فقط ويختفي نهائياً عند اكتماله؛ **الطلب التجريبي لا يدخل الدفتر المالي ولا التحليلات** — وإلا لوّث أرقام التاجر من يومه الأول.
   **اعتماديته الحاجبة:** لا شيء. يتقاطع مع PG-7 (معدل التحول يقاس على هذا المسار نفسه).
   **قرار مطلوب:** هل يُحذف الطلب التجريبي تلقائياً بعد الاكتمال أم يبقى موسوماً؟

**الترتيب:** PG-A أولاً (PG-1 وPG-3 مع حزم التدليل مباشرة؛ PG-2 وPG-9 قبل المرحلة 19)؛ PG-B مع 21/22 (وPG-6 مدمج داخل المرحلة 20)؛ PG-C بعد استقرار التدليل. تقدير الحزمة: 14–20 يوماً موزعة.

### المرحلة 22 — التجربة والعالمية (i18n + WCAG + SEO)

1. **العربية** كاملة (لغة الأساس).
2. **الإنكليزية** كاملة **بكتابة تحريرية أصيلة لا ترجمة حرفية**، تُراجع تحريرياً قبل الاعتماد.
3. **الكردية السورانية بالحرف العربي** (RTL) — الأنسب للسوق العراقية. الكرمانجية اللاتينية قابلة للإضافة لاحقاً كلغة رابعة **دون تغيير بنيوي** (شرط تصميم على بنية i18n).
**العمق المطلوب:** كامل لا واجهة زبون فقط — لوحة التاجر والإشعارات والفواتير أيضاً. هذا هو التميّز المقصود: لا يقدّمه أي منافس إقليمي، والمحليان Jamkhana وStoreIQ يقدّمان الكردية لواجهة الزبون فقط.

> **⚠️ الشطر الزمني (ق-95، قرار المالك 2026-08-27):** المرحلة 22 تُنجز **البنية وحدها بالعربية**؛ ومحتوى الإنكليزية والسورانية ينتقل إلى **المرحلة 27 (بند P27-9)**.
> **السبب:** المنصة تواصل النمو بعد 22 — المراحل 23→26 وحزم التدليل والفجوات كلها تضيف نصوصاً. ترجمةٌ تُكتب عند 22 تلاحق هدفاً متحركاً وتُعاد مرتين، ومراجعتها التحريرية البشرية تُعاد معها. أما البنية فيجب أن تسبق كل ذلك، وإلا استمرت المراحل التالية بتثبيت النصوص داخل المكونات وواجهنا استخراجاً يدوياً للمستودع كله لاحقاً.
> **الفاصل الحاسم:** ما يبقى في 22 هو **استخراج كل نص إلى كتالوج** وتوجيه اللغات واتجاه الصفحة وتنسيق التواريخ والأرقام لكل locale — بعمود لغة واحد مملوء (العربية). وما ينتقل إلى 27 هو **ملء عمودين في كتالوج قائم** على منصة مستقرة، مرة واحدة وبمراجعة تحريرية واحدة.

**بوابة القبول (المرحلة 22 — البنية):**
1. **صفر نص عربي مثبّت داخل أي مكوّن أو خدمة** — كل نص يُقرأ من الكتالوج، ويُثبَت ذلك بفحص آلي يفشل عند أي نص عربي حرفي في الكود، لا بمراجعة بشرية.
2. اتجاه الصفحة وlang من الجذر لا مكرراً في المكونات (D-22: `dir="rtl"` مكرر 43 مرة اليوم).
3. التواريخ والأرقام والعملة والمنطقة الزمنية تتبع الـlocale لا مثبتة على `ar-IQ`.
4. رسائل الأخطاء الخادمية تصل بأكواد قابلة للترجمة لا بنص عربي جاهز (يعتمد zod — ق-49، المرحلة 19).
5. Lighthouse accessibility ≥ 90 للتدفقات الحرجة؛ صفحات المنتجات تجتاز اختبار structured data.

**اعتمادياته الحاجبة:** المرحلة 21 (i18n فوق مكونات غير موحّدة يضاعف العمل) · وبنية zod من المرحلة 19 لأكواد الأخطاء القابلة للترجمة.
**قرار مطلوب منك — انتقل إلى P27-9:** من يكتب النسخة الإنكليزية التحريرية ومن يراجع الكردية السورانية. عمل تحريري بشري لا يُولَّد آلياً، ولم يعد مطلوباً عند بدء 22 بل عند بدء P27-9.
**تقدير:** 7–10 أيام — **خُفِّض من 10–15** بعد نقل محتوى اللغتين إلى P27-9؛ ما بقي هو الاستخراج والبنية بلغة واحدة.

### المرحلة 23 — الأداء والحمل
**النطاق:** Performance budgets (حجم الحزم، LCP للـStorefront)، قياس قبل/بعد لكل تحسين (lazy loading، تحسين صور بأحجام متعددة عبر R2، caching رؤوس HTTP)؛ ثم load/stress بسيناريوهات متدرجة: 100 → 1,000 → 10,000 تاجر ببيانات مولدة، وcheckout متزامن (السيناريو الأخطر: طلبات متنافسة على مخزون محدود تحت حمل)؛ تحديد نقاط الاختناق الفعلية وتوثيق أقصى حمل مختبر وأرقامه.
**بنود الدين التي تُغلق هنا:** D-20 (صفر code splitting — 13 صفحة في حزمة واحدة 842KB) · D-37 (رفع الصور بلا rate limit) · D-38 (تقديم الصور عبر ذاكرة الخادم بلا `Cache-Control` وS3Client جديد لكل عملية) · D-45 (استعلامات مزدوجة بالمسار الساخن) · B-06 (ميزانية أداء «نت ضعيف»: أول محتوى ≤ 3 ثوانٍ على 3G مخنوقة، أول تحميل ≤ 250KB مضغوطاً بدون الصور).
**بوابة القبول:** تقرير أرقام: أقصى حمل، أزمنة استجابة p50/p95/p99، نقاط الفشل، وما أُصلح. **لا ادعاء بلا قياس** (ق-10).
**تقدير:** 6–8 أيام.

### المرحلة 24 — البنية التحتية والتشغيل

**الحالة:** 📅 لم تبدأ. اتسعت ببندين للمالك، وصارت **الاعتمادية الحاجبة لأثمن بند في سجل الأفكار** (مشخّص الأعطال في P27-8).

**24-أ — الرصد والسجلات المنظمة (D-41 — البند المفتاحي):** سجلات منظمة بـ`request_id` و`store_id` و`identity_kind` (اليوم `console.error` عارٍ فقط)، error tracking، health checks، تنبيهات على 5xx وفشل النشر والهجرات — بحيث يُجاب **«أي تاجر تأثر ولماذا» بلا تخمين**.
> **لماذا هذا البند تحديداً حاجب:** **مشخّص الأعطال في P27-8 (ق-84) مستحيل بلا هذه السجلات** — مساعد يقرأ `console.error` عارياً يخمّن ولا يشخّص. وبنداً على ذلك، أي تقديم للمساعد الذكي يبدأ من هنا لا من نموذج اللغة. ويرتفع D-41 إلى **High قبل المرحلة 25أ** لأن مدفوعات بلا correlation تعني تدقيقاً مستحيلاً.

**24-ب — مركز النطاقات (ق-46، الشطر الأول):** إدارة نطاق المنصة العام — النطاق القانوني، فحص سجلات DNS حياً، حالة TLS، وحالة الـwildcard `*.domain` لنطاقات المتاجر الفرعية (بنية المرحلة 17)؛ ودليل نطاقات التجار المخصصة **بتحقق CNAME آلي وربط تلقائي** — بديل التدفق اليدوي القائم. للمالك وحدها أو أعلى صلاحية طاقم منصة (ق-45).
*(شطر البريد من ق-46 يُنفَّذ **بعد المرحلة 19 مباشرة** لا هنا، لأنه يعتمد تشفير 19-د at-rest.)*

**24-ج — النسخ والاستعادة:** التحقق من نسخ Neon + **اختبار Restore فعلي على فرع** وتوثيق RPO/RTO وسيناريوهات فشل DB/Server/Storage/Deploy.

**24-د — البنية والتشغيل:** فصل موثق كامل (App/DB/Storage/CDN/DNS/Email/Monitoring/Backups/Secrets) مع خطة نقل مزود لكل مكوّن؛ تقييم Cloudflare للـDNS/CDN/WAF أمام Storefront (بمعيار الحاجة والتكلفة)؛ استراتيجية cache مكتوبة (ماذا/TTL/إبطال) بطبقة تسمح بـRedis لاحقاً؛ **Webhook infrastructure** (توقيع، إعادة محاولة، idempotency، سجل) تمهيداً للمرحلة 25؛ تنظيف دوري للجلسات المنتهية وحجوزات السلات الميتة (D-39)؛ **صفحة حالة عامة** (D-60 — توسيع معلن)؛ إغلاق نظيف للخادم عند SIGTERM (D-70)؛ بوابة `pnpm audit` في الـCI (D-67).

**بوابة القبول:**
1. Restore مُختبر وموثق **بالدقائق**.
2. لوحة مراقبة حية تعرض صحة الخدمات؛ إطفاء مصطنع لمكوّن يطلق تنبيهاً فعلياً.
3. **سؤال «أي تاجر تأثر بالعطل الفلاني ومتى» يُجاب من السجلات وحدها** — هذا هو معيار قبول D-41 الحقيقي، لا مجرد وجود مكتبة سجلات.
4. نطاق تاجر مخصص يُربط ويُتحقق منه آلياً بلا خطوة يدوية من المالك.

**تفتح بدورها:** P27-8 مساعد الذكاء الاصطناعي (ق-84) · P27-6 شراء النطاق (ق-82، مع 25أ) · تكاملات 25 كلها (Webhooks).
**قرارات مطلوبة منك عند البدء:** مزود error tracking والسجلات، وهل تُقيَّم Cloudflare للـWAF أم يُؤجَّل بمعيار التكلفة.
**تقدير:** 10–14 يوماً (رُفع من 7–10 بعد ضمّ مركز النطاقات وصفحة الحالة).

### المرحلة 25 — التكاملات والفوترة الكاملة (مشطورة بقرار المالك 2026-08-26)
شُطرت لأن حزمة الدفع/التوصيل القياسية تختلف عن حزمة عمليات COD العراقية الخاصة؛ كل شطر ببوابته.

#### المرحلة 25أ — الدفع والتوصيل والفوترة
**النطاق:** بوابة دفع إلكتروني أولى (المتاح عراقيًا — ZainCash/قي كارد/أو مزود إقليمي) خلف Provider abstraction من مرحلة 15، بفتح قيد CHECK لوسيلة CARD المقفلة منذ المرحلة 1 (migration مدروسة)؛ شركة توصيل أولى بنفس النمط (إنشاء شحنة، تتبع، webhook حالة)؛ الفوترة الكاملة للاشتراكات فوق بنية مرحلة 16: فواتير، تجديد، فشل دفع وإمهال، ترقية/تخفيض بتناسب، إلغاء؛ كل حركة مالية للاشتراكات في سجل append-only.
**بوابة القبول:** دفع اختباري كامل (sandbox المزود) حتى `payment_status=paid`؛ webhook مزيف التوقيع يُرفض؛ دورة اشتراك كاملة (اشتراك → فشل تجديد → إمهال → تسوية) في اختبارات سيناريو.

**اعتمادياتها الحاجبة:** Webhook infrastructure من المرحلة 24 · السجلات المنظمة D-41 (**مدفوعات بلا correlation = تدقيق مستحيل**) · بنية zod للتحقق الصارم من payloads الدفع (ق-49، المرحلة 19) · **وPG-9 السياسات القانونية (ق-71) — بوابة قانونية إلزامية: لا بوابة دفع تقبل منصة بلا شروط استخدام وسياسة خصوصية وسياسة إرجاع منشورة.**

**قرارك المعلّق (ق-21 — لم يُحسم بعد):** اختيار بوابة الدفع وشركة التوصيل الأوليين.
**المرشح الأول المسجّل (ق-22): WAYL** (wayl.io، بغداد) — مجمّع مرخّص من البنك المركزي وPCI-DSS يجمع Visa/MC وزين كاش وFIB في تكامل واحد، بواجهة checkout-link واسترجاعات، ودينار ودولار. **لا اتفاق ولا حساب حتى الآن.**
- **الشرط التقني غير القابل للتفاوض قبل أي توقيع:** بيئة sandbox + توثيق API كامل. لا سطر كود قبل وجودهما.
- **سؤال التفاوض المفتوح:** هل يدعم نموذج المنصة/التاجر الفرعي (كل تاجر يُدفع له مباشرة) أم تُحصّل CODIQ ثم توزّع؟ الإجابة تغيّر تصميم الدفتر المالي والتسويات، فتُحسم **قبل** التنفيذ لا بعده.
- **توسيع معلن (D-02/D-03):** الهدف بوابتان–ثلاث وثلاثة ناقلين+ لا «واحد أول» — لكن الإطلاق يبدأ بواحد مثبت.

**تقدير:** 10–14 يوماً.

#### المرحلة 25ب — عمليات COD العراقية (حزمة «لماذا يبقى التاجر») — نطاق جديد بقرار المالك (2026-08-26)
**السبب:** بنود D-04/05/06 من سجل الدين — أوجاع COD اليومية التي لا يحلها أي منافس إقليمي كاملة، وهي أكبر نزيف مالي للتاجر العراقي (رفض استلام 20–40%).
**النطاق:**
1. **تأكيد طلبات COD قبل الشحن** (D-05): تدفق تأكيد عبر واتساب/OTP، قائمة حظر أرقام، درجة موثوقية زبون عبر المنصة — فوق Outbox (15) وWebhooks (24).
2. **تجارة واتساب** (D-06): إشعارات الحالة وتأكيد بأزرار وتتبع عبر مزود WhatsApp Cloud API ضمن تجريد المرحلة 15.
3. **مطابقة نقد COD مع الناقل** (D-04): لوحة مطابقة آلية (المتوقع تحصيله مقابل المُحوَّل فعلياً، كشف العجز) فوق الدفتر المالي append-only (17) مرتبطة بتكاملات الناقلين في 25أ.
**بوابة القبول:** تدفق تأكيد كامل مختبر (تأكيد/رفض/عدم رد)؛ مطابقة نقد بسيناريو عجز مكشوف؛ عزل بين متجرين؛ الانحدار الكامل.
**تقدير:** 12–16 يوماً.

# المرحلة 28 — منتج الصفحات والعيادات (مسار تطوير مستقل، بقرار المالك 2026-08-27)

فُصل عن المسار التجاري (1→26) لأن جمهوره ونموذج دخله مختلفان: أفراد وشركات وأطباء لا تجار تجزئة. يبدأ بعد استقرار المسار التجاري، ويشارك معه الأساس نفسه (الهوية، الجلسات، الخطط، الدفتر المالي، الإشعارات، النطاقات) دون ازدواج.

**28-A — باني الصفحات (الأساس المشترك):** محرك صفحات واحد يخدم: الصفحات التعريفية للأفراد والشركات (تُباع لمرة واحدة — ق-44، نطاقها التفصيلي في قسمها ضمن القسم الثالث)، وصفحة كل طبيب/عيادة، وصفحة تعريف كل متجر، وتحرير صفحة هبوط المنصة (P27-4 / ق-80). يُبنى فوق Design Tokens ومكتبة مكونات المرحلة 21. **محرك واحد لا أربعة — هذا هو سبب فتح المرحلة أصلاً.**

**28-B — وحدة العيادات (الحجز والمواعيد):** صفحة الطبيب + حجز دور ومواعيد بلا تضارب (يعاد استخدام محرك الحجوزات المتزامنة نفسه الذي يحمي المخزون: الموعد = وحدة قابلة للحجز)، تذكيرات عبر واتساب (25ب)، ملف مراجعة مبسط، وطاقم العيادة عبر نظام الصلاحيات (14). العيادة = صفحة + وحدة حجز مركّبة فوقها، فيبدأ الطبيب بصفحة ويرقّيها لاحقاً.

**اعتمادياتها:** 21 (نظام التصميم) · 24 (التشغيل والمراقبة) · 25أ (الدفع) · 25ب (واتساب). **لا تبدأ قبلها.**
**قرارات مطلوبة عند الوصول:** تسعير الصفحات والعيادات، وهل العيادات منتج منفصل بعلامته أم قسم داخل CODIQ.
