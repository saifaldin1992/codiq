# النشر وبيئات CODIQ

**الحالة:** محدّثة بعد تنفيذ البنية التشغيلية للمرحلة 11B. تصف المسار الحاجب لـCI، وبيئة Railway staging العاملة، وحدود الإنتاج التي لا تزال يدوية وغير معدلة ضمن هذه المرحلة.

## المسار الحالي: من التغيير إلى دمج `main`

كل تغيير وظيفي أو توثيقي يبدأ في فرع مستقل ثم يُرفع إلى Pull Request. فحص GitHub Actions المسمى **`ci / integration`** يعمل على كل PR وعلى كل push إلى `main`. ينشئ هذا الفحص PostgreSQL 16 مؤقتًا داخل GitHub Actions، يطبق هجرات Prisma، ثم يشغل الفحص الساكن والبناء واختبارات التكامل المعتمدة. لا يستخدم هذا الفحص أسرار Neon أو اتصالًا بقاعدة إنتاجية. [1]

حماية `main` تلزم Pull Request وتجعل نجاح `ci / integration` شرطًا للحماية، بما في ذلك المسؤولون. لذلك لا يملك أي طرف، بما في ذلك مالك المستودع، مسار دفع مباشر مقبول إلى `main`. قرار مراجعة الـPR ودمجه يملكه **مالك المشروع** صراحةً. [2]

| المرحلة | المسؤول | الحالة الحالية |
|---|---|---|
| إنشاء فرع وتنفيذ تغيير | المنفذ وفق نطاق مرحلة معتمد | مطبق |
| فتح PR ومراجعة النطاق | مالك المشروع | مطبق |
| فحص CI الحاجب | GitHub Actions | مطبق: `ci / integration` |
| دمج PR | مالك المشروع بعد مراجعة واضحة | مطبق كسياسة؛ لا دمج تلقائي |
| النشر إلى staging | Railway بعد نجاح مراجعة ودمج `main` | مطبق؛ الخدمة مرتبطة بـ`main` مع نشر تلقائي |
| النشر إلى الإنتاج | مالك المشروع بموافقة صريحة | يدوي فقط: أكد المالك أن زر Railway تغيّر من `Disable` إلى `Enable` بعد تنفيذ التعطيل؛ تعذر التحقق المستقل لاحقاً بسبب صفحة عطل Railway. |

## اختبارات المتصفح

وظيفة **`ci / browser acceptance`** موجودة ومرئية، لكنها غير حاجبة مؤقتًا. يرجع ذلك إلى فشل مرحلة المتصفح 6 داخل GitHub Runner رغم نجاح اختبارات المتصفح محليًا في بوابات مراحل المشروع. سُجل هذا الدين تحت B-15. لا تتحول الوظيفة إلى شرط حماية قبل تشغيلات خضراء مستقرة متكررة وقرار صريح من مالك المشروع. [1] [3]

## الأسرار والبيئات

لا يحتوي repository على ملفات `.env` أو أسرار ضمن الـworkflow. لا يقرأ CI في 11A أي GitHub Secret لـNeon أو S3. تستخدم وظيفة CI عنوان PostgreSQL محليًا خاصًا بخدمة الاختبار فقط، ويحتوي اسم قاعدة البيانات على `test` ليمر حارس قواعد الاختبار. [1]

| البيئة | موضع الأسرار | السياسة |
|---|---|---|
| CI الحالي | لا أسرار خارجية؛ قيم اختبار محلية مؤقتة فقط | ممنوع Neon والإنتاج |
| Staging | متغيرات بيئة خدمة Railway `staging` فقط | اتصال Neon staging مستقل وأسرار S3/JWT خاصة بها؛ لا تُكتب في GitHub أو الكود |
| الإنتاج | إعدادات بيئة مزود النشر فقط | لا توضع القيم في GitHub أو الكود، ولا يُنشر إلا بقرار صريح من المالك |

تتضمن أسماء الإعدادات التشغيلية الحالية، من دون قيم، `CODIQ_POSTGRES_URL` و`CODIQ_POSTGRES_URL_UNPOOLED` و`SESSION_JWT_SECRET` وإعدادات تخزين S3-compatible التي تبدأ بـ`PRODUCT_S3_`. لا تُكتب قيم هذه المتغيرات في وثائق أو commits. [4]

## أسرار ما قبل الإطلاق — تمريرة واحدة

تُنفَّذ **مرّة واحدة قبل الإطلاق**، لا خمس مرات متفرّقة: كل تدوير يُعطّل الإنتاج دقيقتين، وجمعها يجعلها تعطّلاً واحداً.

### ١. كلمة سرّ قاعدة البيانات (`neondb_owner`)

لكل فرع في Neon **نسخته المستقلّة** من الدور، فيُدوَّر كلٌّ على حدة.

| الفرع | لازم؟ | أين تُستعمل السلسلة الجديدة |
|---|---|---|
| `production` | **نعم** | Railway → بيئة `production` → خدمة `strong-amazement` |
| `staging` | **نعم** | Railway → بيئة `staging` → خدمة `CODIQ` |
| `development` · `phase14-test` | يُستحسن | لا تُستعمل في Railway؛ لهما نقاط اتصال حيّة فقط |
| `backup-before-upgrade-*` | لا | **بلا compute** — لا يُوصَل إليه أصلاً |

**الخطوات لكل بيئة:**

1. Neon → **Connection details** → اختر الفرع → **Reset password**
2. **Connection pooling مُشغّل** → انسخ → الصق في `CODIQ_POSTGRES_URL` **و** `DATABASE_URL`
3. **Connection pooling مُطفأ** → انسخ → الصق في `CODIQ_POSTGRES_URL_UNPOOLED`
4. **Deploy**، ثم تحقّق من سطر `Datasource "db": ... at "ep-..."` في السجلّ

**الفخّان اللذان أوقعا نشرتين في 2026-08-31:** حذف معرّف نقطة الاتصال كاملاً بدل `-pooler` وحده، وخلط نصفَي عنوانَين (`ep-soft-smoke` من الإنتاج مع `b1tc5e9d` من staging). **انسخ من Neon بالمفتاح، ولا تحرّر السلسلة يدوياً.**

### ٢. `SESSION_JWT_SECRET` — بند D-62 المفتوح

ولّد سرّاً جديداً بـ64 خانة hex، وضع القديم في `SESSION_JWT_SECRET_PREVIOUS`، وانشر؛ ثم احذف القديم بعد **مدّة جلسة واحدة (8 ساعات)**. تفصيله في «تدوير سرّ الجلسات» أدناه.

قرار مفتوح مرتبط به: فرض حدّ أدنى لطول السرّ. مكتوب وغير مُدمج لأنه يُفشل الإقلاع إن كان السرّ الحالي أقصر — وبعد التدوير إلى 64 خانة يصير فرضه بلا مخاطرة.

### ٣. مفاتيح `PRODUCT_S3_*`

استبدل مفاتيح التطوير بمفاتيح إنتاج مخصّصة، بأقلّ صلاحية تكفي للحاوية وحدها.

### ٣ج. فحص البيئة — قبل أن تثق بالنشر

```bash
pnpm env:check
```

**شغّله على خدمة Railway بعد كل تحرير للمتغيّرات.** الإقلاع الأخضر ليس جواباً: المنصة تقلع سليمةً بينما ميزتان منشورتان ميتتان — وهذا ما وُجد يوم 2026-09-05.

**العلّة الحيّة التي أظهرها:** `CODIQ_PUBLIC_BASE_URL` **غير مضبوط في الإنتاج**. فـ`publicUrl()` تعيد `null`، و`resetLinkFor()` تعيد `null`، واستعادة كلمة السرّ تُجيب `delivery: "unavailable"` لكل تاجر ومالك وموظّف — **منذ يوم شحنها**. الخدمة أمينة (ترفض إرسال رسالةٍ ميتة)، لكن الميزة معطَّلة ولا سطر في أي سجلّ يقولها.

والتمييز الذي يعمل هنا:

| الحكم | معناه | متى يكون خطأ |
|---|---|---|
| `ok` | المجموعة كاملة | — |
| `absent` | لا شيء منها مضبوط | في بيئةٍ منشورة فقط — التطوير يُسمح له بالنقص |
| `incomplete` | **نصفها مضبوط** | **دائماً، وفي كل بيئة** |

`incomplete` ليس قراراً قط: هو تحريرٌ لم يكتمل في لوحة، وهو بالضبط الشكل الذي **يقلع نظيفاً ويفشل عند الاستعمال**. ولذلك يُفشِل الفحصَ حتى في التطوير.

و`/ready` صار يحمل الحكم نفسه (`config`) — أحكاماً فقط، بلا أسماء متغيّرات ولا قيم ولا مضيفات، لأن المسار غير مُصادَق (القاعدة نفسها التي أرساها `mail.configured`).

**ولماذا لم يمسك هذا شيءٌ من قبل؟** لأن السلوك **مُختبَر أصلاً**: `pr1.password-recovery.integration.mjs` يحذف المتغيّر عمداً ويوكّد أن الجواب يصير `unavailable`. الشيفرة صحيحة والاختبار صحيح — الناقص أن لا أحد فحص **وجود المتغيّر حيث يهمّ**. اختبارٌ يضبط متغيّراً في أعلى الملف لا يقول شيئاً عن Railway.

### ٣د. نطاق الإنتاج — بندٌ بيد المالك

| البيئة | النطاق المخصّص | حالة `CODIQ_PUBLIC_BASE_URL` |
|---|---|---|
| التجريب | `staging.codiqos.com` ✓ | مضبوط 2026-09-05 → `https://staging.codiqos.com` |
| **الإنتاج** | **لا شيء** — يُقدَّم من `strong-amazement-production-903a.up.railway.app` | **غير مضبوط** |

المالك يملك `codiqos.com` (التجريب على نطاقٍ فرعي منه)، لكن الإنتاج بلا نطاقٍ مخصّص إطلاقاً. وضبط المتغيّر على الإنتاج **يستدعي إعادة نشر**، وهي قراره وحده بحكم ق-134 — فتُركت له مع بقية قائمة ما قبل الإطلاق:

1. اربط `codiqos.com` (والحرف البدل `*.codiqos.com` لنطاقات المتاجر الفرعية) بخدمة `strong-amazement`.
2. اضبط `CODIQ_PUBLIC_BASE_URL = https://codiqos.com`.
3. `pnpm env:check` يجيب بسطر.
### ٣ب. قناة البريد — أثبتها، لا تفترضها

**تدقيق 2026-09-05 على البيئتين الحيّتين: الإنتاج بلا صفٍّ واحد في `notification_outbox`، والتجريب ٣٨ صفّاً كلّها `skipped` وأحدثها ٢٥ آب** — أي قبل وجود SMTP. فالمنصة لم ترسل بريداً واحداً قط، بينما إشارتان تُقرآن نجاحاً: سطر إقلاع العامل «started (provider: smtp-email)» و`/ready` بـ`mail: { configured: true }`. كلتاهما صادقة وليست تسليماً — الأولى تثبت أن المتغيّرات **قُرئت**، والثانية أنها **تُحلَّل**.

والسطح الذي كان سيكتشف هذا هو **استعادة كلمة السرّ** — يوم الإطلاق، لتاجرٍ محبوس خارج متجره، بلا قناة ثانية.

```bash
# يتصل ويصادق ولا يرسل شيئاً — آمن على الإنتاج
pnpm mail:probe

# ثم رسالة حقيقية من طرف إلى طرف
pnpm mail:probe -- --to your-address@example.com
```

شغّله **حيث يعيش السرّ أصلاً** (خدمة Railway)، فلا تُنسخ كلمة السرّ إلى مكانٍ آخر لأجل فحص. ولا يكتب المسبار صفّاً في `notification_outbox`: تلك الجداول تعني «ما أرسلته المنصة إلى زبون»، وفحص المشغّل ليس ذلك.

و«قُبلت من الخادم» ليست «وصلت» — افتح البريد. وGmail المجاني يقف عند ≈٥٠٠ مستلم يومياً، وهو سقف حقيقي حين يصير التجّار أحياءً.

### ٤. تحقّق أخير

بعد التمريرة: افتح `/api/public/plans` (يقرأ من قاعدة البيانات)، وصفحة تاجر حقيقية. **`/api/health` لا يكفي** — لا يلمس قاعدة البيانات ويُعيد `ok` مهما كان حالها.

## فرع الإصدار — كيف يُنشَر إلى الإنتاج (ق-134)

**الإنتاج مربوط بفرع `release`، لا بـ`main`.** قرار المالك 2026-08-31: يُؤجَّل النشر إلى ما قبل الإطلاق، وأُريدَ للتأجيل أن يكون **مضموناً بالإعداد لا بالتذكّر**.

| | |
|---|---|
| دمج إلى `main` | **لا ينشر شيئاً**. التطوير كله هنا، وCI هو البوّابة. |
| النشر | دمج `main` ← `release`. قرار صريح، ومؤرَّخ، وقابل للمراجعة كأي طلب دمج. |
| الحماية | «Wait for CI» مُفعَّل، فلا تُنشر دفعة لم تجتز الاختبارات. |
| التراجع | `release` فرع عادي: أعِده إلى دفعة سابقة وادفعه، فيعود الإنتاج إليها. |

**لماذا فرع لا زرّ:** حين كان الإنتاج مربوطاً بـ`main` مع نشر تلقائي معطّل، لم يكن هناك زرّ «انشر آخر دفعة» **أصلاً** — Railway لا يُنشئ بطاقة لدفعة لم يستقبلها. أضاع ذلك ساعة في 2026-08-31. أما الدمج إلى فرع فهو فعل نملكه بالكامل ولا يعتمد على واجهة أحد.

### الإجراء عند الإطلاق

1. تأكّد أن CI أخضر على `main`.
2. افتح طلب دمج من `main` إلى `release` — عنوانه هو محتوى الإصدار.
3. ادمجه. ينطلق البناء، ثم `pnpm phase1:db:migrate`، ثم التبديل.
4. **لا تكتفِ بـ`/api/health`** — فهو لا يلمس قاعدة البيانات ويُعيد `ok` مهما كان حال المخطّط. افتح نقطة تقرأ بيانات فعلاً (`/api/public/plans`) وصفحة تاجر حقيقية.
5. **قدِّم `prisma/migrations/RELEASED`** إلى اسم آخر هجرةٍ نُشرت الآن، في طلب الدمج التالي إلى `main`. هذا الملفّ هو نقطةُ انطلاق `pnpm migrate:rehearsal` (ق-247): كلُّ هجرةٍ بعده تُعاد في CI فوق صفوفٍ بشكل الإنتاج (`phase1-backend/tests/fixtures/migration-rehearsal-seed.sql`) قبل أن يُسمح لها بالاقتراب منه — لأنّ قاعدة CI الفارغة لا تُثبت شيئاً عن هجرةٍ تُعدّل صفوفاً أو تُقيّدها. إن غيّرت هجرةٌ منشورة عموداً تزرعه البذرة، تُحدَّث البذرة في الطلب نفسه.

### قاعدة البيانات — ما حدث فعلاً في 2026-08-31، مصحَّحاً

**التشخيص الأول كان خاطئاً وسُجّل هنا كي لا يُعاد.** قلتُ إن «staging والإنتاج يتشاركان قاعدة بيانات واحدة»، مستنتجاً ذلك من ظهور نفس المضيف في سجلّي النشر.

**الحقيقة:** Neon مضبوط بشكل صحيح — فروع منفصلة (`production`, `staging`, `development`). العطل كان في **متغيّرات Railway**: بيئة `production` كانت تشير إلى **نقطة اتصال فرع staging** (`ep-red-mode-b1tc5e9d`) بدل فرعها (`ep-soft-smoke-b1b1olu4`). فرع الإنتاج كان خاملاً منذ 2026-08-29 ولم يقرأ منه أحد.

الفرق بين الوصفين ليس لفظياً: «قاعدة مشتركة» تستدعي إعادة تصميم في Neon، بينما «متغيّر يشير إلى الفرع الخطأ» يُصلَح بلصق ثلاث سلاسل. الأول كان سيرسل العمل في اتجاه لا لزوم له.

**وخطأ ثانٍ في نفس اليوم:** استنتجتُ أن قاعدة الإنتاج «متأخّرة 33 هجرة» لأنها خاملة. بعد التصحيح، قال `prisma migrate deploy` وهو على الفرع الصحيح: «No pending migrations to apply» — أي أنها كانت **مُهاجَرة بالكامل**. الخمول ليس تأخّراً.

**الدرس المعمول به:** لا يكفي أن تكون الفروع منفصلة في Neon. تحقّق من **نقطة الاتصال التي يذكرها سجلّ النشر نفسه** (`Datasource "db": ... at "ep-..."`) — فهي الحقيقة الوحيدة عن القاعدة التي تُستعمل فعلاً. وهذه هي الطريقة التي أُثبت بها الإصلاح آخر الأمر.

**الحالة بعد الإصلاح:** الإنتاج على `ep-soft-smoke-b1b1olu4`، والهجرات تجري عبر العنوان **المباشر** (بلا `-pooler`) كما صُمّم السكربت، وفرع `production` في Neon صار نشطاً لأول مرة منذ 29 آب.

**بند مفتوح:** كلمة سرّ `neondb_owner` انكشفت في محادثة أثناء التشخيص. لكل فرع نسخته المستقلّة من الدور، فيُدوَّر كلٌّ على حدة: `production` و`staging` إلزاماً، و`development` و`phase14-test` استحساناً (لهما نقاط اتصال حيّة). فرع النسخة الاحتياطية بلا compute فلا يُوصَل إليه.

## التسجيل المُهيكل ومُعرِّف الطلب (D-41 — المرحلة 24-أ)

كل استجابة تحمل ترويسة `x-request-id`، وكل جسم خطأ يحمل الحقل نفسه داخل `error.requestId`. حين يقول تاجر «صار خطأ» اطلب منه هذا المُعرِّف (١٦ حرفاً ست عشرياً) — يكفي وحده للوصول إلى سطر السجل.

السجلات أسطر JSON على `stdout` يلتقطها Railway مباشرة؛ لا يوجد transport ولا مكتبة تسجيل. شكل السطر واحد: `level` و`time` و`message` و`requestId` و`ctx`.

**الحجم المتوقّع لكل طلب في الإنتاج:** لا شيء لطلب ناجح، ولا شيء لطلب مرفوض بـ4xx (الاستجابة نفسها هي الجواب)، وسطر واحد فقط لكل فشل 5xx. سجلّ الوصول موجود أصلاً في الطبقة الأمامية؛ ما يحمله `stdout` هو ما لا تراه تلك الطبقة.

**المفتاح الوحيد عند وقوع حادثة:** `CODIQ_LOG_LEVEL`. القيمة الافتراضية `info`. اضبطه على `debug` في متغيّرات بيئة Railway لتحصل على سطر `request.completed` واحد إضافيّ لكل طلب (المسار والحالة والمدّة)، ثم أعِده إلى `info` بعد انتهاء الحادثة — لا تتركه `debug`. القيمة `silent` للاختبارات فقط.

**ما لا يُسجَّل أبداً:** كلمات السر ورموز الجلسات وأسرار TOTP ومفتاح التعمية وأي مظروف من `secret-box` ومفاتيح كائنات R2 وسلاسل الاستعلام. أرقام الهواتف والبُرد الإلكترونية تُقنَّع ولا تُحذف. القائمة الكاملة مع أسبابها في رأس `phase1-backend/src/logging/redact.ts`، ويحرسها `pnpm logging:guard`.

## النطاقات (المرحلة 17)

يوفر الخادم حلاً عاماً للقراءة فقط `GET /api/public/store-for-host?host=<host>` يطابق
`custom_domain` أولاً ثم أول label من المضيف مقابل `default_subdomain`، وتعيد الواجهة
توجيه جذر نطاق المتجر إلى `/store/{slug}`.

لتفعيل نطاق فعلياً أمام staging/الإنتاج:

1. **نطاق فرعي للمنصة** (مثل `store-x.codiq.iq`): سجل CNAME wildcard `*.codiq.iq`
   إلى نطاق خدمة Railway، وأضف النطاق في Railway → Settings → Domains (يُصدر TLS
   تلقائياً). كل subdomain يحل تلقائياً لمتجره عبر `default_subdomain`.
2. **نطاق مخصص لتاجر** (مثل `shop.example.com`): يسجل التاجر CNAME إلى نطاق الخدمة،
   وتضيف المالك النطاق في Railway لإصدار TLS، ثم يُخزن في `stores.custom_domain`
   (إدارته الذاتية من لوحة التاجر تأتي مع مراحل لاحقة).

لا يغيّر هذا القسم أي سلوك نشر: staging تلقائية من `main` والإنتاج يدوي بموافقة المالك.

## هجرات staging التلقائية (ما بعد دمج المراحل 14–17)

خدمة Railway في بيئة **staging** مضبوطة الآن بأمر ما قبل النشر
`pnpm phase1:db:migrate` (المُهيأ في لوحة Railway على مستوى بيئة staging فقط)،
فيطبق كل نشر هجرات Prisma على فرع Neon `staging` قبل إقلاع الخادم. بيئة
production غير ممسوسة: نشرها يدوي بموافقة المالك وتُنفذ هجراتها ضمن ذلك
النشر اليدوي حصراً.

## بريد دخول مالك المنصة ومعلومات التواصل (PC-1)

بريد **الدخول** ومعلومات **التواصل** شيئان مختلفان، ولكل منهما مكانه:

| ما هو | أين يُخزَّن | من يغيّره وكيف |
| --- | --- | --- |
| بريد دخول مالك المنصة | `platform_owners.email` | المالك نفسه: **لوحة المالك ← حسابي ومعلومات التواصل ← الأمان** |
| بريد التواصل المنشور | `platform_settings['platform.contact.email']` | المالك نفسه: **… ← معلومات التواصل** |
| رقم التواصل | `platform_settings['platform.contact.phone']` | المصدر نفسه |
| رقم واتساب | `platform_settings['platform.contact.whatsapp']` | المصدر نفسه — **صف غائب يعني: واتساب على رقم التواصل نفسه** |

### الخطوة الصفر: إنشاء المالك أصلاً — لأن الإنتاج بلا مالك

**إحصاء 2026-09-05 على قاعدة الإنتاج أجاب `platform_owners = 0`.** لا صفَّ واحد.
وهذا وحده يفسّر تعذّر دخول المالك، ويُبطل بصمت كل مسارات الاسترجاع أدناه: نموذج
اللوحة يحتاج جلسة، و`owner:email` يرفض الإنشاء بقرار مقصود، وعبارة `UPDATE` لا
تطابق شيئاً. ثلاثة إجراءات صحيحة، كلّها تفترض صفّاً غير موجود.

**قبل الإطلاق، على قاعدة الإنتاج، مرّة واحدة:**

```bash
pnpm owner:create -- --email codiqos.iq@gmail.com --name "اسم المالك"
```

يطلب كلمة السرّ من الطرفية **بلا إظهار** ويطلب تأكيدها. ثم سجّل الدخول وفعّل
المصادقة الثنائية فوراً (ق-124).

| ما يفعله | ما يرفضه |
| --- | --- |
| يستدعي `registerPlatformOwner` نفسها التي يستدعيها مسار HTTP — فسياسة كلمة السرّ (ق-129) وتطبيع البريد وفحص تعارض بريد التاجر هي **الشيفرة ذاتها** لا نسخة منها | **مالكاً ثانياً**: أي صفّ قائم يوقفه ويحيلك إلى `owner:email` — منصةٌ بمالكَين يقدران على كل شيء وبلا سجلٍّ لمن تصرّف أسوأ من أمرٍ فاشل |
| يقرأ كلمة السرّ من الطرفية وحدها | **`--password`**: الوسيط يبقى في سجلّ الأوامر وفي `ps` وفي شاشة من كان ينظر — ثلاث نسخ من سرّ الحساب الذي لا أحد فوقه ليعيد ضبطه |
| يحتاج `DATABASE_URL` (أو `CODIQ_POSTGRES_URL`) للبيئة المقصودة | **الأنبوب**: `stdin` غير تفاعلي مرفوض، فهو السرّ نفسه في ملفٍّ آخر |

**ولماذا ليس `POST /auth/platform/register`؟** لأنه يعمل فقط بينما
`CODIQ_ALLOW_OWNER_REGISTRATION=true` — أي فتح إنشاء مالك بلا مصادقة على الإنترنت
العام، ثم تذكُّر إغلاقه. النافذة هي الخطر، وهي بلا داعٍ: السكربت يحتاج بيانات
اعتماد القاعدة — وهو حدٌّ أعلى صرامةً من مسار HTTP مفتوح — ولا يترك شيئاً يُغلق.

يحرسه `pnpm owner:bootstrap:test`، ويشترط قاعدةً بلا مالكين فيقول ذلك صراحةً بدل
أن يحذف.

### تغيير بريد الدخول — المسار المعتمد

من اللوحة: **حسابي ومعلومات التواصل ← الأمان ← تغيير بريدك الإلكتروني**. يطلب النموذج
**كلمة مرورك الحالية** لأن من يملك تغيير بريدك يملك حسابك. النتيجة:

- كلمة المرور **لا تتغيّر** ولا تُمسّ تجزئتها؛
- جلستك الحالية **تبقى مفتوحة** وجلساتك الأخرى لا تُنهى؛
- يُكتب سطر في سجل تدقيق المنصة (`owner_email_changed`) يحمل البريد القديم والجديد؛
- بريد يملكه تاجر أو موظف متجر أو طاقم منصة يُرفض بـ **409** لا بخطأ خادم.

### إذا تعذّر الدخول أصلاً — سكربت موثّق

عندما لا يستطيع المالك الوصول إلى النموذج (بريده القديم غير متاح، أو قاعدة مستعادة
لتوّها)، يُستعمل السكربت. لا ينشئ مالكاً جديداً، ولا يمسّ `password_hash`، ويُعاد
تشغيله بلا ضرر:

```bash
# اعرض صفوف المالك أولاً
pnpm owner:email -- --list

# غيّر البريد بالبريد القديم
pnpm owner:email -- --from old@example.com --to codiqos.iq@gmail.com

# أو بالمعرّف، إذا كان البريد القديم مجهولاً
pnpm owner:email -- --id 8f2c… --to codiqos.iq@gmail.com
```

يحتاج السكربت `DATABASE_URL` (أو `CODIQ_POSTGRES_URL`) للبيئة المقصودة، ويطبع
`already_set` ويخرج بصفر إذا كان البريد مضبوطاً سلفاً.

### وإذا لم يتوفّر شيء غير `psql`

هذه العبارة تفعل ما يفعله السكربت بالضبط — عموداً واحداً، بلا مساس بكلمة المرور —
لكنها **لا تكتب سطر تدقيق**، فاستعملها آخراً لا أولاً:

```sql
-- بدّل البريدين فقط. WHERE على البريد القديم لا على 1=1:
-- منصة بأكثر من مالك ستفقد الجميع لو حُذف الشرط.
UPDATE platform_owners
   SET email = 'codiqos.iq@gmail.com'
 WHERE email = 'old@example.com';
```

يرفض حارس `codiq_guard_owner_merchant_staff_email` العبارة بـ `23505` إذا كان البريد
مملوكاً لهوية أخرى — وهذا رفض صحيح، لا عطل.
