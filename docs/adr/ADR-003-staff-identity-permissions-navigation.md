# ADR-003 — هوية Staff المستقلة والصلاحيات الدقيقة والتنقل المركزي

**الحالة:** معتمد (قرارات المالك D14-01 إلى D14-07) — منفذ على فرع `phase14-staff-permissions-navigation`.
**التاريخ:** 2026-08-25 (إعادة بناء موثقة بعد فقدان التنفيذ الأول غير المدفوع).

## السياق

يحتاج التاجر إلى تشغيل متجره بفريق عمل دون منح كل موظف هوية التاجر أو صلاحياته
الكاملة. تلتزم المنصة منذ المرحلة الأولى بفلسفة الفصل الكامل بين الهويات
(platform_owner / merchant / customer)، وبأن الخادم — لا الواجهة — هو مصدر
الإذن الوحيد.

## القرارات المعتمدة

| الرمز | القرار |
|---|---|
| D14-01 | هوية `staff` مستقلة تماماً في جدول `staff` بجلساتها الخاصة `staff_sessions`؛ لا role flag داخل merchant أو customer |
| D14-02 | بريد staff فريد عالمياً؛ يمنع Trigger واحد بقفل استشاري أي تداخل بريد بين owner/merchant/staff |
| D14-03 | دوران حزميان فقط في هذه المرحلة: `store_manager` و`store_staff` |
| D14-04 | مصفوفة 11 permission code معتمدة (انظر `phase1-backend/src/auth/staff-permissions.ts` — المصدر الوحيد) |
| D14-05 | إنشاء الموظف مباشر بكلمة مرور مؤقتة (12+ حرفاً)؛ دعوات البريد مؤجلة لمرحلة الإشعارات |
| D14-06 | العضويات المتعددة مسموحة بنيوياً (`store_staff_memberships` بقيد فريد staff+store)؛ اختيار المتجر صريح عند الدخول؛ كل جلسة مقيدة بعضوية واحدة ومتجر واحد |
| D14-07 | الرفض فوري: تعطيل staff أو العضوية أو تغيير الدور يبطل الجلسات المفتوحة فوراً، ويعاد التحقق الحي من النشاط عند كل طلب حساس |

## البنية المنفذة

- **الجلسات:** `createTypedSession("staff", staffId, storeId, membershipId)` تحمل
  claims مقيدة؛ التحقق يطابق السجل الخادمي (tokenHash + expiry + revocation +
  membership/store binding) ثم يتحقق حياً من نشاط staff والعضوية.
- **المحلّل المركزي:** `resolvePermissionSet(role, overrides)` = مصفوفة الدور
  ثم استثناءات العضوية (سماح يضيف، منع يزيل؛ استثناء واحد كحد أقصى لكل code).
- **بوابة المسارات:** `requireStoreActor(request, permission)` تسمح لمالك المتجر
  (بملكيته القائمة) أو لموظف تملك عضويته الصلاحية؛ لا يُقرأ أي دور أو storeId أو
  membershipId من جسم الطلب إطلاقاً.
- **التدقيق:** `order_status_events.actor_kind` يشمل `staff` ويسجل المعرف الحقيقي.
- **التنقل المركزي:** `client/src/config/navigation.ts` مصدر وحيد للوحات
  المالك والتاجر والموظف؛ الترشيح الواجهي عرضي فقط والخادم يرفض 403 عند التجاوز.

## البدائل المرفوضة

- علم دور داخل جدول merchant: يكسر عزل الهوية ويخلط الجلسات.
- صلاحيات محسوبة في الواجهة أو claims ثابتة في JWT: تبقى صالحة بعد تغيير الدور
  وتخالف D14-07؛ الحساب حي من قاعدة البيانات في كل طلب حساس.
- أدوار حرة قابلة للتأليف في هذه المرحلة: تؤجل حتى وجود حاجة منتجية موثقة.
