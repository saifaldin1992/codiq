# ADR-001 — نافذة قرار `completed → returned`

**الحالة:** محسوم — نُفّذ في RI-1 «فحص المرتجعات» (2026-09-02، ق-140): صاحب القرار حامل `inventory.update`؛ الحالات النهائية `restocked / written_off / split` بقيد حسابي في القاعدة؛ حركتا المخزون `storefront_returned_restored` (+) و`storefront_returned_written_off` (−)؛ الواجهة بطاقة «فحص المرتجعات» في شاشة المخزون؛ والفرع الحرج: صف نشط (لم يُخصم مخزونه) يُحرَّر بلا زيادة، وصف مستهلك يُزاد فعلاً — فلا عدّ مزدوج.

**التاريخ:** 2026-08-21

## السياق

تسمح آلة حالات الطلبات بالانتقال `completed → returned`. عند اكتمال طلب COD قد تكون السلعة المرتجعة صالحة لإعادة البيع أو متضررة أو ناقصة أو تحتاج فحصاً. لا توجد في النطاق الحالي Workflow فحص مرتجعات أو حكم جودة أو اعتماد تشغيلي يثبت قابلية إعادة المخزون.

## القرار الحالي

لا يزيد الانتقال `completed → returned` قيمة `products.stock_quantity` تلقائياً، ولا ينشئ حركة مخزون من نوع إعادة استعادة تلقائية. يحدّث التنفيذ الحالي حجز المخزون إلى `returnDisposition = pending_inspection` فقط، لتسجيل أن الطلب عاد ويحتاج قراراً لاحقاً.

## سبب التأجيل

إعادة المخزون تلقائياً قبل الفحص قد تجعل سلعة غير صالحة متاحة للبيع، وتخالف مبدأ دقة المخزون. كما أن اختيار إعادة السلعة أو إتلافها أو تسويتها يتطلب مسؤولاً وسجل قرار وواجهة تشغيلية، وهي متطلبات خارج المرحلة 10.

## العواقب

يبقى المخزون بعد العودة محافظاً: لا يرتفع حتى يصدر قرار فحص صريح. تُصمم المرحلة 17 لتحديد Workflow المرتجعات، وهوية صاحب القرار، وحركات المخزون، وواجهات العرض والتدقيق، ثم تعالج البيانات ذات `pending_inspection` بمسار صريح قابل للمراجعة.
