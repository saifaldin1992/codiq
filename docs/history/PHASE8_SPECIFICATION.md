# codiq — مواصفات المرحلة الثامنة المقترحة

**الحالة:** المواصفة المنقحة النهائية للمراجعة فقط؛ لا تمثل بدء تنفيذ، ولا تتضمن migration أو تغييرًا في `main`.  
**الافتراض التخطيطي:** المرحلة الثامنة هي **إدارة دورة حياة الطلبات الحقيقية** بعد اكتمال الكتالوج والمخزون في المرحلة السابعة. هذا افتراض مبني على أن مساحات الطلبات موجودة حاليًا في لوحتي المالك والتاجر كبنية، وأن نموذج `store_orders` و`order_items` موجود فعليًا لكنه للقراءة فقط. لا يبدأ التنفيذ إلا بموافقة صريحة على هذا الافتراض وهذه المواصفات.

> هذه الوثيقة تحل محل أي مسودة سابقة للمرحلة الثامنة. ويُقرأ معها تقرير `PHASE8_ARCHITECTURAL_REVIEW.md` بوصفه قيدًا معماريًا ملزمًا: هويات منفصلة، تاجر متعدد المتاجر بجلسة متجر مقيدة، عميل محلي لكل متجر، Storefront وCheckout واشتراكات مستقبلية خارج النطاق، وهجرات PostgreSQL additive-first فقط.

> الهدف ليس بناء checkout أو دفع أو توصيل في هذه المرحلة. الهدف هو تحويل الطلبات الموجودة بالفعل إلى وحدة تشغيلية آمنة: عرض مقيد بالمتجر، تفاصيل، انتقالات حالة مضبوطة، وسجل تدقيق غير قابل للمحو وظيفيًا.

## 1. مراجعة الحالة المعتمدة للمراحل 1–7

| المرحلة | الأصل القابل لإعادة الاستخدام في المرحلة الثامنة | القيد الذي تفرضه على المرحلة الثامنة |
|---|---|---|
| 1 | هويات وجلسات منفصلة للمالك والتاجر والزبون، وجلسة التاجر تحمل `merchantId` و`storeId`. | لا يوجد endpoint للطلب بدون تحقق نوع الجلسة ثم متجر الجلسة. |
| 2–3 | مسارات ولوحتا مالك/تاجر وأقسام «الطلبات» المعرفة مسبقًا. | تستبدل صفحات الطلبات فقط؛ لا تغيّر بنية التنقل أو الأقسام غير المرتبطة. |
| 4 | بوابة أثبتت تطابق مسار التاجر المقيد بـ`store-slug` مع الواجهة. | كل واجهة تشغيلية للتاجر تبقى تحت `/merchant/stores/{store-slug}/dashboard`. |
| 5 | `store_orders` و`order_items` ومسارات قراءة مقيدة بالمتجر، مع IDOR موثق. | تُحافظ المرحلة على `403` عند تبديل المتجر و`404` عند حقن مورد متجر آخر. |
| 6 | جلسات HTTP ونماذج فعلية ومسارات API نسبية تحت `/api`. | تستخدم الواجهة الكوكي المعياري ولا تطلب Bearer token يدويًا. |
| 7 | منتجات ومخزون وتصنيفات وصور مقيدة بالمتجر وفهارس cursor pagination. | لا تُخصم كمية مخزون عند تغيير حالة طلب في هذه المرحلة؛ حجز المخزون عند إنشاء الطلب نطاق مستقل لاحقًا. |

## 2. الهدف الكامل للمرحلة الثامنة

تنفيذ إدارة تشغيلية حقيقية للطلبات الموجودة: يستطيع التاجر رؤية طلبات متجر جلسة واحدة، قراءة تفاصيلها، ونقلها خلال حالات محددة مع سبب اختياري وسجل زمني. يستطيع مالك المنصة البحث والقراءة عبر كل المتاجر لأغراض الإشراف والتدقيق، لكنه لا يغير طلبات التاجر في هذه المرحلة. لا ينشئ أي طرف طلبًا جديدًا من لوحة الإدارة، لأن منشأ الطلبات (checkout أو API تكاملية أو إدخال داخلي منضبط) لم يعتمد بعد.

### حالات الطلب المعتمدة

| الحالة التقنية | التسمية في الواجهة | انتقالات صادرة مسموحة |
|---|---|---|
| `new` | جديدة / بحاجة لإجراء | `processing`، `cancelled`، `rejected` |
| `processing` | قيد المعالجة | `preparation`، `cancelled` |
| `preparation` | قيد التجهيز | `out_for_delivery`، `cancelled` |
| `out_for_delivery` | قيد التوصيل | `completed`، `returned` |
| `completed` | مكتملة | `returned` فقط |
| `cancelled` | ملغاة | حالة نهائية |
| `rejected` | مرفوضة | حالة نهائية |
| `returned` | مرتجعة | حالة نهائية |

ترفض أي قفزة غير موجودة في الجدول بحالة `422 / INVALID_ORDER_TRANSITION`. كما يستلزم التغيير إرسال `expectedVersion` لمنع الكتابة فوق تغيير متزامن؛ عند اختلاف النسخة يعاد `409 / ORDER_VERSION_CONFLICT`.

**تصحيح صريح للتعارض السابق:** `processing → new` **ليس** انتقالًا مشروعًا، ولا يوجد أي انتقال rollback إلى `new` من أي حالة. القائمة أعلاه هي مصدر الحقيقة الوحيد للانتقالات في التنفيذ والاختبارات والواجهة.

## 3. الوظائف الداخلة في المرحلة

| المجال | التنفيذ المقترح |
|---|---|
| قائمة الطلبات | قائمة cursor-paginated، وفرز تنازلي حسب وقت الإنشاء، وترشيح بالحالة والنطاق الزمني ورقم الطلب؛ دون جلب غير محدود. |
| تفاصيل الطلب | العميل/المستلم كـsnapshot، بنود الطلب، أسعار اللقطة، الإجمالي، العنوان المختصر، حالة الدفع الحالية، وحالة الطلب وسجل الحالة. |
| انتقال الحالة | نموذج آمن يعرض فقط الحالات المسموح الوصول إليها من الحالة الحالية، مع ملاحظة تشغيلية اختيارية لا تتجاوز 1000 حرف. |
| تدقيق الحالة | سجل أحداث append-only لكل تغيير: الحالة السابقة والجديدة، نوع ومنشئ الفعل، الملاحظة، والوقت UTC. |
| إشراف المالك | قائمة عالمية مقسمة إلى صفحات مع أعمدة المتجر والتاجر، وقراءة تفصيل كل طلب وسجل حالته، بلا تعديل. |
| مؤشرات تشغيلية | عدادات الصفحة الأولى للحالات الجديدة/المعالجة/قيد التوصيل فقط؛ ليست تقارير مالية أو تحليلات تاريخية. |

## 4. الصفحات المطلوبة

### لوحة التاجر

| صفحة موجودة | المسار الفعلي المقيد بالمتجر | ما تصبح عليه في المرحلة الثامنة |
|---|---|---|
| جميع الطلبات | `/merchant/stores/{store-slug}/dashboard/orders` | قائمة الطلبات مع pagination وترشيح وبحث برقم الطلب. |
| بحاجة لإجراء | `/merchant/stores/{store-slug}/dashboard/orders/action-needed` | قائمة `new`، مع انتقالات أولية فقط. |
| جديدة | `/merchant/stores/{store-slug}/dashboard/orders/new` | مرشح `status=new`. |
| قيد المعالجة | `/merchant/stores/{store-slug}/dashboard/orders/processing` | مرشح `status=processing`. |
| قيد التجهيز | `/merchant/stores/{store-slug}/dashboard/orders/preparation` | مرشح `status=preparation`. |
| قيد التوصيل | `/merchant/stores/{store-slug}/dashboard/orders/out-for-delivery` | مرشح `status=out_for_delivery`. |
| مكتملة / ملغاة / مرفوضة / مرتجعة | مساراتها الحالية المقابلة | قوائم قراءة مرشحة بالحالة. |
| تفاصيل طلب جديدة | `/merchant/stores/{store-slug}/dashboard/orders/{orderId}` | تفاصيل مقيدة بمتجر الجلسة، وسجل حالة، وتحكم انتقال آمن. |

تبقى «التسليم»، «التسويات»، و«التقارير» placeholders؛ فالربط بسائق أو تسوية مالية أو تصدير ليس ضمن هذه المرحلة.

### لوحة مالك المنصة

| صفحة موجودة | المسار | ما تصبح عليه في المرحلة الثامنة |
|---|---|---|
| جميع الطلبات | `/platform/dashboard/orders` | قائمة إشراف عالمية مقسمة إلى صفحات، مع أعمدة متجر وتاجر وحالة. |
| صفحات الحالات | مسارات `orders/new` و`orders/processing` و`orders/out-for-delivery` و`orders/completed` و`orders/cancelled` و`orders/returned` | عروض قراءة فقط مرشحة بالحالة. |
| تفاصيل طلب جديدة | `/platform/dashboard/orders/{orderId}` | تفاصيل وسجل تدقيق؛ لا يوجد زر تغيير حالة. |

تبقى «الإرجاع»، «التسليم»، و«التقارير» كواجهات placeholder أو قراءة محدودة؛ لا تنفذ التسويات أو الدفع أو إدارة شركات الشحن الآن.

## 5. نموذج البيانات والعلاقات المقترحة

لا يعدل التنفيذ المقبول جداول قائمة بطريقة مدمرة. تعتمد الهجرة additive-first وتبقي `customer_name` و`total_iqd` الحاليين لسلامة البيانات القديمة.

| الجدول | الإضافة أو التغيير | العلاقات والقيود |
|---|---|---|
| `store_orders` | `customer_id` nullable، `recipient_phone`، `shipping_governorate`، `shipping_address_line1`، `subtotal_iqd`، `delivery_fee_iqd default 0`، `discount_iqd default 0`، `payment_status default 'unpaid'`، `version default 1`، `status_updated_at`، `updated_by_kind` nullable. | يبقى `store_id` إلزاميًا؛ `customer_id` مرجع `customers` بـ`ON DELETE RESTRICT`؛ قيود مبالغ غير سالبة؛ `total_iqd` يساوي لقطة الإجمالي عند الإنشاء ولا يعاد حسابه أثناء انتقال الحالة. |
| `order_status_events` **جديد** | `id` UUID، `store_id`، `order_id`، `from_status` nullable، `to_status`، `actor_kind`، `actor_id` nullable، `note` nullable، `created_at`. | `store_id` و`order_id` إلزاميان؛ Trigger يرفض إدخال حدث لطلب من متجر مختلف؛ لا API للحذف أو التعديل. |
| `order_items` | `sku` nullable كـsnapshot مستقبلي فقط إن وافقت الهجرة؛ لا تغير `product_id` أو تسعير اللقطة الحالي. | يحتفظ `product_name` و`unit_price_iqd` و`line_total_iqd` كبيانات تاريخية. |

### الفهارس المطلوبة

| الفهرس | الغرض |
|---|---|
| `(store_id, status, created_at DESC, id DESC)` على `store_orders` | قوائم حالة التاجر والـcursor. |
| `(store_id, created_at DESC, id DESC)` على `store_orders` | جميع طلبات متجر واحد. |
| `(status, created_at DESC, id DESC)` على `store_orders` | إشراف المالك عبر المنصة مع مرشح الحالة. |
| `(store_id, order_id, created_at DESC)` على `order_status_events` | سجل الطلب المقيد بالمتجر. |

## 6. API endpoints المطلوبة

### التاجر — جميعها تتطلب جلسة `merchant` ومتجر مسار مطابقًا للجلسة

| الطريقة والمسار | الوظيفة | النتيجة الناجحة |
|---|---|---:|
| `GET /api/merchant/stores/:storeSlug/orders` | قائمة cursor-paginated؛ `status`, `from`, `to`, `q`, `limit`, `cursor`. | `200` |
| `GET /api/merchant/stores/:storeSlug/orders/:orderId` | تفاصيل طلب وبنوده وسجل الحالة. | `200` |
| `POST /api/merchant/stores/:storeSlug/orders/:orderId/status` | انتقال الحالة: `toStatus`, `expectedVersion`, `note?`. | `200` |
| `GET /api/merchant/stores/:storeSlug/orders/:orderId/history` | سجل الأحداث append-only. | `200` |

### مالك المنصة — جميعها تتطلب جلسة `platform_owner`

| الطريقة والمسار | الوظيفة | النتيجة الناجحة |
|---|---|---:|
| `GET /api/platform/orders` | قائمة عالمية مقسمة إلى صفحات؛ مرشحات `storeSlug`, `merchantId`, `status`, `from`, `to`, `q`, `limit`, `cursor`. | `200` |
| `GET /api/platform/orders/:orderId` | تفاصيل طلب عالمي مع متجره وتاجره وبنوده وسجل الحالة. | `200` |
| `GET /api/platform/orders/:orderId/history` | قراءة سجل تدقيق عالمي. | `200` |

تنفذ مسارات المالك قراءة فقط. أي طلب `POST/PATCH/DELETE` من مالك على طلب في هذه المرحلة يعاد `404` لعدم وجود endpoint، وليس امتيازًا ضمنيًا. لا يقبل أي endpoint من الجداول السابقة `storeId` في body لتحديد نطاق التفويض.

## 7. الصلاحيات وعزل المستأجر

| الفاعل | مسموح | ممنوع |
|---|---|---|
| تاجر | قراءة وتغيير حالة طلبات متجر الجلسة فقط، ورؤية سجلها. | الوصول لطلب/حدث/قائمة متجر آخر، أو تغيير `store_id`، أو تغيير طلب عبر `orderId` من متجر آخر. |
| مالك منصة | قراءة كل طلبات المتاجر عبر مسارات المالك، مع متجر/تاجر ظاهرين. | استخدام مسارات التاجر، أو تغيير حالة الطلب في المرحلة الثامنة. |
| زبون | لا endpoint تشغيلي للطلبات في المرحلة الثامنة. | كل مسارات التاجر والمالك؛ ترفض قبل منطق البيانات بـ`403 / IDENTITY_BOUNDARY_DENIED`. |

ينفذ كل استعلام تاجر ترتيبًا ثابتًا: `verifyTypedSession('merchant')` ثم حل `storeSlug` ثم تطابق `store.id == claims.storeId` و`store.merchantId == claims.subjectId` ثم الاستعلام بزوج `id + store_id`. ينتج عن تبديل slug `403 / STORE_BOUNDARY_DENIED`، وعن `orderId` يخص متجرًا آخر تحت slug صحيح `404 / RESOURCE_NOT_FOUND`. يطبق `order_status_events` قاعدة المتجر نفسها ولا يعتمد على `order_id` وحده.

## 8. اختبارات IDOR الإلزامية

| الاختبار | الطلب الضار | النتيجة المتوقعة |
|---|---|---|
| تبديل متجر القائمة | Token التاجر A إلى `/merchant/stores/B/orders`. | `403 / STORE_BOUNDARY_DENIED`. |
| قراءة طلب B من مسار A | Token A إلى `/merchant/stores/A/orders/{orderB}`. | `404 / RESOURCE_NOT_FOUND`. |
| تغيير حالة طلب B | Token A إلى `POST /merchant/stores/A/orders/{orderB}/status`. | `404` ولا يتغير `status` ولا يضاف event. |
| قراءة سجل B | Token A إلى `/merchant/stores/A/orders/{orderB}/history`. | `404`. |
| حقن `storeId` في body | Token A يرسل `storeId=B` في طلب تغيير حالة طلب A. | يتجاهل الحقل/يرفضه؛ لا يتجاوز حدود A. |
| مالك المنصة | Token المالك إلى طلب A وB عبر `/api/platform/orders`. | `200` مصرح به، مع البيانات الصحيحة. |
| تاجر إلى مسار المالك | Token التاجر إلى `/api/platform/orders`. | `403 / IDENTITY_BOUNDARY_DENIED`. |
| زبون إلى مسار التاجر | Token زبون إلى قائمة أو تغيير حالة طلب متجره. | `403 / IDENTITY_BOUNDARY_DENIED`. |
| تجاوز SQL | إدخال `order_status_events` يربط متجر A بطلب B مباشرة. | رفض Trigger PostgreSQL برمز قيد دقيق موثق. |

## 9. اختبارات القبول

| السيناريو | معيار القبول |
|---|---|
| قائمة التاجر | تظهر فقط طلبات متجر الجلسة، مع pagination ومرشح حالة وعدد إجمالي غير ضروري لجلب غير محدود. |
| تفاصيل التاجر | تعرض اللقطة التاريخية للبنود والأسعار؛ لا تتغير إذا عدّل المنتج لاحقًا. |
| انتقال مشروع | `new → processing` ينجح بـ`200`، يزيد `version`، ويضيف event واحدًا صحيحًا. |
| انتقال مرفوض | `new → completed` يعاد `422 / INVALID_ORDER_TRANSITION`. |
| إلغاء بعد التوصيل | `out_for_delivery → cancelled` يعاد `422 / INVALID_ORDER_TRANSITION` ولا يضاف حدث. |
| تعارض متزامن | طلبان بنفس `expectedVersion`: واحد `200` والآخر `409 / ORDER_VERSION_CONFLICT`. |
| واجهة التاجر | لا تعرض إلا الانتقالات التالية الصحيحة؛ تظهر رسالة نجاح وتحدّث الحالة وسجلها دون إعادة تحميل كاملة. |
| إشراف المالك | يعرض طلبات A وB ويظهر المتجر/التاجر؛ لا يوجد تحكم تعديل. |
| استمرارية المرحلة 7 | لا يعدل انتقال الحالة `inventory_movements` أو `stock_quantity`. |
| الأداء | اختبار قائمة بـحد 25 وcursor؛ تحقق خطة الاستعلام من استخدام فهرس المتجر/الحالة عند بيانات اختبار كافية. |

## 10. ما ينفذ وما يؤجل

| ينفذ الآن | يؤجل صراحة |
|---|---|
| قراءة وإدارة حالة الطلب وسجل الأحداث، ولوحات التاجر والمالك، pagination، التفويض والاختبارات. | إنشاء الطلب من storefront أو checkout. |
| snapshots التوصيل والعميل اللازمة للتفاصيل عند وجودها. | سلة، كوبونات، ضريبة، احتساب تلقائي للتوصيل، أو دفع إلكتروني. |
| مراجعة مالك المنصة للطلبات فقط. | تغيير حالة إداري استثنائي، تسويات، عمولات، فواتير، أو تقارير مالية. |
| استعادة المخزون أو حجزه **لا يحدث** عند انتقال الحالة. | سياسة حجز/خصم/استعادة مخزون ذرية عند إنشاء/إلغاء الطلب، وتنفيذها مع checkout لاحق. |
| تاريخ تغييرات الحالة. | رسائل SMS/WhatsApp/Email أو webhooks أو أي معالجة خلفية مجدولة. |

## 11. التعارضات والمخاطر التي يجب حلها في التنفيذ

| النقطة | الوضع الحالي | قرار المواصفة |
|---|---|---|
| مصدر إنشاء الطلب | الجداول موجودة والطلبات الحالية اختبارية؛ لا يوجد checkout. | لا تضيف المرحلة الثامنة إنشاء طلب من الواجهة؛ تعامل فقط الطلبات الموجودة. |
| حالات order الحالية | `status` حقل نصي حر من المرحلة الخامسة. | هجرة non-destructive تضيف `CHECK NOT VALID` بعد توحيد البيانات القديمة، ثم تتحقق من القيد قبل تفعيله. |
| العنوان والدفع | لا توجد أعمدة تفصيلية كافية. | إضافات nullable/default-first، ولا يجعلها النموذج إلزامية في المرحلة الثامنة. |
| المخزون | المرحلة السابعة تسجل تعديلًا يدويًا فقط. | لا تغيره المرحلة الثامنة؛ تتطلب سياسة مخزون عند إنشاء الطلب لاحقًا. |
| حجم bundle | بناء المرحلة السابعة أصدر تحذيرًا أكبر من 500KB. | أي مكوّن طلبات ثقيل يستخدم dynamic import أو تقسيم مكوّنات؛ لا يعدل architecture. |

| الطبقة | الأثر المخطط |
|---|---|
| PostgreSQL | هجرة additive-only، فهارس cursor/الحالة، جدول أحداث الحالة وTriggers سلامة store/order؛ لا `DROP` ولا تغيير تدميري قبل موافقة منفصلة. |
| Prisma | توسعة `StoreOrder` و`OrderItem` وإضافة `OrderStatusEvent` وعلاقاتها وفهارسها؛ يعاد توليد العميل بعد مراجعة SQL. |
| Express | خدمة أوامر مستقلة، validation صارم، مسارات API المحددة أعلاه، وتحكم انتقال atomic داخل `prisma.$transaction`. |
| R2 / S3-compatible | لا كتابة جديدة للمرحلة الثامنة. تبقى صور المنتجات من المرحلة السابعة قابلة للقراءة كمرجع فقط إن لزم؛ لا اعتماد على خدمة مغلقة. |

## 13. بوابة الاعتماد قبل التنفيذ

لا يبدأ أي كود أو migration قبل الموافقة الصريحة على: افتراض إدارة الطلبات، مصفوفة الحالات المصححة، قراءة المالك فقط، عدم خصم المخزون في المرحلة، حقول التوافق المستقبلية (`customer_id` nullable وsnapshots و`source` و`version`)، ونطاق تأجيل checkout والدفع والتوصيل. عند الاعتماد، يمكن تقسيم التنفيذ إلى مراحل فرعية: **8A** للمخطط والخدمة واختبارات العزل، ثم **8B** للواجهات واختبارات القبول، ثم بوابة مراجعة نهائية قبل المرحلة التاسعة.
