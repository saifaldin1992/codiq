# مصفوفة مواءمة المرحلة 12 — Storefront وحساب الزبون

**نوع العمل:** تحقق تخطيطي من رأس `main` فقط. لا يتضمن هذا التقرير أي تعديل كود أو قاعدة بيانات أو migration أو تشغيل اختبار يكتب في بيئة development.

**رأس المراجعة:** `d0aa0f81588d4e780fe74538a00a89c1ff250107`، وهو Merge Commit الخاص بـPR #3 للمرحلة 11B.[1]

## النتيجة التنفيذية

يظهر من فحص رأس `main` أن **الأساس الوظيفي للمرحلة 12 موجود فعلياً** تحت التسمية التاريخية PHASE 9B: مسارات Storefront، السلة، حساب الزبون، Checkout COD، والعناوين والطلبات واختبارات القبول موجودة في الشجرة المدمجة. ومع ذلك، لا يطابق التنفيذ الحالي حرفياً أربعة بنود في الخطة الرسمية: **البحث، تصفية التصنيفات، مؤشر نفاد المخزون في الواجهة، ومتغيرات CSS قابلة للحقن لكل متجر**.[2] [3]

> النتيجة المقترحة: لا إعادة بناء للـStorefront. النطاق الصحيح إن أجيز التنفيذ هو **gap-only**: سد الفجوات الأربع المثبتة وإعادة تشغيل قبول Storefront وانحدار النظام.

## الفجوات المقترحة حصراً

| المعرف | النطاق الدقيق | خارج النطاق صراحةً | المخاطر المطلوب حمايتها |
|---|---|---|---|
| G12-01 | تصفية منتجات عامة حسب تصنيف المتجر | إدارة التصنيفات أو تغيير لوحة التاجر | عزل `store_id` وعدم قبول category من متجر آخر |
| G12-02 | بحث منتجات المتجر بالاسم/الوصف ضمن API وصفحة الكتالوج | pg_trgm/tsvector أو `/api/v1`؛ هذه للمرحلة 20 | ترقيم cursor ثابت، وحدود length، ومنع الاستعلامات العابرة للمتجر |
| G12-03 | `isAvailable` عام ورسالة «نفد المخزون» وتعطيل الإضافة | كشف `stockQuantity` أو تغيير reservation/checkout | عدم خلق وعد كاذب بالتوفر؛ يبقى تحقق checkout هو الحكم النهائي |
| G12-04 | CSS custom properties على جذر Storefront بقيم افتراضية آمنة | `store_theme`، لوحة تخصيص، شعار/غلاف؛ هذه للمرحلة 21 | تباين مقروء، RTL، وعدم تغيير business logic |

## اختبارات القبول المقترحة بعد اعتماد فجوات التنفيذ

ستُبنى فقط بعد الموافقة على G12-01…G12-04:

| المعرف | التحقق |
|---|---|
| S12-G01 | تصنيف متجر A يعرض منتجات A فقط؛ تصنيف متجر B لا يمكن استعماله في رابط A أو API A. |
| S12-G02 | البحث يعيد نتائج المتجر نفسه فقط، مع empty/error/loading وترقيم صحيح. |
| S12-G03 | المنتج بصفر مخزون يظهر «نفد المخزون» ولا يقبل الإضافة من الواجهة؛ ويبقى الخادم رافضاً عند checkout في حالة السباق. |
| S12-G04 | القيم الافتراضية لمتغيرات Storefront ظاهرة ومقروءة على 390px وسطح المكتب، من دون تغيير تسعير أو سلة أو Checkout. |
| S12-R01 | إعادة UI-01…UI-07 وواجهات الاختبارات السلبية للعزل وCookies وidempotency. |

## قرار مطلوب قبل أي تنفيذ

لا توجد مشكلة أمنية أو IDOR أو عدم اتساق قاعدة بيانات مثبتة في هذا الفحص الساكن. القرار المطلوب هو أحد الخيارين:

1. **اعتماد gap-only**: تنفيذ G12-01 إلى G12-04 واختباراتها فقط على فرع جديد وPR جديد.
2. **اعتبار المرحلة 12 مصدقاً عليها وظيفياً**: عدم تنفيذ كود جديد، مع تسجيل أن البحث/التصفية/مؤشر النفاد/variables مؤجلة للمرحلة 20 أو 21 بقرار صريح.

لا يبدأ أي خيار قبل موافقة مالك المشروع الصريحة.
