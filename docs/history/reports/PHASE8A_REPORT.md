# تقرير المرحلة 8A — دورة حياة الطلبات: البيانات والخدمة والعزل

**الحالة:** مكتملة فنياً ومختبرة.  
**النطاق المنفذ:** مخطط PostgreSQL وPrisma، خدمة Express/Prisma، معاملات الانتقال، Triggers قاعدة البيانات، ومسارات API واختبارات التكامل فقط.  
**خارج النطاق عمداً:** أي واجهة مستخدم جديدة أو تعديل للوحة التاجر أو لوحة المالك أو Storefront أو Customer API تشغيلي. لا تبدأ المرحلة 8B قبل موافقة صريحة جديدة.

## 1. ملخص التنفيذ

تضيف المرحلة 8A دورة حياة أوامر موحدة وقابلة للتدقيق إلى أساس CODIQ متعدد المستأجرين. تُنفَّذ الانتقالات الحساسة داخل معاملة PostgreSQL واحدة: قراءة الطلب المقيد بـ`store_id`، التحقق من النسخة المتوقعة، التحقق من State Machine، تحديث الحالة وزيادة الإصدار، ثم إضافة حدث تاريخي append-only. لا توجد في هذه المعاملة أي عملية تعديل للمخزون أو لحركات المخزون.

اُستخدمت هجرة **additive-first** باسم `20260817201500_order_lifecycle_8a`، وطُبقت بنجاح على قاعدة PostgreSQL المحلية `codiq_phase5` بواسطة دور التطبيق الفعلي `codiq_app`. تأكد أمر حالة Prisma لاحقاً أن قاعدة البيانات أصبحت متوافقة مع جميع الهجرات الخمس الموجودة.

| المجال | التنفيذ |
|---|---|
| حالات الأوامر | `new`, `processing`, `preparation`, `out_for_delivery`, `completed`, `cancelled`, `rejected`, `returned` |
| إقفال التزامن | `version` مع `expectedVersion` وتحديث ذري مشروط |
| سجل التدقيق | جدول `order_status_events` append-only |
| عزل التاجر | كل قراءة أو انتقال تاجر مقيد بـ`store_id` لجلسة التاجر ومسار `storeSlug` |
| صلاحية المالك | قراءة عالمية فقط لمسارات المرحلة 8A |
| المخزون | لا تعديل تلقائي للمخزون عند تغيير حالة الطلب |

## 2. State Machine المعتمدة والمنفذة

لا يقبل الخادم انتقالاً خارج الجدول التالي. الحالات `cancelled` و`rejected` و`returned` نهائية، ولا توجد عودة إلى `new` من أي حالة.

| الحالة الحالية | الحالات التالية المسموح بها | قرارات أمان مؤكدة |
|---|---|---|
| `new` | `processing`, `cancelled`, `rejected` | لا يوجد انتقال عكسي إلى `new` لاحقاً |
| `processing` | `preparation`, `cancelled` | `processing → new` مرفوض برمز 422 |
| `preparation` | `out_for_delivery`, `cancelled` | — |
| `out_for_delivery` | `completed`, `returned` | `out_for_delivery → cancelled` مرفوض برمز 422 |
| `completed` | `returned` | الانتقال `completed → returned` مسموح ومختبر |
| `cancelled` | لا شيء | نهائية |
| `rejected` | لا شيء | نهائية |
| `returned` | لا شيء | نهائية |

## 3. تغييرات قاعدة البيانات وPrisma

حُدِّث نموذج `StoreOrder` بحقول توافق لازمة للطلبات القادمة، مع الإبقاء على بيانات المراحل السابقة. تشمل هذه الحقول مرجع العميل الاختياري ومعلومات التسليم والمبالغ المفصلة وحالة الدفع والمصدر وإصدار التزامن وزمن آخر تغيير للحالة ونوع الجهة المنفذة. كما أُضيف حقل `sku` الاختياري إلى `OrderItem` للحفاظ على لقطة SKU عند توفرها.

| الكيان | الحقول أو العلاقات الجديدة | الغرض |
|---|---|---|
| `store_orders` | `customer_id`, بيانات المستلم والعنوان، `subtotal_iqd`, `delivery_fee_iqd`, `discount_iqd`, `payment_status`, `source`, `version`, `status_updated_at`, `updated_by_kind` | توافق Checkout المستقبلي وتحكم في التزامن وتدقيق الحالة |
| `order_items` | `sku` | لقطة معرف المنتج التجاري وقت الطلب |
| `order_status_events` | `store_id`, `order_id`, `from_status`, `to_status`, `actor_kind`, `actor_id`, `note`, `created_at` | سجل زمني مستقل وغير قابل للتعديل لانتقالات الحالة |
| فهارس `store_orders` | `(store_id,status,created_at,id)`, `(store_id,created_at,id)`, `(status,created_at,id)`, `customer_id` | قوائم متجرية وعالمية قابلة للترقيم بالمؤشر |
| فهرس الأحداث | `(store_id,order_id,created_at)` | عرض تاريخ الطلب المقيد بالمتجر |

طبقت الهجرة تطبيعاً لمرة واحدة لقيم الحالة القديمة المعروفة المكتوبة بحروف كبيرة إلى حروف صغيرة، ثم أضافت قيد `CHECK` للحالات المعتمدة. إضافة القيد نفذت بصيغة `NOT VALID` ثم `VALIDATE` لتظل الخطوة قابلة للمراجعة وصريحة عند اكتشاف بيانات تاريخية مخالفة.

### حماية بنيوية داخل PostgreSQL

> `order_status_events` هو سجل تدقيق append-only وليس جدولاً قابلاً للتحرير الإداري.

تُفرض الحمايتان التاليتان في قاعدة البيانات نفسها، وليس في Express فقط:

| Trigger | السلوك المحمي | نتيجة الاختبار المباشر |
|---|---|---|
| `order_status_events_guard_store` | يمنع إدراج حدث يحمل `store_id` يختلف عن متجر الطلب المشار إليه | SQLSTATE `23514` |
| `order_status_events_immutable` | يمنع `UPDATE` أو `DELETE` لأي حدث حالة موجود | SQLSTATE `23514` |

## 4. خدمة دورة الحياة والمعاملات

يوجد منطق المرحلة في `phase1-backend/src/services/order-lifecycle.service.ts`. تتلقى خدمة التاجر `storeId` الناتج من مصادقة الجلسة، ولا تقبل `storeId` من جسم الطلب. تستعلم عن الطلب دائماً مع الشرط المركب `id + storeId`، ولذلك لا يمكن لمعرف طلب من متجر آخر أن يصبح قابلاً للقراءة أو التعديل بتبديل المعرف وحده.

يُفحص `expectedVersion` قبل صلاحية الانتقال. إذا كانت النسخة قديمة، يُعاد `409 ORDER_VERSION_CONFLICT` حتى لو تغيرت الحالة إلى حالة تجعل الانتقال المطلوب غير صالح الآن؛ وهذا يمنع نتيجة غير حتمية للطلبات المتوازية ويطلب من العميل إعادة القراءة قبل اتخاذ قرار جديد.

| المسار | الهوية المسموحة | السلوك |
|---|---|---|
| `GET /merchant/stores/:storeSlug/orders` | التاجر المقيد بالمتجر | قائمة cursor-paginated مع مرشحات `status`, `from`, `to`, `q` |
| `GET /merchant/stores/:storeSlug/orders/:orderId` | التاجر المقيد بالمتجر | تفاصيل طلب واحد مع العناصر وسجل الأحداث |
| `POST /merchant/stores/:storeSlug/orders/:orderId/status` | التاجر المقيد بالمتجر | انتقال حالة ذري باستخدام `toStatus`, `expectedVersion`, و`note` اختياري |
| `GET /merchant/stores/:storeSlug/orders/:orderId/history` | التاجر المقيد بالمتجر | سجل أحداث الطلب بالترتيب الزمني |
| `GET /platform/orders` | مالك المنصة | قائمة عالمية بمرشحات الحالة والتاريخ والبحث والتاجر والمتجر |
| `GET /platform/orders/:orderId` | مالك المنصة | تفاصيل عالمية للطلب |
| `GET /platform/orders/:orderId/history` | مالك المنصة | تاريخ الحالة العالمي للطلب |

لا يوجد في 8A endpoint لإنشاء طلب Customer أو لعرض طلبات Customer أو لتغييرها. كما أن مسارات المالك في هذه المرحلة قراءة فقط ولا يوجد endpoint مالك لتغيير الحالة.

## 5. نتائج الاختبارات الموثقة

## 6. حدود المرحلة والتوقف الإلزامي

اكتملت 8A من دون تنفيذ 8B. لم تُبن أي صفحات Merchant أو Platform لعرض أو تغيير الطلبات، ولم تُنفذ أي اختبارات متصفح أو Acceptance Tests للواجهة. كما لم تنفذ حسابات العملاء التشغيلية أو Storefront أو Cart أو Checkout أو اشتراكات أو خطط أو Feature Gating أو تكاملات دفع أو توصيل.

الخطوة التالية المقترحة، **بعد موافقة صريحة فقط**، هي 8B: ربط مسارات القراءة والتحديث الحالية بواجهات التاجر والمالك وفق هوية One UI، ثم اختبارات المتصفح ومعايير القبول المخصصة للواجهة. لا يُتخذ أي إجراء متعلق بـ8B قبل هذه الموافقة.
