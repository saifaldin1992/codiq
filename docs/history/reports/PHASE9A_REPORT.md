# تقرير المرحلة 9A — المخطط والخدمات والاختبارات الخلفية

**الحالة:** مكتملة فنياً ومجتازة بوابة الاختبارات.  
**النطاق المنفذ:** PostgreSQL وPrisma وExpress وخدمات السلة والحساب وcheckout والحجز واختبارات DB/API/IDOR/concurrency فقط.  
**النطاق غير المنفذ:** لا توجد واجهة Storefront أو صفحة حساب عميل أو صفحة سلة أو Checkout مرئية؛ هذه العناصر تبقى حصراً في 9B بعد موافقة مستقلة.

## 1. ملخص التنفيذ

نفذت 9A نموذج Storefront الخلفي المتفق عليه: هوية العميل بالهاتف وكلمة المرور، سلة موحدة للضيف والعميل، دمج معاملاتي للسلات، checkout COD بمعاملة `Serializable` ومفتاح idempotency، وحجز مخزون منفصل يمنع overselling. لا تغير خدمة انتقال الحالة العامة في 8A المخزون للطلبات السابقة. تضاف آثار الحجز فقط إلى طلب `source='storefront'` يمتلك حجوزات فعلية.

طبقت هجرات 9A على PostgreSQL المحلي ثم على Neon الدائم. يتأكد الفحص النهائي في Neon من وجود **7 هجرات Prisma** و**6 جداول Storefront**: `shopping_carts` و`cart_items` و`customer_addresses` و`checkout_requests` و`inventory_reservations` و`storefront_rate_limits`.

| مجال التنفيذ | النتيجة |
|---|---|
| هوية العميل | الهاتف المعياري E.164 وكلمة المرور هما اعتماد Storefront؛ البريد اختياري، والمسارات القديمة بقيت متوافقة مع تسجيل البريد للمراحل السابقة فقط. |
| السلات | جدول `shopping_carts` واحد بدل polymorphic carts؛ رمز الضيف الخام في cookie فقط وبصمته SHA-256 في PostgreSQL. |
| العزل | قيود مركبة تمنع cart/address/order من الإشارة إلى customer أو product في متجر آخر. |
| checkout | طلب COD واحد لكل مفتاح idempotency وبصمة طلب؛ ينتج الطلب والبنود والحدث والحجوزات وتحويل السلة في معاملة واحدة. |
| المخزون | لا خصم عند الإضافة إلى السلة ولا عند checkout؛ الحجز يمنع oversell. الخصم يحدث عند `completed` فقط لطلب Storefront. |
| المرتجعات | `completed → returned` أو `out_for_delivery → returned` يسجل `pending_inspection` فقط. لا زيادة تلقائية في `stock_quantity` ولا حركة `storefront_returned_restored`. |
| الحماية | جلسات وcookies عميل مقيدة بمسار المتجر، تحقق Origin للكتابة، وحدود معدل مخزنة في PostgreSQL لمسارات الكتابة الحساسة. |

## 4. نتائج Acceptance Tests للمرحلة 9A

شغل `pnpm phase9a:test` قاعدة PostgreSQL محلية منعزلة مع خادمي API وجلسات فعلية. أنشأ الاختبار تاجرين ومتجرين ومنتجات وحسابات وسلات وطلبات ثم نظف البيانات ضمن قاعدة الاختبار.

| المجموعة | التغطية | النتيجة |
|---|---|---|
| قيود الهوية | الهاتف المكرر في المتجر نفسه مرفوض، والهاتف نفسه في متجر آخر مقبول. | **نجح.** استجابة API مكررة `409`، وعزل المتجر محفوظ. |
| قيود العزل البنيوية | رمز ضيف مكرر، منتج Store-B في سلة Store-A، عنوان Store-B لعميل Store-A، وطلب Store-B لعميل Store-A. | **نجح.** SQLSTATEs: `23505` لرمز الضيف و`23503` لجميع FK المركبة العابرة للمتجر. |
| السلة | تصفح عام مقيد بالمتجر، رفض منتج متجر آخر، لقطة السعر، انتهاء كسول للسلة، وOrigin خاطئ. | **نجح.** `404` للمنتج العابر، لقطة `10000` بقيت ثابتة، سلة منتهية ظهرت فارغة، وOrigin غير موثوق عاد `403`. |
| الدمج | دمج ضيف→عميل وتسجيلا دخول متزامنان لنفس سلة الضيف. | **نجح.** عنصر واحد فقط بكمية صحيحة؛ لا تضاعف عناصر السلة. |
| checkout | COD، request أول، replay بالمفتاح نفسه، ومطلبان متزامنان بالمفتاح نفسه. | **نجح.** الأول `201`، replay `200` بالطلب نفسه، والتزامن أعاد `200/201` لنفس معرف الطلب فقط. |
| الحجز والمخزون | حجز checkout، إلغاء، رفض، إرجاع قبل الإكمال، إكمال ثم إرجاع محافظ. | **نجح.** checkout لا يخصم المخزون؛ cancelled/rejected يحرران الحجز؛ قبل الإكمال يبقى الحجز `active/pending_inspection`؛ وبعد `completed → returned` بقي الحجز `consumed/pending_inspection` وكمية المخزون `3` بلا حركة restore. |
| IDOR والهوية | عميل A إلى طلب عميل B، جلسة A في Store-B، وCustomer token لمسار تاجر. | **نجح.** `404` للطلب غير المملوك، و`403` لعبور المتجر والهوية. |
| سجل حالات 8A | تعديل event أنشئ من Storefront. | **نجح.** Trigger رفض التعديل بـ`23514`. |
| حد المعدل | تجاوز محاولات login ضمن النافذة. | **نجح.** `429 RATE_LIMITED`. |

## 6. المشكلات المكتشفة وكيف عولجت

| المسألة | المعالجة |
|---|---|
| بيانات اعتماد دور تطوير PostgreSQL القديمة لم تعد صالحة. | استخدم دور التطبيق المحلي الفعلي `codiq_app` لتطبيق هجرة الاختبارات؛ لم يغير ذلك بنية الإنتاج أو أسرار Neon. |

| دمج سلة الضيف يحتاج حماية من login متزامن. | أضيف retry Serializable واختبار جلستي login متوازيتين، مع إثبات عنصر واحد فقط بعد الدمج. |

| حد المعدل في ذاكرة process لا يفي بالتوسع أو تعدد instances. | نفذ حد معدل ذري في PostgreSQL بمفتاح hash مركب، قابل للعمل عبر أكثر من instance. |

## 7. ملاحظات باقية قبل 9B

المرحلة 9A لا تتضمن أي واجهة Storefront، لذلك لا يوجد كتالوج أو سلة أو login أو checkout مرئي للمستخدم النهائي بعد. هذه الواجهة تؤجل كلياً إلى 9B. كما أن `returned` يسجل حالة `pending_inspection` فقط؛ لا توجد شاشة أو workflow فحص لتقرير كمية قابلة للبيع، ولا يجوز بناء ذلك ضمن 9B من دون مواصفة مستقلة للمرتجعات.

يبقى SMS/OTP، الدفع الإلكتروني، كوبونات، تسعير الشحن، إشعارات الزبون، وإعادة بيع المرتجعات خارج النطاق. قبل فتح الموقع أمام عملاء فعليين، ينبغي أيضاً تفعيل نسخ Neon المجدولة ونافذة استعادة مناسبة وفق الخطة التشغيلية المختارة.
