# خطة المرحلة 12 — واجهة Storefront وحساب الزبون

**الحالة:** تخطيط ومراجعة فقط. لا يشكل هذا المستند إذناً لتنفيذ كود أو تعديل قاعدة بيانات أو تشغيل migration أو فتح Pull Request جديد.

**المرجع الرسمي:** تسمي خطة CODIQ المراحل مرحلة 12 باسم **«واجهة Storefront وحساب الزبون (9B)»**.[1] ولذلك فإنها تقابل وظيفياً العمل الموثق تاريخياً باسم **PHASE 9B**؛ ولا يجوز افتراض أن المطلوب هو إعادة بناء واجهة موجودة من الصفر.

## 1. هدف المرحلة

الهدف الرسمي هو جعل المتجر العام تحت `/store/{slug}` واجهة تجارية صالحة للزبون: كتالوج ومنتج وسلة وCheckout عند الاستلام وحساب زبون وعناوين وطلبات، مع دعم RTL والجوال وحالات الواجهة.[1]

> **مبدأ هذه الخطة:** تبدأ المرحلة بتحقيق مواءمة، لا بتكرار التنفيذ. فالتقرير الحالي لـPHASE 9B يوثق وجود معظم هذا النطاق، بما في ذلك الكتالوج والسلة وحساب الزبون وCheckout COD وتسعير التوصيل واختبارات UI-01…UI-07.[2]

## 2. نقطة التحقق الإلزامية قبل أي تنفيذ

يوجد اختلاف ترقيم ينبغي حسمه توثيقياً: خطة 26 مرحلة تضع Storefront في المرحلة 12، بينما تقرير المشروع يوثق نطاقاً منفذاً باسم 9B. لذلك تكون أول بوابة للمرحلة **مراجعة مواءمة commit-to-scope** للتحقق من الآتي:

| سؤال المواءمة | الدليل المطلوب | النتيجة التي تسمح بالمتابعة |
|---|---|---|
| هل كود Storefront 9B موجود على `main` فعلياً؟ | Git ancestry وملفات الواجهة والاختبارات على رأس `main` | يثبت أن التنفيذ السابق هو أساس المرحلة 12 |
| هل يغطي التنفيذ البنود الستة الرسمية للمرحلة 12؟ | مصفوفة requirement → route/component/API/test | تُصنّف البنود: مغطى / جزئي / غير مغطى |
| هل تقرير 9B التاريخي يعكس حالة Git الحالية؟ | مقارنة التقرير بسجل commits وPRs | يوثق أي قدم أو اختلاف في التقرير، بلا إعادة كتابة للتاريخ |
| هل توجد فجوة حرجة أمنية أو عزل؟ | اختبار API والمتصفح وCI وstaging | التوقف الفوري عند أي Critical أو IDOR أو عدم اتساق بيانات |

إذا أثبتت هذه البوابة أن النطاق مكتمل فعلاً، تتحول المرحلة 12 إلى **مرحلة تصديق وإغلاق رسمي** فقط. وإذا أثبتت فجوة، يُعرض فرق محدد وخطة ضيقة لها قبل تعديل أي كود.

## 3. نطاق المواءمة الرسمي

| بند المرحلة 12 الرسمي | الدليل الموثق حالياً | ما يجب التحقق منه في مواءمة المرحلة |
|---|---|---|
| كتالوج عام ومنتج وتصنيفات وبحث ونفاد مخزون | يصف تقرير 9B كتالوجاً وواجهات Storefront فوق `/store/:storeSlug`.[2] | المسارات الحية، حالات loading/empty/error، ودقة حالة المخزون |
| سلة ضيف وزبون وحجوزات وتوفر | يوثق التقرير سلة ضيف/زبون، Cookies HttpOnly، دمج السلة، وحجز checkout.[2] | عدم تسرب Cookies بين المتاجر، وعدم كسر حماية overselling |
| Checkout COD والتوصيل والنجاح | يوثق التقرير Quote، رسوم توصيل ملتقطة، رفض المحافظة غير المتاحة، والإجمالي النهائي.[2] | تدفق العنوان → quote → checkout → رقم الطلب على staging |
| حساب الزبون | يوثق التقرير الدخول بالهاتف، العناوين، سجل الطلبات والتفاصيل.[2] | عزل العميل، رموز 401/403/404، وعدم كشف metadata داخل history |
| CSS Variables وRTL والجوال | يوثق التقرير RTL وفحص عرض 390px وعدم وجود overflow.[2] | وجود CSS tokens قابلة للتوسع، وسلامة 390px وسطح المكتب |
| سيناريوهات قبول المتصفح | يوثق التقرير UI-01 إلى UI-07 بنتائج نجاح تاريخية.[2] | قابلية إعادة التشغيل على البيئة المعتمدة، وقرار معالجة B-15 منفصلاً إن ظل CI هشاً |

## 4. ما هو خارج النطاق

لا تتضمن المرحلة 12، وفق الخطة الرسمية، الدفع الإلكتروني أو تخصيص شكل المتجر من لوحة التاجر أو SEO المتقدم؛ تبقى هذه العناصر لمراحلها اللاحقة.[1] كما لا تسمح هذه الخطة بتغيير Prisma schema أو migrations أو إضافة مزود دفع أو OTP/SMS أو كوبونات أو تكامل شحن.

## 5. معايير قبول مقترحة للمصادقة الرسمية

هذه قائمة تحقق للمراجعة؛ لا تصبح اختباراً ملزماً أو نطاق تنفيذ إلا بعد إجازة المالك:

| المعرف | السيناريو | معيار النجاح |
|---|---|---|
| S12-01 | زائر يتصفح كتالوج متجر وصفحة منتج | يعرض المنتجات والتصنيفات والتوفر، مع حالات loading/empty/error سليمة |
| S12-02 | ضيف يضيف للسلة ثم يسجل | تندمج السلة من الخادم، ولا تستخدم الواجهة Bearer أو `localStorage` للجلسة |
| S12-03 | زبون ينفذ COD | يختار عنواناً ومحافظة، يرى رسوم التوصيل والإجمالي، ثم يحصل على رقم طلب |
| S12-04 | محافظة غير متاحة | يعرض الخادم `422 DELIVERY_UNAVAILABLE_FOR_GOVERNORATE` والواجهة رسالة عربية واضحة |
| S12-05 | إعادة المحاولة بالمفتاح نفسه | يعود نفس الطلب بنفس لقطة رسوم التوصيل ولا ينشأ طلب مكرر |
| S12-06 | محاولة عزل عابرة لمتجر أو زبون | Cookies/Orders/Addresses لا تعبر حدود المتجر أو العميل، مع رموز رفض صحيحة |
| S12-07 | الجوال وسطح المكتب | تعمل التدفقات الحرجة على 390px وسطح المكتب بلا تجاوز أفقي أو انقطاع تفاعل |

## 6. بوابة الانحدار المقترحة

قبل أي إغلاق رسمي، يجري تشغيل `pnpm check` و`pnpm phase1:typecheck` و`pnpm build`، ثم مجموعات تكامل المراحل السابقة وفحوص Storefront. يبقى `ci / integration` الحاجب شرطاً لأي PR، بينما `ci / browser acceptance` غير حاجب حالياً بسبب B-15؛ لا يجوز الادعاء بحل B-15 أو جعله حاجباً ضمن هذه المرحلة من دون قرار مستقل.[1]

## 7. قرارات مطلوبة من المالك قبل التنفيذ

| القرار | الخيارات | التوصية |
|---|---|---|
| معالجة الترقيم | اعتماد 9B السابقة بوصفها التنفيذ المكافئ للمرحلة 12، أو طلب gap-only لإكمال أي نقص مثبت | اعتماد **مواءمة + gap-only**؛ يمنع إعادة العمل ويجعل السجل الرسمي صحيحاً |
| قائمة القبول | اعتماد S12-01…S12-07 أعلاه أو تعديلها | مراجعتها واعتمادها قبل أي تشغيل قبول رسمي |
| أي فجوة جديدة | عرض diff وخطة ضيقة أولاً أو السماح بتنفيذ مفتوح | عرض فرق محدد أولاً؛ لا تنفيذ مفتوح |

## 8. ترتيب التنفيذ المقترح بعد الموافقة

1. إنشاء فرع مخصص للمرحلة 12، بلا تعديل في `main`.
2. تنفيذ بوابة مواءمة Git والكود والاختبارات وإعداد مصفوفة التغطية.
3. عرض المصفوفة والفجوات، إن وجدت، على المالك قبل تعديل أي كود.
4. تنفيذ الفجوات المثبتة فقط، مع الاختبارات والسلوكيات السلبية والعزل.
5. تشغيل بوابة الانحدار وCI وstaging، ثم كتابة تقرير المرحلة.
6. فتح PR، انتظار المراجعة والموافقة الصريحة، ثم الدمج بـMerge Commit فقط.

## 9. حالة هذه الخطة

لم يُنشأ فرع مرحلة 12، ولم يُعدّل كود أو schema أو migration، ولم تُشغّل اختبارات قبول جديدة نتيجة هذه الخطة. الإجراء التالي الصحيح هو قرار المالك على **معالجة الترقيم** وقائمة القبول، ثم إذن صريح منفصل لبدء التنفيذ.
