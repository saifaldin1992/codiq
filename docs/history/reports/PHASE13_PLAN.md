# خطة المرحلة 13 — Store Switcher وإنشاء المتاجر

**الحالة:** تخطيط فقط؛ لا توجد موافقة تنفيذية بعد.  
**المرجع الرسمي:** المرحلة 13 من `docs/CODIQ_FULL_PLAN_26_PHASES.md`.  
**القرار المطلوب قبل التنفيذ:** الحد المؤقت لعدد المتاجر لكل تاجر. الاقتراح: **3 متاجر إجمالاً لكل تاجر، شاملة المتجر الأول**. [1]

## 1. الهدف والنتيجة التجارية

تمكّن المرحلة 13 التاجر الواحد من امتلاك أكثر من متجر وإدارتهما بأمان، مع المحافظة على القاعدة المعمارية الحالية:

> **جلسة التاجر مقيدة بمتجر واحد.** لا يُسمح لمسار متجر B باستخدام جلسة متجر A حتى إذا كان المتجران للتاجر نفسه.

لا تعني المرحلة إنشاء هوية تاجر جديدة أو تحويل الجلسة إلى جلسة «شاملة لكل المتاجر». بدلاً من ذلك، يصدر التبديل **جلسة جديدة مستقلة** ومقيدة صراحةً بالمتجر المختار، فيما تظل الجلسة السابقة صالحة في سياق متجرها الأصلي إلى أن تنتهي أو تُلغى. [1] [2]

| المخرج | النتيجة المطلوبة |
|---|---|
| تبديل السياق | التاجر يرى متاجره ويختار متجراً يملكه؛ يتلقى cookie جلسة جديدة مقيدة به ويُعاد إلى لوحة المتجر المختار. |
| إنشاء متجر | التاجر ينشئ متجراً باسم وslug صالحين؛ يجهز النظام أساس المتجر ذرياً عبر `createStoreFoundation`. |
| عزل الجلسات | مسار متجر مختلف يرفض الجلسة القديمة بـ`403`، ولا يوجد تبديل ضمني من `storeSlug` في الرابط. |
| حد مؤقت | يرفض الخادم إنشاء متجر فوق الحد المعتمد برمز ثابت ورسالة عربية واضحة. |

## 2. ما هو موجود بالفعل وما ستضيفه المرحلة

المخطط الحالي يحتوي علاقة `Merchant.stores`، وجدول `merchant_sessions` يتضمن `merchant_id` و`store_id`، كما أن جدول `stores` يحمل اسم المتجر وslug فريداً وعلاقة مالكه. لذا فإن الأساس البنيوي لتعدد المتاجر موجود بالفعل؛ المطلوب هو مسار التبديل، الإنشاء المصرح به من التاجر، وواجهة التحكم. [2]

| موجود فعلياً | تضيفه المرحلة 13 |
|---|---|
| جلسة تاجر مرتبطة بـ`store_id` | إصدار جلسة جديدة للمتجر المختار بعد تحقق الملكية. |
| مسارات لوحة التاجر المقيدة بـ`/merchant/stores/:storeSlug/dashboard` | قائمة متاجر حقيقية ومؤشر متجر نشط وروابط انتقال آمنة. |
| `createStoreFoundation` مستخدم في provisioning المالك | إعادة استخدامه لإنشاء متجر التاجر مع تهيئة القيم الأساسية داخل معاملة ذرية. |
| slug فريد في قاعدة البيانات | تحقق regex خادمي ورسائل أخطاء صريحة وحد متجر مؤقت. |
| حارس `requireMerchantStore` | اختبار صريح يثبت أن التبديل، لا تغيير الرابط، هو الطريق الوحيد للوصول للمتجر الثاني. |

## 3. النطاق الوظيفي التفصيلي

### 3.1 عقد API المقترح

لا يعد هذا الجدول عقداً منفذاً بعد؛ هو المقترح الذي يجب تثبيته قبل كتابة الكود.

| المسار المقترح | الغرض | التفويض | النتيجة الناجحة | حالات الرفض الأساسية |
|---|---|---|---|---|
| `GET /api/merchant/stores` | قائمة متاجر صاحب جلسة التاجر فقط | cookie تاجر صالحة | `200` وقائمة `{id,name,slug,isActive}` | `401` بلا جلسة |
| `POST /api/merchant/stores/switch` | تبديل السياق إلى `{storeSlug}` يملكه التاجر | cookie تاجر صالحة + ملكية المتجر | `200`، cookie جلسة جديدة، `{store}` | `404` لمتجر غير مملوك، `422` لإدخال غير صالح |
| `POST /api/merchant/stores` | إنشاء متجر جديد من `{name,slug}` | cookie تاجر صالحة + ضمن الحد | `201` مع store وcookie جلسة المتجر الجديد | `422` لاسم/slug غير صالح، `409` لslug مستخدم، `403` عند تجاوز الحد |

**اختيار أمني مقترح:** يعيد endpoint التبديل `404` للـslug غير المملوك بدلاً من `403` حتى لا يكشف وجود متجر لتاجر آخر. أما محاولة استعمال cookie متجر A مباشرة مع مسار B المملوك لنفس التاجر فتظل `403 / STORE_BOUNDARY_DENIED` كما هي؛ فهي ليست عملية تبديل. [1]

### 3.2 قواعد الإدخال

| الحقل | القاعدة |
|---|---|
| `name` | مطلوب بعد trim، نص مرئي غير فارغ، حد طول يوثق أثناء التنفيذ. |
| `slug` | مطلوب، lowercase فقط، ويطابق: `^[a-z0-9](?:[a-z0-9-]{1,48}[a-z0-9])?$`. |
| `slug` الفريد | تتحقق الخدمة مبكراً للرسالة الواضحة، وتبقى unique constraint في قاعدة البيانات الحارس النهائي. |
| الحد المؤقت | عدّ المتاجر النشطة/المملوكة داخل المعاملة قبل الإنشاء؛ لا يطبق في الواجهة وحدها. |

### 3.3 إنشاء أساس المتجر

يجب أن يستدعي إنشاء التاجر لنفسه `createStoreFoundation` داخل معاملة واحدة، لا أن يعيد كتابة التهيئة. ويجب التحقق اختبارياً من إنشاء سجل المتجر، وإعدادات الإشعار، وسائل الدفع الأساسية، وصفوف رسوم التوصيل المتوقعة بنفس خصائص المتجر الأول. فشل أي جزء يجب أن يلغي كل العملية، بما في ذلك إنشاء المتجر نفسه. [3]

## 4. الواجهة وتجربة المستخدم

| الموضع | السلوك المطلوب | حالات الواجهة |
|---|---|---|
| رأس لوحة التاجر / Store Switcher | يعرض اسم المتجر النشط، ويكشف قائمة المتاجر المملوكة فقط | loading، empty لا يحدث للتاجر الصحيح، error مع إعادة محاولة، active واضح |
| عنصر المتجر في القائمة | الاسم وslug؛ المتجر الحالي موسوم بوضوح | النقر على المتجر الحالي لا ينشئ جلسة مكررة |
| إجراء «إنشاء متجر» | نموذج اسم/slug مع إرشاد regex وتغذية راجعة خادمية | loading، field errors، slug conflict، limit reached، success redirect |
| بعد نجاح التبديل/الإنشاء | الانتقال إلى `/merchant/stores/{slug}/dashboard` | لا تبديل route قبل نجاح API وكتابة cookie |

لا تشمل المرحلة لوحة تخصيص المظهر أو النطاقات أو الاشتراكات أو الموظفين. Store Switcher في المراحل السابقة كان بنية بصرية فقط؛ يحل محله سلوك فعلي مقيد بالخادم. [1]

## 5. الأمان والعزل والجلسات

1. تعتمد كل عملية على cookie التاجر HttpOnly الحالية؛ لا تقبل `merchantId` أو `storeId` من جسم الطلب كمرجع تفويض.
2. يستخرج الخادم التاجر من الجلسة، ثم يبحث عن المتجر بـ`{ slug, merchantId }` قبل إصدار الجلسة الجديدة.
3. لا تُلغى الجلسة السابقة عند التبديل؛ تثبت اختبارات API أنها تعمل على متجر A فقط ولا تعمل على B.
4. تظل كل endpoints الحالية مستخدمة لـ`requireMerchantStore`، ولذلك لا يُخفف الحارس ولا يُستبدل بفحص frontend.
5. لا تكشف رسائل التبديل وجود متجر خارجي، ولا تسمح الواجهة بعرض متاجر غير مالك الجلسة.
6. لا يوجد تعديل لـPrisma schema أو migration مقترح؛ تتحقق هذه النتيجة من جداول `merchants` و`stores` و`merchant_sessions` القائمة. [2]

## 6. الاختبارات وبوابة القبول

| المعرّف | نوع الاختبار | الإثبات الحتمي |
|---|---|---|
| S13-01 | API إيجابي | قائمة متجرين لنفس التاجر تعرضهما فقط. |
| S13-02 | عزل | cookie متجر A يطلب مورد/مسار متجر B لنفس التاجر → `403 / STORE_BOUNDARY_DENIED`. |
| S13-03 | تبديل | switch إلى B يصدر cookie جديدة تعمل في B؛ token الجلسة القديمة يبقى صالحاً في A فقط. |
| S13-04 | IDOR | switch إلى slug يملكه تاجر آخر → `404`، ولا تصدر cookie جديدة. |
| S13-05 | تحقق | slug لا يطابق regex → `422` بخطأ محدد. |
| S13-06 | التفرد | slug مستخدم → `409`، مع ثبات عدد المتاجر. |
| S13-07 | الحد | المتجر التالي فوق الحد المؤقت → `403 / STORE_LIMIT_REACHED`، حتى بطلب API مباشر. |
| S13-08 | الذرية | نجاح الإنشاء يجهز أساس المتجر؛ فشل مصطنع في foundation لا يترك متجراً جزئياً. |
| S13-09 | متصفح حي | تسجيل الدخول → التبديل → ظهور المتجر النشط → إنشاء متجر → الانتقال إليه على 390px وسطح المكتب. |
| S13-10 | انحدار | `pnpm check` و`phase1:typecheck` و`build` وكل اختبارات 1→12 وBrowser Storefront. |

## 8. ما هو خارج النطاق صراحةً

لا تشمل المرحلة 13: staff أو RBAC granular (14)، الإشعارات (15)، الخطط والاشتراكات (16)، النطاقات أو الموقع العام أو التسجيل الذاتي (17)، تخصيص المظهر، المدفوعات، SMS/OTP، التكامل مع الشحن، أو أي تغيير في قاعدة بيانات الإنتاج. [1]

## 9. ترتيب التنفيذ المقترح

1. تثبيت قرار الحد المؤقت وتحديد رموز الخطأ العربية المقترحة.
2. إنشاء فرع `phase13-store-switcher` من `main` بعد قرارك الصريح.
3. كتابة اختبارات API السلبية S13-02 وS13-04 إلى S13-08 أولاً على قاعدة الاختبار المحروسة.
4. إضافة list/switch/create مع إعادة استخدام إصدار الجلسة و`createStoreFoundation`.
5. تشغيل اختبارات التكامل والعزل، ثم إضافة واجهة التبديل والإنشاء.
6. تشغيل Browser acceptance، الجوال/سطح المكتب، والانحدار الكامل.
7. إنشاء `PHASE13_REPORT.md` وPR، انتظار CI ومراجعتك، ثم Merge Commit فقط بعد إذنك.

## 10. بوابة قرار البدء

لا يبدأ التنفيذ حتى يصدر قرارك الصريح بالقيم التالية:

| القرار | الاقتراح | أثره |
|---|---|---|
| الحد المؤقت للمتاجر | **3 إجمالاً لكل تاجر** | يمنع إنشاء متجر رابع حتى تدخل حدود الخطط في المرحلة 16. |
| سياسة الجلسة القديمة | تبقى صالحة في متجرها فقط | تحافظ على وعد «جلسة = متجر واحد» وتدعم الأجهزة/التبويبات. |
