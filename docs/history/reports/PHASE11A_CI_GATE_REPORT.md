# تقرير بوابة CI — المرحلة 11A

**الحالة:** بوابة CI اجتازت وظيفتها الحاجبة، مع وظيفة متصفح ظاهرة وغير حاجبة مسجلة كدين تقني. لا يزال PR مفتوحاً ولم تُفعّل حماية `main` ولم يبدأ 11B.

## 1. الغرض والنطاق

ينفذ هذا الفرع الجزء الأول من المرحلة 11A فقط: تعريف GitHub Actions باسم `ci` لتشغيل الفحص والبناء واختبارات التكامل ضد PostgreSQL 16 مؤقت داخل GitHub Actions. لا يقرأ الـworkflow أي سر Neon ولا ينشئ أو يعدّل فرع Neon. يظل 11B، أي فرع `staging` والنشر التلقائي، خارج النطاق بالكامل. [1] [2]

| PR التجريبي | مفتوح: [PR #1](https://github.com/phsaifaldin/CODIQ/pull/1) من `phase11a-ci-staging` إلى `main` | GitHub PR [1] |
| رأس الفرع الذي اجتاز CI | `b64e080c62833b5d4af98e8e9f437d1f53a0dcf4` | GitHub PR/Run [1] [3] |

## 2. ما ينفذه الـworkflow

تعمل وظيفة **`ci / integration`** على كل Pull Request وكل push إلى `main`. تبدأ بتثبيت pnpm مع cache، ثم تولد Prisma Client وتطبق هجرات Prisma على PostgreSQL المؤقت، ثم تشغل `pnpm check` و`pnpm phase1:typecheck` و`pnpm build`. بعد ذلك تنفذ اختبارات المراحل 1 و5 و6 و7 و8A و9A واختبار الخادم المركب للمرحلة 10. [2]

> لا يستخدم الأنبوب أي قيمة اتصال إنتاج أو Neon. جميع متغيرات قواعد البيانات في الوظيفة تشير إلى PostgreSQL خدمة GitHub Actions المحلية فقط.

| خطوة التحقق الحاجبة | نتيجة آخر تشغيل | الدليل |
|---|---|---|
| إعداد PostgreSQL 16 المؤقت وهجرات Prisma | نجح | تشغيل CI رقم 32462604083 [3] |
| فحص TypeScript للواجهة والخلفية | نجح | تشغيل CI رقم 32462604083 [3] |
| بناء التطبيق المركب | نجح | تشغيل CI رقم 32462604083 [3] |
| phase1، phase5، phase6، phase7، phase8A، phase9A، phase10 composite | نجحت | تشغيل CI رقم 32462604083 [3] |
| النتيجة العامة للـworkflow | **Success** | تشغيل CI رقم 32462604083 [3] |

## 3. اختبارات المتصفح وحالة الدين التقني

توجد وظيفة ثانية باسم **`ci / browser acceptance (temporary non-blocking)`**. تثبت Chromium وMoto، ثم تبني التطبيق وتحاول تشغيل اختبارات المتصفح للمرحلات 6 و7 و8B و9B. جعلت الوظيفة غير حاجبة صراحة عبر `continue-on-error: true`؛ فهي لا تُخفى ولا تُسقط من workflow. [2]

في آخر تشغيل، نجحت وظيفة التكامل الحاجبة، لكن فشلت خطوة **`Browser — phase 6`** داخل GitHub Runner؛ لذلك لم تبدأ المراحل اللاحقة في وظيفة المتصفح. الاختبار نفسه اجتاز محلياً ضمن بوابة المرحلة 10، لذا لا توجد دلالة موثقة حتى الآن على خلل في منطق التطبيق أو PostgreSQL. لكن هذا لا يكفي لاعتباره مستقراً في CI. [3] [4]

سُجل هذا كـ **B-15** في `docs/BACKLOG.md`:

> تثبيت اختبارات المتصفح في GitHub Actions، وعزل سبب اختلاف Runner ثم تحويل الوظيفة إلى حاجبة فقط بعد تشغيلات خضراء ثابتة متكررة.

لا ينبغي جعل وظيفة المتصفح فحص حماية إلزامياً قبل معالجة B-15 بموافقة صريحة منفصلة. [4]

## 5. القرار المطلوب من مالك المشروع

تحققت بوابة البند 2 بالمعنى المسموح في المتطلبات: الوظيفة الحاجبة خضراء على PR فعلي، ووظيفة المتصفح لم تُسقط صامتة بل بقيت ظاهرة وغير حاجبة ووثقت كدين. قبل بدء البند 3، يلزم قرار المالك بين المسارين التاليين.

| الخيار | الأثر |
|---|---|
| **A — متابعة حماية `main` الآن** | حماية `main` ستلزم نجاح `ci / integration` فقط. تبقى وظيفة المتصفح واضحة في PR لكن غير حاجبة إلى أن يعالج B-15. هذا متسق مع آلية الاستثناء المؤقتة المعتمدة. |
| **B — إيقاف حماية `main` حتى معالجة B-15** | يمنع تفعيل الحماية حتى تنجح وظيفة المتصفح بثبات. لا تنفيذ إضافي هنا من دون أمر صريح؛ معالجة B-15 ليست ضمن نطاق 11A الحالي. |

## 6. ما لم ينفذ بعد

لم تُفعّل Branch Protection على `main`، ولم تُنشأ `docs/DEPLOYMENT.md` أو `docs/history/reports/PHASE11A_REPORT.md`، ولم يُدمج PR #1. كما لم يبدأ 11B ولم يُنشأ فرع Neon باسم `staging` ولم يحدث أي نشر تلقائي أو يدوي.
