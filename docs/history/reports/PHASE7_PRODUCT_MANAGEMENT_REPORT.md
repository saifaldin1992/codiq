# codiq — المرحلة السابعة: إدارة المنتجات الحقيقية

**تاريخ الاختبار:** 17 أغسطس 2026.  
**النتيجة:** **اجتازت إدارة المنتجات والتصنيفات والمخزون والصور واختبارات IDOR.**  
**النطاق:** لوحة التاجر المقيدة بالمتجر، PostgreSQL/Prisma/Express، وتخزين صور S3-compatible وفق مبادئ النقل المعتمدة.

> يعامل النظام المنتج والتصنيف والصورة وحركة المخزون ككيانات متجرية. لا يقبل أي مسار API `store_id` من العميل؛ يحل الخادم `storeSlug` ثم يطابقه مع جلسة التاجر قبل أي قراءة أو كتابة.

## 1. الوظائف المنفذة ومساراتها

| الوظيفة | واجهة التاجر | API المقيد بالمتجر | النتيجة |
|---|---|---|---|
| قائمة المنتجات | `/merchant/stores/{store-slug}/dashboard/products` | `GET /api/merchant/stores/:storeSlug/catalog/products` | قائمة cursor-paginated بحد افتراضي 25 وحد أقصى 100. |
| إضافة منتج | `/products/add` | `POST /catalog/products` | اسم ووصف وSKU وسعر ومخزون وحد تنبيه وتصنيف وصور. |
| تعديل المنتج | قائمة المنتجات | `PATCH /catalog/products/:productId` | تعديل الاسم والسعر والمخزون وحد التنبيه والتصنيف والحالة. |
| حذف المنتج | قائمة المنتجات | `DELETE /catalog/products/:productId` | يحذف فقط داخل متجر المالك، ويرفض المنتج المستخدم في طلب. |
| التصنيفات | `/products/categories` | `GET/POST/PATCH/DELETE /catalog/categories` | إنشاء وإعادة تسمية وحذف؛ أسماء فريدة لكل متجر وحذف محمي من التصنيف المستخدم. |
| المخزون | `/products/inventory` | `POST /catalog/products/:productId/inventory` | كمية وحركة مخزون بسبب مسجل وتنبيه `is_low_stock` مولّد داخل PostgreSQL. |
| صور المنتجات | نموذج الإضافة وقائمة المنتج | `POST /catalog/products/:productId/images` و`GET .../images/:imageId` | رفع multipart محمي وقراءة صورة مقيدة بجلسة التاجر. |

## 2. نموذج البيانات والحماية البنيوية

أضيفت `product_categories` و`products` و`product_images` و`inventory_movements` ضمن هجرة `20260817093000_store_scoped_product_management`. تحمل كل الجداول `store_id` وفهارس مناسبة لمسارات المتجر، ومنها فهرس المنتجات حسب `(store_id, created_at)` وفهرس المخزون المنخفض حسب `store_id` ومؤشر اسم التصنيف المطبّع داخل المتجر.

القيود تتضمن `UNIQUE(store_id, sku)` و`UNIQUE(store_id, normalized_name)`. وتمنع Triggers PostgreSQL ربط منتج بتصنيف من متجر مختلف، أو ربط صورة أو حركة مخزون بمنتج خارج متجرهما. `is_low_stock` عمود PostgreSQL مولد من الكمية وحد التنبيه، فلا تعتمد حالته على زر واجهة أو قيمة يرسلها العميل.

## 3. رفع الصور والتخزين القابل للنقل

تستخدم الخدمة `@aws-sdk/client-s3` القياسي فقط. يُنشأ مفتاح الصورة ضمن `products/{storeId}/{productId}/{uuid}.{extension}`، وتحفظ القاعدة المفتاح وMIME type والحجم والترتيب، لا بايتات الصورة. يسمح الخادم فقط بـJPEG وPNG وWebP، بحد 5MB للصورة و8 صور للمنتج. لا توجد صور ثابتة محفوظة في مجلد المشروع أو اعتماد على خدمة تخزين مقفلة.

| التحقق | النتيجة |
|---|---|
| اختبار S3 الفعلي | نجح `HeadBucket` ثم رفع كائن تحقق مؤقت وحذفه في حاوية S3-compatible المهيأة. |
| رفع صورة منتج عبر API | `201`، صورة PNG بحجم 66 بايت في محاكي S3-compatible؛ استردادها المصرح به أعاد `200` وبايتات مساوية. |
| رفض صورة غير مسموحة | `422 / INVALID_PRODUCT_IMAGE` لملف `text/plain` عبر مسار الرفع نفسه. |
| رفض صورة تتجاوز 5MB | `422 / INVALID_PRODUCT_IMAGE` من حد multer الخادمي قبل حفظ أي كائن. |
| اختبار المتصفح | تاجر دخل بجلسة HTTP ثم أنشأ تصنيفًا وأعاد تسميته من الواجهة، واختاره عند إنشاء منتج فعلي مع صورة؛ ظهرت البطاقة في القائمة مع عداد صورة واحد. |

## 4. المنتجات والتصنيفات الفعلية في الاختبار

| المتجر | التصنيف | المنتج | حالة المخزون |
|---|---|---|---|
| A — `phase7-…-a` | قهوة عربية | قهوة عربية محمصة، SKU `COFFEE-001`، عدّل سعرها إلى `13,000` د.ع | بدأت 2 مقابل حد 3: تنبيه منخفض؛ ضُبطت إلى 10 فأزيل التنبيه. |
| B — `phase7-…-b` | أدوات مكتبية | مصباح مكتبي، SKU `DESK-001`، `24,500` د.ع | 15 مقابل حد 3: متاح. |

نجحت عمليات الإنشاء (`201`) وتعديل تصنيف A وتعديل منتج A—بما فيه الوصف والسعر (`200`)—وحذف منتج تجريبي يخص A (`204`). رُفض التصنيف المكرر ضمن A بـ`409 / DUPLICATE_CATEGORY`، وحُظر حذف تصنيف A المرتبط بمنتج بـ`409 / CATEGORY_IN_USE`.

## 5. اختبار IDOR وعزل التصنيفات

| محاولة تاجر B مباشرة | النتيجة | رمز الاستجابة |
|---|---:|---|
| `PATCH` منتج A تحت مسار متجر B | `404` | `RESOURCE_NOT_FOUND` |
| `DELETE` منتج A تحت مسار متجر B | `404` | `RESOURCE_NOT_FOUND` |
| قراءة صورة A تحت منتج ومسار B | `404` | `RESOURCE_NOT_FOUND` |
| `PATCH` تصنيف A تحت متجر B | `404` | `CATEGORY_NOT_FOUND` |
| قائمة تصنيفات B تتضمن تصنيف A | لا | لم يظهر أي معرف أو اسم يخص A. |
| إنشاء منتج A بتصنيف B عبر API | `404` | `CATEGORY_NOT_FOUND` |
| تعديل مباشر في PostgreSQL يربط منتج A بتصنيف B | مرفوض | `23514` من Trigger قاعدة البيانات. |

تثبت النتيجة أن تاجر B لا يستطيع تعديل أو حذف منتج A حتى عند تغيير معرف المنتج أو `storeSlug` أو محاولة تجاوز API بقيد SQL مباشر. تعتمد `404` لمورد يطلب تحت متجر صحيح ظاهريًا ولكن لا يملكه، لتقليل إفصاح وجود المورد.

## 7. ملاحظات التوسع المقترحة

تطبق API cursor pagination وفهارس متجرية من البداية. واجهة القائمة الحالية تقرأ أول صفحة حتى 100 منتج، لذلك قبل وصول كتالوج المتجر إلى حجم كبير أو قبل المرحلة الثامنة، يوصى بربط `nextCursor` بتحميل صفحات متتابعة وبحث مفهرس وفق متطلبات المستخدم. كما يوصى في مرحلة منفصلة لاحقة بإضافة outbox معيارية لأعمال معالجة الصور وتنظيف كائنات S3 المؤجلة، بدلاً من إدخال أي طابور خاص بمزود واحد الآن.
