# المرحلة 9 — واجهة المتجر وحساب الزبون

**الحالة:** مسودة معمارية مصححة للمراجعة فقط.  
**قرار التنفيذ:** لا يوجد كود للمرحلة 9، ولا migration، ولا commit، ولا تعديل لمسارات التطبيق قبل موافقة صريحة على هذه الوثيقة كاملة.  
**المرجع الداخلي:** `PROJECT_ENGINEERING_PRINCIPLES.md`، ومخطط Prisma الحالي، و`PHASE8B_REPORT.md`.

## خلاصة المراجعة المعمارية

المسودة الأصلية تتجه في المسار الصحيح: السلة محفوظة خادمياً، وتسجيل الدخول لا يُطلب قبل checkout، والهوية العميلية مقيدة بالمتجر، وCOD هو خيار الدفع الوحيد. لكنها تحتاج إلى تصحيحات بنيوية قبل التنفيذ حتى لا تنتج عزلًا ضعيفاً أو سلات قابلة للتسريب أو طلبات مكررة أو بيعاً يتجاوز المخزون.

| المسألة المكتشفة | التصحيح المعتمد في هذه المسودة |
|---|---|
| `password_hash` و`phone` مقترحان كإضافات | كلا الحقلين موجودان فعلاً في `customers`؛ المطلوب هو ضبط الهاتف المعياري وفهرسته ومنطق دخوله، لا إضافة كلمة مرور ثانية. |
| البريد مطلوب حالياً في `customers` | يصبح البريد اختيارياً للزبون في Storefront، مع الحفاظ على إمكانية إضافته اختيارياً من لوحة التاجر. يمنع اختراع بريد اصطناعي للزبون. |
| `cart_items` يشير إلى `guest_cart` أو `customer_cart` | يُستبدل ذلك بجدول `shopping_carts` واحد؛ لا توجد علاقة polymorphic لا تستطيع PostgreSQL حمايتها بمفتاح أجنبي. |
| `guest_cart_id` داخل الطلب | لا يضاف إلى `store_orders`. يُغلق مصدر السلة عند التحويل، ويُحفظ `checkout_idempotency_key` أو مرجع تحويل تدقيقي محدود إن لزم؛ إبقاء guest cart كمرجع طلب دائم يزيد أثر بيانات الجلسة ولا يضيف حقاً تشغيلياً. |
| `customer_id` موجود بالفعل في `store_orders` | يُفعّل في checkout مع قيد مركب يضمن أن العميل والطلب ينتميان للمتجر نفسه. |
| Token الضيف UUID محفوظ في قاعدة البيانات | لا يُخزن token الخام؛ تُخزن بصمته SHA-256 فقط، ويكون cookie `HttpOnly`, `Secure` في الإنتاج و`SameSite=Lax`. |
| انتهاء السلة بعد 7 أيام | يُفرض عند كل قراءة/تعديل/دمج بصورة كسولة وآمنة؛ التنظيف الخلفي اختياري لاحقاً، وليس شرطاً لصحة العزل أو انتهاء الوصول. |
| إنشاء الطلب غير معرّف تفصيلياً | يُنفذ بمعاملة `Serializable` قابلة للإعادة مع مفتاح idempotency، وقفل للسلة والمنتجات، ولقطات سعر وعنوان وبند طلب. |
| سياسة المخزون غير مذكورة | تحتاج قراراً صريحاً مذكوراً في القسم D؛ التوصية هي حجز الكمية في checkout مع منع تجاوز المتاح، لا تعديل مخزون عند مجرد تغيير حالة مستقل. |
| مسارات العميل الحالية وتلك المقترحة مختلفة | تعتمد هذه المواصفات واجهة عامة متسقة تحت `/store/{storeSlug}`، مع aliases توافقية مؤقتة للمسارات القديمة `/stores/{storeSlug}/account/*` عند التنفيذ. |

> **قرار مطلوب ضمن الموافقة:** تعالج هذه المواصفات الحجز المخزني عند checkout كجزء من إنشاء الطلب، لا كأثر جانبي لمجرد زر تغيير حالة التاجر في 8A. يحافظ ذلك على معيار 8A بأن انتقال الحالة وحده لا يغير المخزون، ويمنع تجاوز المخزون في checkout. التفاصيل في القسم D.

## A. هدف المرحلة والنطاق الوظيفي

تبني المرحلة التاسعة تجربة Storefront وظيفية، وليست تسويقية: الزائر يتصفح كتالوج متجر محدد، يضيف منتجات إلى سلة محفوظة، يسجل أو يدخل بهوية هاتف مقيدة بهذا المتجر عند checkout فقط، يختار عنواناً، ثم ينشئ طلب دفع عند الاستلام (`COD`). بعد الدخول يستطيع الزبون رؤية طلباته وتفاصيلها وتتبع حالات الطلب المسموح بعرضها له.

لا تعدّل المرحلة 9 صلاحيات مالك المنصة أو التاجر التي اعتمدت في 1–8. هي تضيف سطحاً ثالثاً منفصلاً تماماً: **الزبون**. كل قراءة أو كتابة زبونية تبدأ بحل `storeSlug`، ثم تقييد الاستعلام بـ`store_id`، ثم التحقق من جلسة العميل عند الحاجة. إخفاء عنصر واجهة لا يعد حماية؛ الخادم وقاعدة البيانات هما طبقتا المنع.

| داخل المرحلة 9 | خارج المرحلة 9 |
|---|---|
| كتالوج عام، تفاصيل منتج، صور عامة مقيدة بالمنتج الفعال، وسلة ضيف/عميل. | صفحة تسويقية عامة للمنصة أو تسجيل ذاتي للتاجر. |
| تسجيل/دخول العميل بالهاتف وكلمة المرور، مع حقل بنيوي جاهز للتحقق الهاتفي مستقبلاً. | SMS أو OTP أو مزود رسائل أو تفعيل فعلي للهاتف. |
| دمج سلة الضيف مع سلة العميل، checkout آمن، COD فقط، وعناوين العميل. | بوابات دفع إلكترونية، كوبونات، خصومات، شحن طرف ثالث، أو فواتير. |
| سجل الزبون وتفاصيله وتتبعه المقيّد بالطلب والعميل والمتجر. | إلغاء زبوني ذاتي للطلب، طلب إرجاع، محادثة، تقييمات، أو إشعارات. |
| واجهات RTL One UI وظيفية مع حالات تحميل/خطأ/فراغ. | صقل بصري نهائي، تخصيص قالب المتجر، أو CMS/SEO متقدم. |

## B. الهوية والجلسات وعزل المتاجر

### B.1 هوية العميل

يبقى **الهاتف + كلمة المرور** وسيلتي الدخول فقط. ومع ذلك، يحتاج النظام اسماً ظاهراً لتكوين `store_orders.customer_name` غير القابل للفراغ وسجل عنوان مفيد. لذلك تفرق المواصفات بين **بيانات الاعتماد** و**بيانات الملف**: لا يُستخدم الاسم كمعرّف دخول، لكنه حقل إلزامي للتسجيل أو checkout الأول. هذا لا يغير قرار «الهاتف + كلمة المرور فقط» كآلية مصادقة.

| الحقل | القاعدة المصححة |
|---|---|
| `phone_normalized` | قيمة موحدة بصيغة E.164، مطلوبة لكل حساب Storefront جديد، وفريدة ضمن `store_id` فقط. |
| `phone` | قيمة العرض التي أدخلها المستخدم، اختيارية إن قررنا الاحتفاظ بها؛ لا تستخدم في البحث أو التفويض. |
| `password_hash` | موجود حالياً؛ يستمر باستخدام خوارزمية hash المعتمدة، ولا تسجل كلمة المرور أو token في السجلات. |
| `full_name` | مطلوب كبيان ملف/تسليم، لا كمعرّف دخول. |
| `email` | يصبح اختيارياً؛ عند وجوده يطبع ويقيد فريداً داخل المتجر فقط. |
| `phone_verified_at` | حقل nullable جاهز لتفعيل SMS/OTP لاحقاً، ولا يفرض التحقق في هذه المرحلة. |

لا يسمح عدم وجود OTP باعتبار رقم الهاتف موثقاً. حالة عدم التحقق لا تمنع COD في المرحلة 9 بحسب القرار المعتمد، لكنها تبقى واضحة في النموذج لتفعيل التحقق لاحقاً بلا تغيير بنيوي.

### B.2 سياسة الجلسات والكوكيز

يجب فصل Cookie العميل عن Cookie المالك والتاجر الحالية؛ لا تستخدم المرحلة 9 cookie عامة واحدة لكل الهويات. ينشأ cookie مستقل باسم `codiq_customer_session` يحتوي token جلسة زبون `HttpOnly`، و`Secure` في الإنتاج، و`SameSite=Lax`، ومقيد بمسار متجر العميل `/store/{storeSlug}`. يتحقق الحارس الخادمي من نوع الجلسة `customer` ثم من أن `customers.store_id` يطابق store resolved من المسار.

تسمح هذه السياسة بجلستين مستقلتين للعميل نفسه على متجرين مختلفين في المتصفح ذاته، وتمنع cookie عميل متجر A من أن تصبح اعتماداً لمتجر B. تبقى الجلسات القديمة ومسارات الحساب السابقة فعالة فقط كمسارات توافقية خلال التنفيذ، ثم يحدد حذفها في مرحلة مستقلة بعد انتقال الواجهة.

### B.3 سلة الضيف

عند أول عملية تغير السلة — **وليس عند زيارة الصفحة فقط** — ينشئ الخادم cart ضيفاً. ينشئ token عشوائياً عالي الإنتروبيا في cookie `codiq_cart_{storeSlug}`، لكن يخزن في قاعدة البيانات `session_token_hash` فقط. لا تقبل API معرف cart أو token من body أو query؛ cookie هو القناة الوحيدة لمعرف سلة الضيف.

| قاعدة العزل | النتيجة المطلوبة |
|---|---|
| المتصفح A مقابل B | لكل متصفح token مستقل؛ لا يمكن لسلة A الظهور في B حتى داخل المتجر نفسه. |
| المتجر A مقابل B | الكوكي ومسار السلة وحل المتجر تكون مقيدة بـ`storeSlug`، وFK مركب يمنع إضافة منتج B إلى cart A. |
| cookie مسروق أو معدّل | لا يكفي `cart_id`؛ يلزم token سري تطابق بصمته، مع `HttpOnly` و`Secure` وحدود معدل. |
| السلة المنتهية | يرفض الوصول إليها كجلسة فعالة ويمسح cookie؛ لا تعاد تلقائياً. |

## C. تغييرات قاعدة البيانات النهائية

تطبق التغييرات بهجرة additive-first واحدة أو هجرات فرعية مترتبة بعد الموافقة. لا تستخدم `ON DELETE CASCADE` على أوامر أو حسابات إنتاجية؛ تحفظ لقطات الطلب تاريخياً حتى إذا تغير المنتج أو العنوان لاحقاً.

### C.1 تعديل `customers`

| التغيير | الغرض والضمان |
|---|---|
| جعل `email` nullable | يدعم دخول الهاتف فقط، ويحافظ على البريد الاختياري للحسابات اليدوية. |
| استبدال unique الصلب الحالي بـpartial unique للبريد | يمنع تكرار البريد عند وجوده داخل متجر واحد، ويسمح بأكثر من `NULL` بصورة طبيعية. |
| إضافة `phone_normalized text` | المعرف المعياري الحقيقي لتسجيل/دخول العميل. |
| إضافة `phone_verified_at timestamptz null` | نقطة جاهزية OTP غير التشغيلية. |
| `UNIQUE (store_id, phone_normalized)` بصورة partial | يسمح بهواتف قديمة أو حسابات يدوية بلا هاتف أثناء انتقال البيانات، ويمنع التكرار للحسابات الهاتفية. |
| فهرس `(store_id, phone_normalized)` | مسار تسجيل الدخول وعزل الهوية. |

الهجرة لا تجعل سجلات العملاء القديمة بلا هاتف غير صالحة تلقائياً. كل حساب Storefront جديد يجب أن يحمل هاتفاً معيارياً، بينما الحسابات اليدوية القديمة تبقى قابلة للإدارة ولا تستطيع استخدام تسجيل دخول الهاتف حتى تزويدها بهاتف صالح. هذا يمنع تحويلاً مدمراً أو اختراع بيانات.

### C.2 جدول موحد `shopping_carts`

| الحقل | القاعدة |
|---|---|
| `id`, `store_id` | UUID، مع unique مركب `(id, store_id)` لدعم مفاتيح العزل المركبة. |
| `owner_kind` | `guest` أو `customer` فقط عبر CHECK. |
| `customer_id` | nullable؛ مطلوب لسلة العميل وممنوع لسلة الضيف عبر CHECK. |
| `session_token_hash` | nullable؛ مطلوب لسلة الضيف وممنوع لسلة العميل عبر CHECK. لا token خام. |
| `status` | `active`, `merged`, `converted`, `expired`; لا حذف تشغيلي فوري للسلات المحولة. |
| `version` | optimistic concurrency للدمج وcheckout. |
| `expires_at` | مطلوب لضيف (7 أيام من آخر نشاط وفق السياسة)، وnullable لسلة العميل النشطة. |
| `merged_into_cart_id`, `converted_order_id` | مراجع تدقيقية اختيارية تمنع إعادة التحويل أو checkout المضاعف. |
| timestamps | `created_at`, `updated_at`, `last_activity_at`. |

تضاف قيود partial unique: سلة عميل نشطة واحدة فقط لكل `(store_id, customer_id)`، وبصمة token نشطة واحدة فقط لكل متجر. يضاف فهرس `(store_id, status, expires_at)` لانتهاء الصلاحية والفهرس `(store_id, customer_id, status)` لاسترجاع سلة العميل.

### C.3 جدول `cart_items`

| الحقل | القاعدة |
|---|---|
| `id`, `cart_id`, `store_id`, `product_id` | UUID؛ `store_id` متكرر عمداً لتطبيق FK مركب مع السلة والمنتج. |
| `quantity` | integer موجب، بحد أعلى تجاري يحدد في الخدمة لمنع إساءة الاستهلاك. |
| `price_snapshot_iqd` | integer غير سالب، لقطة سعر المنتج عند الإضافة أو عند دمج السلة حسب القرار. |
| `created_at`, `updated_at` | تدقيق زمني. |

تضاف القيود: unique `(cart_id, product_id)`؛ FK `(cart_id, store_id)` إلى `shopping_carts(id, store_id)`؛ وFK `(product_id, store_id)` إلى `products(id, store_id)`. يلزم إضافة unique مركب `(id, store_id)` إلى `products`. بهذا يصبح إدخال منتج متجر B في سلة متجر A مستحيلاً بنيوياً حتى مع خطأ في التطبيق.

### C.4 عناوين العميل `customer_addresses`

| الحقل | القاعدة |
|---|---|
| `id`, `store_id`, `customer_id` | UUID، مع FK مركب يربط العميل والمتجر. |
| `recipient_name`, `full_address`, `city`, `governorate`, `phone_contact_normalized` | لقطات بيانات التسليم القابلة للتحقق. |
| `is_default` | default واحد على الأكثر لكل عميل/متجر عبر partial unique. |
| timestamps | إنشاء وتحديث، مع soft deletion اختياري فقط إذا احتجنا حفظ مرجع واجهة. |

لا يشير الطلب إلى عنوان حي بوصفه مصدر حقيقة. عند checkout، تنسخ البيانات إلى حقول الطلب الموجودة (`customer_name`, `recipient_phone`, `shipping_governorate`, `shipping_address_line1`, `shipping_address_line2`) حتى لا يغير تعديل عنوان لاحق الطلب السابق.

### C.5 تعديل `store_orders` و`order_items`

| التغيير | القاعدة |
|---|---|
| تفعيل `customer_id` الموجود | يجب أن يكون العميل من المتجر نفسه عبر FK مركب `(customer_id, store_id)` إلى `customers(id, store_id)`. |
| `payment_method_code` | قيمة `cod` فقط في المرحلة 9 عبر CHECK؛ `payment_status='unpaid'` عند الإنشاء. |
| `checkout_idempotency_key` | قيمة مطلوبة في checkout، فريدة ضمن `(store_id, customer_id, checkout_idempotency_key)` لمنع إنشاء طلبين من إعادة إرسال واحدة. |
| `source` | يضبط إلى `storefront`. |
| `order_status_events` | يضاف حدث append-only عند الإنشاء: `from_status = NULL`, `to_status = new`, `actor_kind = customer`, و`actor_id = customer_id`. قيد 8A يدعم `customer` بالفعل. |
| `order_items` | تنشأ من `cart_items` مع لقطة الاسم وSKU والسعر والكمية والإجمالي. |

لا يضاف `guest_cart_id` إلى الطلب. السلة ليست هوية طلب ولا يجب أن تفتح طريقاً لقراءة طلب عبر token ضيف منتهٍ أو مسروق. إذا احتاج التدقيق مرجع تحويل، يبقى في `shopping_carts.converted_order_id` ومغلقاً على التحويل نفسه.

## D. منطق السلة والدمج وcheckout والمخزون

### D.1 دورة حياة السلة

```text
ضيف —(أول إضافة)→ guest active
guest active —(تسجيل/دخول ناجح)→ merged أو converted إلى customer active
customer active —(checkout ناجح)→ converted
guest active —(expires_at ≤ now)→ expired
```

السلة المنتهية لا تقبل قراءة أو تعديل أو دمج. يُمسح cookie، ويعامل الطلب كسلة جديدة. لا تحتاج صحة هذا السلوك وظيفة زمنية؛ يفحص الخادم `expires_at` في كل endpoint. يمكن إضافة تنظيف يومي لاحقاً لحذف/أرشفة السلات المنتهية بعد نشر الموقع، لكنه تحسين مساحة وليس أساساً أمنياً أو وظيفياً.

| آلية الانتهاء | التجارة بين الخيارات | القرار في المرحلة 9 |
|---|---|---|
| فحص كسول عند كل طلب | لا يحتاج عملية خلفية، ويمنع الاستعادة فوراً حتى إن لم ينفذ تنظيف. | **معتمد.** |
| تنظيف يومي للخلفية | يستعيد مساحة أسرع، لكنه يحتاج موقعاً منشوراً وhandler محمياً وعملية idempotent. | مؤجل كتحسين تشغيلي؛ لا ينفذ الآن. |

### D.2 إضافة وتحديث السلة

عند الإضافة، يحل الخادم المتجر أولاً ويقرأ المنتج بقايدين: `store_id` مطابق و`is_active=true`. يرفض منتجاً غير موجود أو غير فعال أو كمية غير صالحة بـ`404` أو `422`. يحفظ `price_snapshot_iqd` بسعر المنتج وقت الإضافة. تغيير السعر بعد ذلك لا يعيد تسعير السلة تلقائياً؛ يبقى السعر محفوظاً كما طلبت المسودة الأصلية.

لا تحجز الإضافة إلى السلة المخزون. يفحص checkout فقط توفر الكمية داخل معاملته، لأن حجز المخزون عند التصفح يجعل المخزون محجوزاً لزوار لا ينوون الشراء.

### D.3 الدمج بعد التسجيل أو الدخول

يسجل أو يدخل العميل في المتجر نفسه، ثم يستدعي الخادم عملية دمج داخل معاملة `Serializable` قابلة لإعادة المحاولة عند التعارض. يقفل cart الضيف وسلة العميل النشطة والصفوف المتأثرة، ويتحقق من store متماثل وعدم انتهاء الضيف، ثم:

1. ينشئ سلة عميل نشطة إن لم توجد.
2. يدمج العناصر ذات `product_id` نفسه بجمع الكمية.
3. يحدّث `price_snapshot_iqd` لكل المنتج المدمج إلى السعر الفعال الأحدث، كما قررت المسودة.
4. يعلّم سلة الضيف `merged` ويملأ `merged_into_cart_id` ثم يمسح cookie الضيف.
5. يعيد السلة النهائية والإصدار الجديد فقط بعد commit ناجح.

إذا لم يوجد حساب سابق، تتحول سلة الضيف إلى سلة العميل في المعاملة نفسها أو تنشأ سلة عميل وتنقل العناصر؛ لا توجد فترة تستطيع فيها API قراءة عناصر بلا مالك صحيح. إعادة إرسال login أو register لا تضاعف العناصر لأن cart الضيف لا يدمج مرتين.

### D.4 checkout وCOD

التحويل إلى طلب لا يعتمد على الواجهة. إذا حاول ضيف استدعاء endpoint مباشرة، يعود الخادم بـ`401 CUSTOMER_SESSION_REQUIRED` ولا ينشئ طلباً أو حركة مخزون. واجهة `/checkout` توجه الضيف إلى login/register، لكن حارس الخادم هو الحد النهائي.

ينفذ checkout بمعاملة واحدة، وبـidempotency key صالح من الواجهة:

1. يتحقق من جلسة العميل ومن مطابقة العميل والمتجر.
2. يقفل سلة العميل النشطة ويقارن `version`، ويتحقق من أنها غير فارغة وغير محولة.
3. يتحقق من العنوان المختار أو عنوان التسليم المدخل: ملكية العميل، `store_id`، وصحة الاسم والهاتف والمحافظة والعنوان.
4. يقفل المنتجات، ويتحقق من كونها فعالة ومن توفر الكمية، ويعيد حساب الإجمالي من `price_snapshot_iqd` الموجود في السلة لا من السعر الحالي.
5. ينشئ `store_orders` بحالة `new` و`payment_method_code=cod` و`payment_status=unpaid` ولقطات العميل والعنوان.
6. ينشئ `order_items` وسجل `order_status_events` الأولي append-only.
7. يطبق سياسة حجز المخزون المعتمدة أدناه، ثم يعلّم السلة `converted` ويربطها بالطلب.
8. يعيد نفس الطلب من المحاولة المكررة ذات `checkout_idempotency_key`؛ ولا ينشئ طلباً أو خصماً جديداً.

### D.5 قرار المخزون المطلوب

تمنع المعاملة تجاوز الكمية المتاحة عند checkout. توجد سياستان سليمتان، ويجب عدم دمجهما ضمنياً:

| السياسة | السلوك | الأثر |
|---|---|---|
| **الحجز المنفصل — التوصية** | يضاف `inventory_reservations` للطلب؛ المتاح = `stock_quantity - active reservations`. يلغي أو يرفض الطلب الحجز، ويحول التنفيذ اللاحق الحجز إلى حركة مخزون وفق مرحلة fulfillment مستقلة. | يمنع oversell من دون إنقاص المخزون الفعلي عند `new`. يحتاج تكاملاً محدوداً ومدروساً مع إلغاء/رفض التاجر. |
| خصم عند checkout | ينقص `stock_quantity` وينشئ حركة `checkout_cod`. تلغي أو ترفض الطلب تعويضاً يدقق به. | أبسط حالياً، لكن يغير المخزون فوراً ويحتاج سياسة واضحة للمرتجع والطلب الذي لم يسلم. |

**التوصية لهذه المواصفات: الحجز المنفصل.** لا تتغير قاعدة 8A بأن زر انتقال الحالة المجرد لا يعدل المخزون. إن وافقت على هذا القرار، تقسم مرحلة 9 تقنياً إلى **9A-1 (الحجز والـcheckout الخلفي)** ثم **9A-2 (الواجهة والحساب)**، مع اختبارات تعويض الحجز عند `cancelled` و`rejected`. لا ينفذ خصم نهائي للمرتجع في المرحلة 9؛ سيعالج ضمن دورة إرجاع/تسليم مستقلة لاحقة.

## E. واجهات API النهائية

تكون كل الردود JSON وتعيد الأخطاء بصيغة CODIQ القائمة `{ error: { code, message } }`. تطبق rate limiting على التسجيل وتسجيل الدخول وكل إنشاء cart وcheckout؛ لا يكشف login ما إذا كان الهاتف مسجلاً.

### E.1 storefront العام والسلة

| الطريقة والمسار | الحماية | السلوك |
|---|---|---|
| `GET /store/:storeSlug/products` | عام | قائمة cursor-paginated لمنتجات المتجر الفعالة فقط، مع التصنيف والصورة العامة الآمنة. |
| `GET /store/:storeSlug/products/:productId` | عام | منتج فعال من المتجر فقط؛ `404` لمنتج متجر آخر أو غير فعال. |
| `GET /store/:storeSlug/products/:productId/images/:imageId` | عام مقيد | يعرض صورة منتج فعال من المتجر نفسه فقط؛ لا يفتح مسارات S3 الخام. |
| `GET /store/:storeSlug/cart` | cookie cart أو جلسة عميل | يقرأ سلة العميل، أو سلة الضيف المطابقة للـcookie، أو يعيد سلة فارغة بعد expiration. |
| `POST /store/:storeSlug/cart/items` | cookie cart أو عام لإنشاء الضيف | ينشئ/يحدث سلة المتجر، ويدمج المنتج نفسه، ويأخذ لقطة السعر. |
| `PATCH /store/:storeSlug/cart/items/:itemId` | مالك cart | يعدل كمية عنصر داخل cart المصرح فقط. |
| `DELETE /store/:storeSlug/cart/items/:itemId` | مالك cart | يحذف عنصر cart المصرح فقط. |

### E.2 حساب العميل والعناوين

| الطريقة والمسار | الحماية | السلوك |
|---|---|---|
| `POST /store/:storeSlug/account/register` | عام + rate limit | ينشئ حساباً بهاتف معيار وكلمة مرور وبيان الاسم؛ يدمج سلة الضيف بعد النجاح، وينشئ cookie عميل. |
| `POST /store/:storeSlug/account/login` | عام + rate limit | يثبت الهاتف/كلمة المرور داخل المتجر فقط، يدمج السلة، وينشئ cookie عميل. |
| `POST /store/:storeSlug/account/logout` | جلسة عميل | يلغي session ويمسح cookie العميل فقط. |
| `GET /store/:storeSlug/account` | جلسة عميل للمتجر | يعرض ملفاً آمناً بلا `password_hash`. |
| `GET /store/:storeSlug/account/addresses` | جلسة عميل للمتجر | عناوين العميل نفسه داخل المتجر فقط. |
| `POST /store/:storeSlug/account/addresses` | جلسة عميل للمتجر | ينشئ عنواناً مع ضبط default معاملاتي. |
| `PATCH` / `DELETE /store/:storeSlug/account/addresses/:addressId` | جلسة عميل للمتجر | يعدل/يحذف عنوان العميل نفسه؛ `404` لعنوان آخر. |

### E.3 checkout والطلبات

| الطريقة والمسار | الحماية | السلوك |
|---|---|---|
| `POST /store/:storeSlug/checkout` | جلسة عميل + `Idempotency-Key` | ينشئ طلب COD من سلة العميل النشطة داخل معاملة؛ يعيد `201` لأول طلب و`200` عند إعادة المحاولة المطابقة. |
| `GET /store/:storeSlug/account/orders` | جلسة عميل للمتجر | قائمة cursor-paginated للطلبات التي تملك `customer_id` مساويًا للجلسة فقط. |
| `GET /store/:storeSlug/account/orders/:orderId` | جلسة عميل للمتجر | تفاصيل order وitem snapshots وحالة مناسبة للعميل فقط؛ `404` لأي طلب آخر. |
| `GET /store/:storeSlug/account/orders/:orderId/history` | جلسة عميل للمتجر | timeline مخصص للعميل؛ يخفي `actor_id` وملاحظات التاجر/المنصة الداخلية. |

تبقى المسارات الحالية `/stores/:storeSlug/account/register` و`/login` aliases انتقالية، لكنها لا تصبح المسارات الرئيسية للواجهة الجديدة. لا يحذف أي مسار قائم في المرحلة 9 من دون اختبار توافق صريح.

| رمز الاستجابة | مثال |
|---|---|
| `400` | هاتف أو عنوان أو idempotency key غير صالح. |
| `401` | checkout أو account API من دون customer session. |
| `403` | cookie/session مرتبطة بمتجر آخر أو هوية غير زبون. |
| `404` | منتج أو cart item أو عنوان أو order خارج نطاق المتجر/العميل. |
| `409` | هاتف مكرر داخل المتجر، cart version conflict، أو تعارض idempotency payload. |
| `422` | سلة فارغة/منتهية، منتج غير متاح، كمية تتجاوز المتاح، أو انتقال غير صالح. |
| `429` | حد معدل التسجيل أو login أو checkout. |

## F. الواجهات وAcceptance Criteria

### F.1 المسارات الأمامية

| المسار | الصفحة | الحماية |
|---|---|---|
| `/store/{slug}` | كتالوج المتجر | عام. |
| `/store/{slug}/products/{productId}` | تفاصيل منتج | عام، منتج فعال مقيد بالمتجر. |
| `/store/{slug}/cart` | السلة | عام مع cookie ضيف/عميل. |
| `/store/{slug}/checkout` | نموذج عنوان وتأكيد COD | يعرض redirect/login للضيف؛ API محمية بالخادم. |
| `/store/{slug}/account/register` | التسجيل | عام. |
| `/store/{slug}/account/login` | الدخول | عام. |
| `/store/{slug}/account/orders` | سجل طلبات الزبون | جلسة عميل المتجر. |
| `/store/{slug}/account/orders/{orderId}` | تفاصيل وتتبع الطلب | جلسة عميل مالك الطلب فقط. |

تعتمد الواجهة العربية RTL وOne UI وظيفياً: بطاقات مقروءة، حالات تحميل وفراغ وخطأ، أزرار قابلة للوصول بلوحة المفاتيح، وتنبيه واضح قبل إرسال checkout. لا تدخل المرحلة في صقل بصري كامل أو قوالب متجر متقدمة.

### F.2 سيناريوهات القبول الإلزامية

| المعرف | السيناريو | النتيجة المطلوبة |
|---|---|---|
| SF-01 | زائر يفتح Store-A ويرى الكتالوج. | تظهر منتجات Store-A الفعالة فقط؛ منتج Store-B أو منتج غير فعال يعود `404`. |
| SF-02 | متصفحان يضيفان إلى Store-A. | السلتان مختلفتان ولا تتبادلان العناصر. |
| SF-03 | يحاول العميل وضع productId من Store-B في cart Store-A. | رفض `404` أو `422` قبل إنشاء cart item؛ يؤكد FK المركب عدم إمكان التسرب. |
| SF-04 | يضيف المنتج ثم يغير التاجر سعره. | تبقى `price_snapshot_iqd` في السلة كما عند الإضافة. |
| SF-05 | يعدل كمية إلى صفر أو سالبة أو أكبر من حد الخدمة. | رفض `422` ولا تتغير السلة. |
| SF-06 | تفتح سلة ضيف بعد 7 أيام. | لا تستعاد؛ تمسح cookie وتظهر سلة فارغة. |
| CA-01 | التسجيل بالهاتف نفسه في Store-A مرتين. | رفض `409`; ويقبل الهاتف نفسه في Store-B كحساب مستقل. |
| CA-02 | login برقم خاطئ أو رقم غير موجود. | رد `401` موحد من دون كشف وجود حساب. |
| CA-03 | تسجيل/دخول ضيف له 3 عناصر وحساب بلا سلة. | تنتقل العناصر الثلاثة مرة واحدة إلى سلة العميل. |
| CA-04 | دخول ضيف لحساب له سلة سابقة فيها منتج مشترك. | تجمع الكميات وتحدّث لقطة المنتج المشترك إلى السعر الأحدث. |
| CA-05 | يعاد إرسال login أو register مع سلة الضيف نفسها. | لا تضاعف عناصر cart، وتكون السلة الضيف `merged` مرة واحدة. |
| CA-06 | يبدل العميل المسار من Store-A إلى Store-B وهو يحمل جلسة A. | رد `403`؛ لا تظهر بيانات أو سلة أو عناوين A في B. |
| CO-01 | يدخل ضيف `/checkout` أو يستدعي POST مباشرة. | الواجهة توجهه للدخول، والخادم يعيد `401` ولا ينشئ order. |
| CO-02 | ينفذ عميل checkout بكمية متاحة وعنوانه الصحيح. | ينشأ طلب `new`، عناصر ومبالغ snapshots وحدث customer وCOD، وتغلق السلة. |
| CO-03 | يعيد المتصفح POST checkout بالمفتاح نفسه. | يعود الطلب نفسه؛ لا يتكرر order أو event أو حجز/خصم. |
| CO-04 | ترسل محاولتان متزامنتان checkout للسلة نفسها. | ينشأ طلب واحد فقط؛ الأخرى تستقبل النتيجة المكررة أو تعارضاً آمناً. |
| CO-05 | يتغير المنتج إلى inactive أو تنخفض كميته قبل commit. | تفشل المعاملة `422` من دون طلب جزئي أو cart محولة. |
| CO-06 | تحاول سلتان معاً شراء كمية تتجاوز المتاح. | تنجح كمية ضمن المتاح فقط؛ الأخرى ترفض وفق سياسة الحجز المتفق عليها. |
| CO-07 | يرسل عميل addressId لعميل آخر أو Store-B. | `404` بلا كشف بيانات العنوان. |
| OR-01 | العميل يفتح قائمة طلباته في Store-A. | يرى طلباته A فقط بترقيم cursor؛ لا يرى طلب B أو طلب عميل A آخر. |
| OR-02 | يفتح العميل `orderId` لعميل آخر في المتجر نفسه أو متجر آخر. | `404` وليس `403` لتقليل كشف الموارد. |
| OR-03 | يعرض سجل الطلب للزبون. | يعرض الحالة والزمن فقط؛ لا يعرض `actor_id` أو ملاحظات تشغيل داخلية. |
| UI-01 | فحص الهاتف وRTL وحالات الشبكة. | تعمل السلة وlogin وcheckout والطلبات مع focus واضح ورسائل عربية وعدم فقد سلة محلية ظاهراً. |

## G. ما يؤجل ونقاط التوافق المستقبلي

### G.1 خارج التنفيذ الصريح

لا تنفذ هذه المرحلة SMS/OTP، أو مزود رسائل، أو الدفع الإلكتروني، أو طرق دفع أخرى غير COD، أو كوبونات، أو خصومات، أو شحن طرف ثالث، أو استرداد، أو إلغاء ذاتي للزبون، أو مراجعات، أو إشعارات، أو قائمة رغبات، أو تطبيق محمول، أو صقل بصري نهائي، أو ذاتية تسجيل التاجر أو اشتراكاته.

لا تشغل مهمة زمنية لتنظيف السلات ولا تستخدم مؤقتات عملية داخل الخادم. ينفذ انتهاء السلة كسلوك قراءة/كتابة كسول. وإذا أضيف تنظيف يومي لاحقاً، فيجب أن يكون endpoint منشوراً ومحمياً وidempotent، وبعد موافقة مستقلة، لا `setInterval` أو job داخل process.

### G.2 التوافق المستقبلي

| المرحلة المستقبلية | نقطة التكامل المحفوظة الآن |
|---|---|
| SMS/OTP | `phone_normalized` و`phone_verified_at` وحالة عدم التحقق من دون إرسال رسائل الآن. |
| الدفع الإلكتروني | `payment_method_code`, `payment_status`, idempotency key، وorder snapshots؛ تضاف محاولات الدفع وجداول provider لاحقاً. |
| الشحن والتسليم | لقطات العنوان والمحافظة والهاتف داخل order، مع مكان واضح لرسوم delivery لاحقاً. |
| كوبونات وأسعار | لقطة cart مستقلة ولقطة order مستقلة؛ يمكن لاحقاً حساب discount قبل commit من دون إعادة كتابة الماضي. |
| fulfillment والمرتجعات | `inventory_reservations` الموصى به يعزل حجز checkout عن حركة المخزون الفعلية وعن إرجاع البضاعة. |
| تحديث الواجهة | فصل Storefront routes ومكوّنات cart/account عن لوحة التاجر والمالك يسمح بصقل One UI أو قالب متجر لاحقاً. |

## قرار المراجعة

المسودة تصبح قابلة للتنفيذ بعد موافقة صريحة على هذه المواصفات، وبالأخص على: **(1)** جعل البريد اختيارياً للعميل مع الهاتف المعياري كمعرّف دخول، **(2)** نموذج `shopping_carts` الموحد بدلاً من cart polymorphic، **(3)** تخزين بصمة token الضيف فقط، و**(4)** سياسة الحجز المنفصل للمخزون عند checkout.

لن يبدأ أي تنفيذ أو migration أو commit للمرحلة التاسعة قبل تلك الموافقة.
